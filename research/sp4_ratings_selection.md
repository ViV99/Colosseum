## 0. Короткий вывод

1. Единственный источник истины — **журнал матчей** (match log). Рейтинги вычисляются из него; онлайн-рейтинг во время обучения — только индикатор прогресса.
2. Главная модель для отбора — **batch Bradley–Terry (логистическая регрессия со знаковой матрицей включений) с гауссовым приором и bootstrap-интервалами**. Она единообразно покрывает 1v1, команды (сумма сил участников), FFA (парная декомпозиция или Plackett–Luce) и ничьи (Davidson или счёт 0.5).
3. Сущность рейтинга — `(agent_id, policy_version)` (снапшот), плюс скриптовые и замороженные агенты. «latest» — не сущность: матчи latest приписываются корзине версий.
4. Для финального выбора рейтинг служит только **фильтром кандидатов**. Победителя выбирают по свежим играм (hold-out) против заранее заданного поля. Иначе проклятие победителя завышает оценку лучшего (по моей симуляции — на 2–8 п.п. win rate при 20–200 кандидатах).
5. Из внешних библиотек: `openskill` (MIT, активна) годится как опциональный онлайн-индикатор для команд и рангов. `trueskill` (BSD, релиз 2018) и `choix` — только для перекрёстной проверки. Основная подгонка — свой компактный модуль на numpy/scipy.

### 1.2 Elo: проблемы именно в нашем случае

Подтверждено Balduzzi et al. [источник: arXiv 1806.02643, Introduction]:
- Elo закладывает транзитивность: в циклических играх (камень–ножницы–бумага) он «бессмыслен — не имеет предсказательной силы».
- Рейтинг Elo можно раздуть, заведя много копий агента, которого он обыгрывает (и наоборот). Для нас это важно: сотни почти одинаковых снапшотов одной линии — это и есть «клоны».

Дополнительно [вывод]:
- Игрок «latest» меняется непрерывно. Онлайн-Elo с постоянным K отслеживает его дрейф, но не отделяет дрейф от шума.
- Выбор оппонента через PFSP зависит от истории результатов. Для байесовского и правдоподобного вывода такая адаптивность допустима (отбор зависит только от уже наблюдённых данных). Но онлайн-Elo с ней смещён: он обновляется «против сложных», а не против репрезентативного поля.
- Ничьи в Elo — просто счёт 0.5. Для крестиков-ноликов с высокой долей ничьих это сжимает шкалу.
- Перевод шкалы: win rate 52 % ≈ 14 Elo, 55 % ≈ 35 Elo, 60 % ≈ 70 Elo [вывод, `Δ = 400·log10(p/(1−p))`].

### 1.3 Ничьи

- **Счёт 0.5** (в логистической регрессии: ничья = 0.5 победы и 0.5 поражения при одной игре в знаменателе). Просто, совместимо с MM-алгоритмами `choix` через дробные счётчики, но модель не знает про «зону ничьей». [вывод]
- **Davidson (1970)**: `P(i>j)=π_i/(π_i+π_j+ν√(π_iπ_j))`, `P(draw)=ν√(π_iπ_j)/(…)`. **Rao–Kupper (1967)**: порог θ для ничьей. Оба — [память]. Добавляют один параметр ν (или θ) на раскладку. Предпочтителен Davidson: прост и стандарт для шахмат (BayesElo использует похожий параметр `drawElo`) [память].
- **TrueSkill**: явный `draw_probability` (OpenAI Five: `0.02`) [источник: arXiv 1912.06680, App. J]. В `openskill`: равные ранги или очки.
- Влияние на статистику [замер]: при доле ничьих 30 % дисперсия счёта за партию падает с 0.25 до 0.175, при 60 % — до 0.10. То есть высокая доля ничьих сама по себе сокращает нужное число игр, но сжимает различия в силах. В крестиках-ноликах для сильных агентов основная информация лежит в редких поражениях.

### 1.4 Команды

Три случая из нашей постановки:

1. **Один бот управляет командой юнитов** (`Units`): сущность — бот; команда внутри не раскладывается.
2. **Несколько ботов в команде** (`teammates: self | mixed`): стандартная модель сил `s_team = Σ_k r_{a_k}` (TrueSkill, Weng–Lin и OpenSkill устроены так) [источник: документация openskill; Weng–Lin JMLR 2011]. Вклад отдельного бота идентифицируется только при **разнообразных составах**; при `teammates: self` (однородные команды) вклад каждого неотличим от удвоенной силы, что для отбора нормально. [вывод]
3. **Командная игра с разными ролями**: см. 1.6.

Реализация в batch BT: строка матча — вектор `x ∈ {−1,0,+1}^{n}`, `+1` для членов первой команды, `−1` для второй (с кратностью, если бот занимает несколько мест); `P(победа первой) = σ(xᵀ r)`. Это обычная логистическая регрессия на разреженной матрице. [вывод]

### 1.5 FFA и ранги

- Точная модель — **Plackett–Luce**: `P(ранжирование) = ∏_k π_{(k)} / Σ_{j≥k} π_{(j)}`. В `choix`: `ilsr_rankings`, `opt_rankings`, `mm_rankings` (ряды рангов без ничьих) [источник: choix docs]. В `openskill`: PlackettLuce — модель по умолчанию, ничьи через равные ранги.
- Приближение: разложить ранжирование на парные результаты между командами и подгонять BT как **композитное правдоподобие**. Плюс: одна машинерия, агрегируемые счётчики. Минус: переоценка информации (пары внутри одного матча зависимы). Исправляется bootstrap-ом **по матчам**, а не по парам. [вывод]
- Выбывание (elimination): порядок выбывания — естественный ранг; если несколько мест выбыли одновременно — равные ранги.
- 1 vs N: «N» — команда из одного игрока каждая; PL работает без изменений.

### 1.6 Асимметричные роли

Варианты:

| Вариант | Суть | Когда |
|---|---|---|
| Рейтинг на `(агент, роль)` | `P(хищник a бьёт жертву b) = σ(r^pred_a − r^prey_b + c)`; шкалы ролей связаны только константой c | агент играет несколько ролей, их навыки разные |
| Общая сила + смещение роли | `σ(r_a − r_b + c_role)` | роли почти симметричны (сторона в настольной игре) |
| Отдельная подгонка на каждую раскладку | независимые рейтинги по `layout` | уже так в текущем ELO; безопасно, но данные не разделяются между раскладками |

Рекомендация [вывод]: ключ подгонки — `(layout)`, внутри — параметр `(сущность, роль)`. Сквозной «общий» рейтинг агента, нужный для отбора, — это взвешенная сумма по ролям и раскладкам с весами, заданными владельцем (как в самом соревновании). Рейтинги разных ролей напрямую не сравнивать: у жертвы и хищника шкалы связаны лишь через общую константу.

### 1.7 Скриптовые «якоря» и привязка шкалы между запусками

- Шкала рейтинга определена с точностью до сдвига. Практика: зафиксировать якорь. OpenAI Five: случайная игра = TrueSkill 0 [источник: arXiv 1912.06680, App. J]. AlphaStar: встроенный бот Elite = Elo 0 [источник: Nature 2019, Methods, Extended Data].
- OpenAI Five держал **фиксированный пул из 83 эталонных агентов** (0…254) и обновлял только рейтинг тестируемого агента, считая эталоны константами [источник: там же]. Для нас это аналог «панели якорей»: скриптовые боты плюс «исторические чемпионы» прошлых запусков.
- Для привязки запусков: в каждом турнире участвует общая панель якорей; рейтинги других запусков сводятся подгонкой на объединённом журнале. Рейтинги, посчитанные в разных запусках без общих игр, сравнивать нельзя. [вывод]
- Риск: ботов, которые всегда проигрывают (Random), нельзя оценить бесконечно далеко: нужен приор (в `choix` параметр `alpha` — MAP при гауссовом приоре) [источник: choix docs, `opt_*`].

### 2.2 Когда что правильно

| Задача | Онлайн (инкрементальный) | Batch (пересчёт по журналу) |
|---|---|---|
| Индикатор прогресса в дашборде во время обучения | **да**: мгновенно, дёшево | не обязательно |
| Матчмейкинг (PFSP-таблицы) | EMA win rate — уже есть, достаточно | — |
| Решение «какие снапшоты хранить» | приближённо ok | **лучше**: точные CI, нет зависимости от порядка |
| Выбор финального бота | **нет** | **да**, плюс свежие игры |
| Сравнение запусков / архитектур | нет | да |
| Нестационарность | единственный способ отслеживать «latest» | не нужно, если сущности — неизменные снапшоты |

Вывод [вывод]: если сущность — зафиксированный снапшот, нестационарность исчезает, и онлайн-фильтры (Elo, Glicko, TrueSkill) теряют главное преимущество (отслеживание дрейфа). Остаётся стационарная задача логистической регрессии.

### 2.3 Стоимость batch-подгонки на 10^5–10^6 матчей [вывод]

- Достаточные статистики BT: матрицы `W_ij` (победы, дробные при ничьих) и `N_ij` (игры). Число матчей не входит в стоимость итерации: она `O(nnz(N))`, где nnz ≤ n². При 1000 сущностях и разреженной матрице — миллисекунды–секунды на MM-итерацию.
- Для команд и FFA агрегирование по парам невозможно: стоимость `O(число матчей × размер матча)` на итерацию. Для 10^6 матчей с 4–8 участниками — единицы секунд на итерацию Ньютона/L-BFGS на `scipy.sparse`. Достаточно пересчитывать раз в минуты или по запросу CLI.
- Bootstrap на сжатых счётчиках: для каждой ячейки `W_ij ~ Binomial(N_ij, Ŵ_ij/N_ij)` (параметрический) или мультиномиально по `(W, D, L)`. Если игры коррелируют (одинаковое зерно), нужен кластерный bootstrap по зёрнам/запускам. 100–200 реплик с warm start по 3–10 итераций — секунды–минуты.
- **Инкрементальная подгонка без порядковой зависимости**: хранить счётчики, раз в T секунд делать несколько шагов Ньютона/MM с warm start от прошлого решения. Результат — «онлайн-рейтинг», не зависящий от порядка матчей. Это заменяет онлайн-Elo без новой модели.
- Затухание по времени: для стационарных снапшотов не нужно. Если всё же использовать «latest» как сущность, взвешивать матчи экспоненциально по возрасту (`w = 0.5^{age/halflife}` — тот же приём, что EMA в PFSP).

### 2.4 Смещение от PFSP при онлайн-сборе [вывод]

- Условно на историю выбор оппонента не смещает MLE (правдоподобие факторизуется), но смещает **агрегаты**, например «средний win rate» и маргинальный EMA. BT-подгонка корректна, пока модель верна (транзитивность!). При циклах результат зависит от того, с кем PFSP заставляет играть.
- Поэтому для итогового выбора нужен **контролируемый дизайн** (турнир по фиксированному расписанию), а не только журнал обучения.
- Атрибуция матча версии: веса на воркере обновляются по таймеру, значит один эпизод может начаться с версии v и закончиться с v+k. В журнале хранить `policy_version` на начале и конце эпизода; для рейтинга использовать версию начала (или корзину — см. §3).

## 3. Рейтинги снапшотов

**Проблема**: сотни снапшотов на агента, у каждого мало игр, соседние снапшоты почти идентичны.

### 3.1 Варианты

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| Независимые сущности | каждый снапшот — свой параметр | просто | большой шум; гладкую динамику не использует |
| Инициализация от родителя | как OpenAI Five: новый μ = финальный μ предыдущего агента [источник: App. J] | ускоряет сходимость | в batch-подгонке эквивалентно приору |
| **Случайное блуждание (гладкость)** | приор `r_t ~ N(r_{t−1}, τ²)`; MAP = штраф `λ Σ (r_t − r_{t−1})²`, `λ = 1/(2τ²)` | усиление информации от соседей; shrinkage; тот же логистический решатель | выбор τ; сглаживает настоящие скачки (например, после смены гиперпараметра) |
| Корзины версий | игры «latest» приписываются корзине размером в `checkpoint.interval` | достаточно игр на корзину | корзина — смесь соседних политик |
| TrueSkill Through Time / динамические модели | гладкая траектория навыка на всём журнале | теоретически чище | сложнее; ссылки — [память] (Dangauthier et al., 2007) |

### 3.2 Рекомендация и мотивация

- Сущность = снапшот `(agent_id, policy_version)`; игры «latest» (не сохранённого) приписываются корзине между соседними сохранёнными версиями [вывод].
- Приор: гауссов по уровню (сильный: нулевое среднее, σ_prior ~ широкий для якорей) плюс штраф гладкости по цепочке версий одного агента. Штраф — мягкий, чтобы реальные скачки читались; ширина τ выбирается кросс-валидацией на журнале (по log-loss предсказаний исходов). [вывод]
- Неопределённость: интервал bootstrap либо диагональ обратного гессиана (`SE ≈ 1/√(Σ N_ij p̂_ij(1−p̂_ij))`, приближение для BT) [вывод].
- Масштаб чисел [вывод/расчёт]: при `n` играх на пару с p ≈ 0.5, SE логита ≈ `2/√n`; для n = 1000 это ≈ 0.063 логита ≈ 11 Elo (одна пара без учёта информации от других).

### 3.3 Интранзитивность среди снапшотов

- Внутри одной линии обычно доминирует транзитивность (новее — сильнее), но возможны циклы: поздняя версия «забыла» защиту от старой стратегии. AlphaStar: Nash лиги почти не даёт веса старым игрокам, то есть циклы и регрессия минимальны при лиге с PFSP [источник: Nature 2019, Extended Data]. Для нас это оптимистичный ориентир, но не гарантия.
- Диагностика [вывод]:
  1. Сравнить log-loss BT с «насыщенной» моделью (эмпирические доли по парам) на отложенных играх. Большой разрыв — признак нетранзитивности.
  2. Вычислить циклическую компоненту матрицы `A_ij = logit(P_ij)`: `rot(A) = A − grad(div A)` по Balduzzi [источник]; её норма относительно нормы A — «степень циклов».
  3. Для отчёта использовать **минимальный win rate против поля** и RPP/Nash-вес, а не только BT.
- mElo (Balduzzi) нужна только если диагностика показала циклы; лучше не включать в ядро. [вывод]
- Эффект клонов [источник: Balduzzi: инфляция рейтинга копиями побеждаемого]: метрики «среднее по полю» взвешивать **по линиям (агентам), а не по числу снапшотов**; иначе много слабых версий одного агента искажают и рейтинг, и средний win rate. [вывод]

## 4. Выбор лучшего с заданной уверенностью

### 4.1 Объём выборки [замер/расчёт]

Для проверки `p` против 0.5 (двусторонний тест 5 %, мощность 80 %): `n = ((z_{α/2}√(p0q0) + z_β√(p1q1)) / (p1−p0))²`.

| Истинный win rate | Игр (без ничьих) |
|---|---|
| 0.65 | 85 |
| 0.60 | 194 |
| 0.55 | 783 |
| 0.52 | **4 903** |
| 0.51 | 19 620 |

Ширина 95 % интервала (±h) для p ≈ 0.5: h = 0.05 — 384 игры; h = 0.02 — 2 401; h = 0.01 — 9 604.
Ничьи сокращают нужное число игр пропорционально снижению дисперсии счёта (см. §1.3), но не уменьшают смещение к 0.5.

Ориентир AlphaGo Zero: порог 55 % на 400 партиях [память]. Это примерно 2 SE от 0.5 (SE = 0.025), то есть решение о допуске, а не мощный тест.

Вывод: различить 52 % и 50 % напрямую стоит ~5 000 игр. Для хранения и дашборда такая точность не нужна; для финального выбора между двумя финалистами — ещё допустимо, если игра быстрая.

### 4.2 Парные дизайны [вывод]

- **Обмен сторонами / зеркальные зёрна**: каждое зерно играется в обеих расстановках; снимает преимущество карты и стороны. Дисперсия разности падает как `1−ρ`, где ρ — корреляция результатов в парной игре.
- **Общие случайные числа**: кандидаты A и B играют против одного и того же оппонента на одинаковых зёрнах; для игр на счёт (solo, кооператив) — парный t-тест / парный bootstrap на разностях счёта по зёрнам.
- Для 1 vs N / FFA: ротация мест (`schedule_lineups` уже делает per-layout ротацию) — аналог обмена сторонами.
- Игры на счёт (solo): рейтинги не нужны; сравнивать средний счёт на общем наборе зёрен с парным CI.

### 4.3 Доверительные интервалы и «вероятность быть лучшим»

- **Bootstrap по BT** (§2.3): для каждой реплики подгонка → `rank` каждой сущности. «P(best)» = доля реплик, где сущность первая; «P(в топ-k)» аналогично. Это то, что в parked-пункте названо «paired, rating-based selection with bootstrap». [источник: Chatbot Arena, bootstrap и sandwich-интервалы практически совпадают на их данных; arXiv 2403.04132 App.]
- Альтернатива — апостериорная выборка из гауссова приближения `N(r̂, H^{-1})`: быстрее, менее надёжна при малом числе игр. [вывод]
- Множественные сравнения: «чей интервал не пересекается с лучшим» — консервативно; лучше смотреть `P(best)` и доверительное множество (все, кого нельзя исключить). Замечено в публикации «The Leaderboard Illusion»: при пересечении интервалов нельзя решить, кто лучше [источник: arXiv 2504.20879, вторичное].

### 4.4 Проклятие победителя

Максимум из многих шумных оценок завышен. Моя симуляция [замер, `sim.py`]: K кандидатов с истинным win rate против якоря ~ N(0.5, 0.02), по n игр каждый, выбираем максимум оценки:

| K | n | Смещение оценки лучшего (оценка − истина) | Потери выбора (истинный лучший − выбранный) |
|---|---|---|---|
| 20 | 200 | +5.7 п.п. | 1.9 п.п. |
| 50 | 200 | +6.8 п.п. | 2.3 п.п. |
| 50 | 1000 | +2.2 п.п. | 0.95 п.п. |
| 200 | 200 | +8.4 п.п. | 2.8 п.п. |

(Весь разброс истинных сил — SD 2 п.п.: оценка лучшего завышена в 3–4 раза сильнее самого разброса.)

Две вещи отсюда:
1. Заявлять win rate выбранного бота по тем же играм, по которым его выбрали, нельзя. Нужны **свежие игры** выбранного (hold-out).
2. Сами потери выбора уменьшаются двухэтапной схемой: K=50, 200 игр на каждого, затем топ-5 + по 1000 свежих игр (всего 15 000 игр) — потери 1.3 п.п. против 2.3 п.п. у одноэтапной с 10 000 игр [замер].

### 4.5 Racing, successive halving, best-arm identification

- **Successive halving** (Karnin, Koren, Somekh, ICML 2013 — Sequential Halving) [источник]: в каждом раунде равный бюджет на выживших, отбрасывается нижняя половина, повтор. Без параметров, фиксированный бюджет.
- [замер] При одинаковом бюджете 15 000 игр на 50 кандидатах (SD сил 2 п.п.): successive halving — потери 0.9 п.п.; равномерно по 300 игр на каждого — 1.9 п.п. (в 2 раза хуже). Предупреждение: в симуляции скаляр — win rate против одного якоря, без циклов и корреляций.
- **Dueling bandits** (сравнения пар вместо скаляра): RUCB (Zoghi et al. 2014) требует наличия Condorcet-победителя — при циклах поведение непредсказуемо; Copeland-алгоритмы (Zoghi 2015, Komiyama 2016) работают и без него; Borda-победитель (максимум среднего win rate против поля) всегда существует; все три определены в [источник: Komiyama et al. 2016 / arXiv 1605.01677]. Для практики [вывод]: **выберите скаляр заранее** (чаще всего Borda = средний win rate против целевого поля) — тогда это обычный best-arm identification, и дуэльная машинерия не нужна. Copeland, RUCB и подобные — избыточно для SP4.
- **Расписания турниров**:

| Схема | Игр | Когда |
|---|---|---|
| Круговой (round-robin) | O(n²) | ≤ ~10–15 финалистов |
| **Gauntlet** против панели якорей | O(n·|якоря|) | много кандидатов; шкала привязана к якорям; именно так оценивал OpenAI Five |
| Swiss | O(n log n) | много кандидатов, нужен только порядок; адаптивный дизайн, годится для BT-подгонки |
| Successive halving по gauntlet-у | адаптивно | первичный отбор из сотен снапшотов |

Что используют практики: OpenAI Five — gauntlet против фиксированного пула с подбором близких по силе (адаптивно) [источник]; AlphaStar — round-robin лиги + Nash [источник]; Chatbot Arena — случайные пары + BT и bootstrap [источник]; AlphaGo Zero — порог на серии между чекпоинтами [память].

### 4.6 «Лучший» относительно чего

Скаляр для отбора задаётся владельцем и должен быть явным:

| Критерий | Формула | Когда подходит |
|---|---|---|
| Ожидаемый результат против целевого поля | `Σ_j w_j P(i бьёт j)` | известно распределение соперников (рейтинговая лестница) |
| Худший случай (minimax) | `min_j P(i бьёт j)` | нужна робастность к эксплуатации |
| Против равновесия Нэша | `Σ_j Nash_j P(i бьёт j)` (RPP в AlphaStar) | игра с циклами |
| BT-рейтинг | `r_i` | транзитивная игра; быстро |

Практическое замечание [вывод]: на конкурсе противники — незнакомые боты других участников, поэтому разумный дефолт — **смесь**: поле из якорей (скрипты + замороженные чемпионы разных линий), вес по линиям поровну; отчёт показывает среднее, минимум и BT-рейтинг рядом. Минимум по многим оппонентам тоже страдает проклятием победителя (минимум зашумлён вниз) — считать на свежих играх и с поправкой на множественность.

## 5. Хранение топ-k снапшотов по рейтингу

### 5.1 Цели

PFSP-пулу нужны не «k сильнейших», а набор, закрывающий разные стратегии и эпохи. Вывод из AlphaStar: Nash лиги сдвигается на новых игроков, но старые нужны как защита от забывания (минимальный win rate против прошлых версий — отдельная метрика в их абляциях) [источник: Nature 2019, Extended Data]. Простое «top-k по рейтингу» вытеснит ранние, слабые, но полезные для устойчивости версии.

### 5.2 Предлагаемая политика (минимальная) [вывод]

Порядок защиты, от жёсткого к мягкому:
1. Неприкосновенны: `final`, `keep_last` окно, `keep_every` (покрытие эпох) — как сейчас.
2. **Top-k по нижней границе** (`LCB = r̂ − z·SE`, z ≈ 1–1.5): сильные версии. LCB защищает от того, чтобы «выиграть» путём шума на малом числе игр; новые снапшоты с малым числом игр получают срок на «прогрев» (grace) и не вытесняются до накопления игр.
3. **Разнообразие**: при почти равных рейтингах (доверительные интервалы пересекаются) оставлять тех, чьи векторы результатов против панели якорей (вектор win rate по якорям) различаются сильнее; жадный выбор k-medoids / farthest-point по этому вектору. Тогда дубликаты отсеиваются, а версии с иной стратегией выживают.
4. «Единственный лучший против кого-то»: версия, которая лучшая против хотя бы одного оппонента из панели или имеет вес в Nash лиги, не вытесняется (аналог поддержки Nash в PSRO) [вывод].
5. Вытеснять по наименьшему «маргинальному вкладу»: наименьший LCB среди тех, кто не защищён пунктами 1, 3, 4.

Ограничения: решение о вытеснении принимает фоновый процесс по batch-рейтингу; удаление необратимо, поэтому правило — не удалять версию, у которой меньше N игр.

### 5.3 Чего не делать

- Не полагаться только на онлайн-Elo для вытеснения (зависит от порядка, нет неопределённости).
- Не считать снапшоты независимыми для поля «среднее по пулу» — клоны (§3.3).

## 6. Рекомендация для SP4

### 6.1 Архитектура

1. **Match log** (JSONL / компактный бинарный формат): для каждого эпизода — layout, команды и состав (агент, `policy_version` на старте и конце, роль), outcome (`wdl` / `rank` / `score`), очки, ничья, зерно среды, источник (`train` / `tournament`), флаг «контролируемый дизайн», метка времени. Все остальное — функции журнала.
2. **Модуль рейтингов** (чистая функция от журнала, без зависимости от обучения):
   - Модель: логистическая регрессия (BT) со знаковой матрицей включений и гауссовым приором; команды — сумма сил; FFA — парное разложение (композитное правдоподобие) для основной подгонки + опциональный точный PL; ничьи — счёт 0.5 по умолчанию, Davidson как опция; роли — параметр `(сущность, роль)` в рамках раскладки.
   - Сглаживание по цепочке версий агента (штраф гладкости).
   - Привязка шкалы: якорь (`RandomBot` = 0), панель общих якорей между запусками.
   - Bootstrap по матчам или зёрнам: CI, `P(best)`, `P(топ-k)`.
   - Диагностика интранзитивности: log-loss BT против насыщенной модели; доля циклической компоненты.
3. **Онлайн-индикатор**: хранить счётчики, раз в T секунд делать несколько шагов с warm start (не зависит от порядка). Текущий online team-pair ELO сохранить для PFSP и совместимости, но не считать источником истины.
4. **`colosseum tournament`**: контролируемый дизайн (расписание из `schedule_lineups` уже есть), режимы `gauntlet` против панели якорей, `round-robin`, `halving` (successive halving по gauntlet-у) и `swiss`; пишет в тот же match log с флагом дизайна; отчёт тот же.
5. **Отбор лучшего** (двухэтапный, по умолчанию):
   - Этап A (фильтр): BT-рейтинг по всему журналу, кандидаты — топ-N по LCB плюс разнообразие.
   - Этап B (подтверждение): свежие игры только для кандидатов против поля, заданного владельцем (якоря + замороженные чемпионы, поровну по линиям), парный дизайн, обмен сторонами.
   - Отчёт: win rate против поля с 95 % CI, **минимум по оппонентам**, BT-рейтинг с CI, `P(best)`, число игр. Оценка на этапе B не использует игры этапа A.
6. **Top-k хранение**: §5.2.

|---|---|---|
| Проклятие победителя | максимум из шумных оценок завышен (§4.4, замер) | свежие игры на выбранного; двухэтапная схема |
| Инфляция рейтинга клонами | Balduzzi et al. 2018 [источник]; у нас сотни снапшотов одной линии | веса по линиям, Nash averaging как проверка |
| Нетранзитивные циклы | Elo бессмыслен в циклических играх [источник] | диагностика log-loss; минимум по полю; RPP |
| Бесконечные оценки у «всегда проигрывающих» | MLE BT не существует при полной сепарации | приор (`alpha` в `choix`) |
| Несвязный граф игр | рейтинги разных компонент несравнимы | панель общих якорей; Swiss / gauntlet гарантируют связность |
| Ничьи в крестиках-ноликах | почти все игры сильных агентов — ничьи | Davidson или счёт 0.5; сообщать долю ничьих; информативны только редкие поражения |
| Смещённая выборка оппонентов (PFSP) | онлайн-метрики смещены | тот же BT-fit корректен при верной модели; для финала — контролируемый дизайн |
| Версия весов на воркере меняется в ходе эпизода | асинхронная синхронизация весов | логировать версию на старте и конце эпизода; корзины |
| Коррелированные игры (одно зерно, стороны) | занижает SE | кластерный bootstrap по зёрнам |
| Смена окружения / версии игры | OpenAI Five: метрика завышается для агентов, обученных на текущей версии [источник: App. J] | фиксировать версию в журнале; не смешивать версии в одной подгонке |
| Шкала TrueSkill у OpenAI Five | заявлено «8.3 пункта ≈ 80 % побед» при σ=25/3, β=σ/2; я не смог воспроизвести это по стандартной формуле `Φ(Δ/(√2 β))` (получается ≈ 92 %) | не копировать эту калибровку без проверки; шкалу калибровать по своим данным [вывод] |
