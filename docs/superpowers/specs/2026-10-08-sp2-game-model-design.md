Второй из шести подпроектов (см. «Roadmap» в CLAUDE.md). SP1 дал корректное одномашинное обучение на старом API `BaseEnv`. SP2 заменяет модель игры целиком: **обратной совместимости нет**, всё наследие (`BaseEnv`, плоский float32-кодек действий, `info["active"]`, `info["action_mask"]`, `terminal_observation`, три параллельные карты мест) удаляется, примеры и тесты переводятся на новый контракт.

## 1. Цель

Фреймворк одинаково хорошо обучает игры любой структуры, и каждая структура доказана обучением end-to-end на демо-среде:

- **соло** (счёт);
- **1v1** пошаговая и с одновременными ходами;
- **один бот управляет многими юнитами** (переменное число, разные типы юнитов, Dict-наблюдения, списки сущностей);
- **команда на команду**, где каждое место — отдельный экземпляр бота;
- **FFA на любое число игроков** с выбыванием, в том числе **разное число игроков в разных партиях одной игры** (2p и 4p в одном запуске);
- **1 vs N и асимметричные роли** (разные пространства наблюдений и действий у ролей);
- **кооператив**: одна команда без соперников;
- любые смеси: много команд разного размера (2v1v1), команды из ролей с разными пространствами.

Попутно:
- bootstrap переезжает на лёрнер (свежая сеть вместо устаревшей сети воркера);
- появляется централизованный критик (`global_state` только для value);
- матчмейкинг, рейтинги и eval начинают понимать команды, роли и варианты партий.

## 2. Вне рамок

| Что | Куда |

| Скриптовые, замороженные и внешние игроки; PFSP по снимкам (в том числе по чекпоинтам соперника в асимметричных играх); warm start на агента (`init`, прогрев критика); хранение снимков с top-k. BC и kickstart в SP2 только переводятся на новые форматы | SP3 |

| Векторный быстрый путь для сред на массивах и для сотен мест (Neural MMO), GPU-инференс на воркерах, быстрый unroll | SP6 |
| PettingZoo-адаптер | позже, по необходимости |

**Не планируются вовсе** (решения брейншторма, раздел 8):
- один агент на роли с *разными* пространствами (многоролевая сеть);
- награда, value и рекуррентное состояние на юнит;
- встроенная авторегрессия между компонентами действия (возможна через пользовательский `Distribution`);
- серии матчей как сущность фреймворка (best-of-N живёт внутри среды, как в Lux S3);
- MCTS-контроллеры, каналы связи между ботами;
- каноническая перспектива и аугментации (ответственность среды).

**Распределённый режим** (`serve-weight-store`, `run-learner`, `run-workers`) переводится на новый формат чанков и контракт среды в прежнем объёме (self-play на latest), без новых возможностей.

## 3. Критерии готовности

1. **Тесты.** Полный быстрый набор (`pytest -m "not gpu and not slow"`) зелёный, 0 предупреждений; `ruff check .` чистый. Соглашения SP1 соблюдены: файлы только в `tmp_path`, ≤2 воркер-процесса, процессы через `tests/cli_runner.py`.
2. **Контрактные тесты** (раздел 6) зелёные, в том числе: лёрнер воспроизводит совместные и per-unit log-prob воркера при нулевом лаге для четырёх ядер на чанках с `boot`, `pad`, обрывом и выбыванием; V-trace с `boot`-шагами совпадает с эталоном; ни одна награда не теряется (кроме мест, ни разу не ходивших в эпизоде, — они считаются в счётчике).
3. **Тесты «учится».** Быстрые на каждом прогоне: бандит с `Units`, кооперативный бандит. Медленные (`slow`, бюджет примерно ≤3 мин каждый на 8 ядрах). Соперник-эталон живёт в тесте как `PolicyModel` («случайный легальный игрок») и играет через in-process eval-API с явными составами (блоки 5, 8). Составы: `tron` 4p — обученный агент на одном месте против трёх случайных; `coop_buttons` — два обучаемых агента с `teammates: mixed`, порог — для однородной команды каждого агента.

   | Тип игры | Среда | Порог |
   |---|---|---|
   | Соло | `coin_grid` | средний счёт ≥ 2× случайной политики |
   | 1v1 пошаговая | `tic_tac_toe` | ≥80% побед против случайного легального игрока (greedy) |
   | Бот с юнитами, одновременные ходы | `unit_harvest` | ≥80% побед против случайного |
   | Команда на команду | `team_tag` | команда ≥80% против случайной команды |
   | FFA с выбыванием, 2–4 игрока | `tron` | 2p: ≥80% побед; 4p: доля первых мест ≥50% против трёх случайных |
   | Асимметрия 1 vs N | `predator_prey` | каждый агент в своей роли бьёт случайного соперника ≥70% |
   | Кооператив | `coop_buttons` | счёт команды ≥ порога, заданного в плане по замеру случайной политики; отчёт cross-play формируется |

   Пороги стартовые. Если какой-то недостижим за бюджет, он меняется как ruling с замерами, а не молча.
4. **Эксперимент по юнитам.** На `unit_harvest` при K=8 и K=128 сравниваются `ratio_mode` (`joint`/`per_unit`) и `unit_trace` (`joint`/`geo_mean`/`none`) на одном бюджете: win-rate, `clip_frac`, ESS. Результат — в `docs/benchmarks.md`, дефолт `unit_trace` фиксируется как ruling.
5. **Скорость.** Throughput на `tic_tac_toe` (тот же `scripts/bench_throughput.py`) не хуже SP1 более чем на 10%; масштабирование 1→2→4 воркера монотонно.
6. **Эталонные примеры** `space_miners`, `chase` (`composite_action`) переписаны под новый контракт; `validate` и короткий smoke-`train` проходят. Порогов обучения у них нет.
7. **Документация.** `docs/ENV_GUIDE.md` объясняет, как писать среду для каждого типа игры, с примерами; README и статус в CLAUDE.md описывают реальное состояние.
8. **Распределённый режим** работает на новом формате в прежнем объёме; его тесты зелёные.
9. **GPU.** Новые CUDA-пути помечены `gpu` и перечислены в `docs/GPU_CHECKS.md`.
10. **Остатки SP1** (блок 0) закрыты первыми коммитами.

## 4. Принципы

- **Один контракт, без легаси.** Всё, что не нужно новому контракту, удаляется, а не обёртывается.
- **Общий случай без частных веток.** Соло, FFA, команды, кооператив и асимметрия — это один алгоритм над «вариант партии = список команд из мест с ролями». В коде нет `if num_players == 2`.
- **Ошибки контракта громкие.** Нарушение контракта среды — `EnvContractError` с контекстом «воркер, среда, место, шаг эпизода»; ошибка конфига — `ConfigError` с подсказкой. Молчаливых фолбэков нет, кроме описанных в этом документе (исход из наград при отсутствии `Outcome`).
- **Решения SP1 в силе,** если этот документ явно их не меняет (список изменений — раздел 8). Перед правкой области SP1 проверяются rulings в `docs/superpowers/reports/2026-10-08-sp1-acceptance.md`.
- **Тесты вперёд.** Контрактные тесты пишутся до переписывания воркера и лёрнера.

### Блок 1. Контракт среды

Новый модуль `colosseum/envs/game.py` (точное размещение — в плане).

```python
@dataclass(frozen=True)
class RoleSpec:
    observation_space: gymnasium.Space          # блок 2: Box | Discrete | MultiBinary | MultiDiscrete | Dict
    action_space: gymnasium.Space               # блок 2: ... | Units
    global_state_space: gymnasium.Space | None = None   # для критика; None — роль его не даёт

@dataclass(frozen=True)
class SeatSpec:
    role: str
    team: int                                   # 0..T-1 внутри варианта

@dataclass(frozen=True)
class GameSpec:
    roles: dict[str, RoleSpec]
    layouts: dict[str, tuple[SeatSpec, ...]]    # вариант партии; места 0..n-1 заняты, n..P_max-1 пустые

    @property
    def max_seats(self) -> int: ...             # P_max = длина самого большого варианта
    def teams(self, layout: str) -> list[list[int]]: ...

    # хелперы, роль по умолчанию называется "player":
    @classmethod
    def solo(cls, obs, act, global_state=None) -> GameSpec: ...                 # вариант "solo"
    @classmethod
    def symmetric(cls, num_players: int | Iterable[int], obs, act, global_state=None) -> GameSpec: ...
                                                # FFA, команда = место; варианты "2p", "3p", ...
    @classmethod
    def teams_of(cls, sizes: Sequence[int] | Iterable[Sequence[int]], obs, act, global_state=None) -> GameSpec: ...
                                                # варианты "2v2", "3v3", "2v1v1"; [n] — кооператив "coop<n>"
```

**Тип исхода выводится из варианта**, отдельного поля нет (уточнение при написании spec, раздел 8):
- одна команда (соло, кооператив) → `score`;
- две команды → `wdl`;
- три и больше → `rank`.

Так одна игра может иметь и кооперативные, и соревновательные варианты.

**Проверки `GameSpec`** (при `validate` и при создании вектор-среды): роли вариантов существуют; номера команд варианта — ровно `0..T-1`; хотя бы один вариант; имена вариантов и ролей — безопасные идентификаторы.

```python
class MultiAgentEnv(ABC):
    spec: GameSpec                                       # атрибут класса или экземпляра
    @abstractmethod
    def reset(self, seed: int | None, layout: str) -> StepResult: ...
    @abstractmethod
    def step(self, actions: dict[int, Any]) -> StepResult: ...   # ключи — ровно места из acting
    def close(self) -> None: ...

@dataclass
class StepResult:
    acting: set[int]                       # кто ходит на СЛЕДУЮЩЕМ шаге
    obs: dict[int, Any]                    # обязательно для каждого ходящего места (дерево, блок 2)
    action_masks: dict[int, Any]           # только для ходящих; нет ключа — всё разрешено
    rewards: dict[int, float]              # любому живому месту; нет ключа — 0
    terminated: set[int]                   # места, выбывшие на этом шаге
    episode_over: bool = False
    truncated: bool = False                # оборван искусственным лимитом, а не по правилам
    final_obs: dict[int, Any] | None = None       # при truncated: каждому живому месту
    global_state: dict[int, Any] | None = None    # с перспективы места; см. ниже
    outcome: Outcome | None = None         # при episode_over
    infos: dict[int, dict] = field(default_factory=dict)

@dataclass
class Outcome:                             # всё на уровне команд варианта
    team_rank: dict[int, float] | None = None    # 1 — лучший; ничья — равные ранги; дробные допустимы
    team_score: dict[int, float] | None = None   # игровой счёт команды
```

**Жизненный цикл места** (места `0..n-1` варианта; `n..P_max-1` пустые):
- **Пустое.** Никогда не ходит. Награда, наблюдение или `terminated` для него — `EnvContractError`.
- **Живое.** Ходит (в `acting`) или ждёт. Награды копятся в открытом переходе места; до его первого хода в эпизоде — в `pending`, который уходит в первый переход (как в SP1).
- **Выбывшее** (`terminated` на этом шаге). Значит «return места окончателен». Награда в том же `StepResult` разрешена (типичный штраф за смерть) и применяется первой; затем последний переход места получает `terminal`. На *следующих* шагах место не может ходить, получать награды или снова выбыть — иначе `EnvContractError`.
- **Ждущие места и наблюдения.** Наблюдения не ходящим живым местам разрешены и игнорируются: модель места обновляет состояние только на своих ходах. Если игре нужна память о событиях между ходами (туман войны), среда кладёт историю в наблюдение — это правило есть в `docs/ENV_GUIDE.md`.
- **Мёртвый юнит или игрок в команде,** которому ещё положена командная награда в конце: среда его *не* терминирует, а исключает из `acting`. Он продолжает получать награды; `terminal` ставится в конце эпизода.

**Шаг без решений.** Пустой `acting` без `episode_over` допустим (тик, на котором никто не решает): воркер вызывает `step({})`. Больше `env.max_idle_steps` (по умолчанию 1000) таких шагов подряд — `EnvContractError` (защита от среды, забывшей `episode_over`).

**Конец эпизода:**
- `episode_over=True` → `acting` пуст. Все живые места завершаются. «Живое» здесь — не пустое и не выбывшее, включая `terminated` этого же шага: места из `terminated` получают `terminal`, а не `boot`, и `final_obs` им не нужен.
- **По правилам** (включая фиксированную длину матча, как 505 шагов в Lux S3): `truncated=False`, bootstrap 0.
- **Искусственный обрыв:** `truncated=True`, `final_obs` обязателен для каждого живого места; `global_state` (если роль его объявила) — финальное глобальное состояние для тех же мест. Лёрнер считает V по ним (блок 4).
- **`outcome`:** если `None` — счёт команды = **среднее** по её местам их наград за эпизод (среднее, а не сумма: иначе команды разного размера в 2v1v1 или 1 vs N сравнивались бы нечестно), ранги выводятся из счёта. Если есть только `team_score` — ранги выводятся из счёта (больше — лучше). Если есть только `team_rank` — счёт = то же среднее. Ключи — ровно команды варианта, иначе `EnvContractError`.

**`global_state`:** если роль объявила `global_state_space`, среда отдаёт его каждому ходящему месту этой роли на каждом шаге (и при `reset`), а также живым местам при `truncated`. Перспектива места — забота среды.

**`reset`** возвращает `StepResult` с `acting`, `obs`, `action_masks`, `global_state`; `rewards` и `terminated` пусты, `episode_over=False`.

**Проверки контракта** (`EnvContractError` с контекстом): ходящее место без наблюдения; выбывшее или пустое место в `acting`; награда пустому месту или месту, выбывшему на предыдущих шагах; `episode_over` с непустым `acting`; ключи `actions`-ответа не совпадают с `acting`; `layout` не из спеки; `Outcome` не по командам варианта; `final_obs` отсутствует у живого места при `truncated`; наблюдение или маска не соответствует пространству роли (проверяется дёшево: структура дерева и формы; полная проверка `space.contains` — только в `validate`).

**Вектор-среды** (`VectorEnv`, `SubprocessVectorEnv`) больше **не сбрасывают эпизоды сами**:
- `step(actions_per_env) -> list[StepResult]`, где для закончившейся среды возвращается её финальный `StepResult`;
- `reset(env_index, seed, layout) -> StepResult` — сброс одной среды по команде воркера. `SubprocessVectorEnv` может пакетировать сбросы с ближайшим `step`, чтобы не тратить отдельный круг IPC на каждый конец эпизода.

### Блок 2. Наблюдения и действия

**Деревья.** `TensorTree = ndarray | Tensor | dict[str, TensorTree]`. Общие утилиты (`tree_map`, `tree_stack`, `tree_index`, `allocate(spec, leading_shape)`) живут в одном модуле и используются наблюдениями, действиями, масками, `global_state` и `State` модели (утилиты `networks/state.py` обобщаются).

**Наблюдения.** `observation_space` роли: `Box`, `Discrete`, `MultiBinary`, `MultiDiscrete` или вложенный `Dict` из них. `ObsSpec.from_space` даёт формы и типы листьев.
- **Тип данных сохраняется** по всему пути: среда → буфер → чанк → транспорт → батч лёрнера. `uint8` остаётся `uint8`; к float приводит энкодер.
- **Список сущностей — соглашение:** `Dict(entities=Box(N_max, F), entity_mask=MultiBinary(N_max))`.
- **`NormalizeObs`** знает путь своего листа в дереве; `update_normalizers` получает дерево.

**Действия — деревья с родными типами:** int64 для дискретных, float32 для `Box`. `action_space` роли: `Discrete`, `MultiDiscrete`, `Box` (1-D), `Units` или вложенный `Dict` из них. Плоский float32-кодек `ActionSpec`, лимит 2^24 и `CompositeDist` поверх плоского вектора удаляются; новый `ActionSpec` описывает дерево листьев.

**Пространство `Units(max_units, per_unit, only_if=None)`** (новый `gymnasium.Space`):
- `per_unit`: `Discrete(A)`, `MultiDiscrete([A1..Ac])`, `Box(d,)` или `Dict` из них — упорядоченный список именованных компонентов юнита. Порядок компонентов `Dict` — порядок `space.spaces` (естественный порядок, как у `ActionSpec` SP1); от него зависит раскладка маски `action`. `gymnasium.spaces.Dict`, построенный из обычного `dict`, сортирует ключи — `docs/ENV_GUIDE.md` говорит об этом явно;
- **действие группы:** дерево массивов с ведущим измерением `[U]` (например, `int64[U, C]` для `MultiDiscrete`, `float32[U, d]` для `Box`);
- **цель-указатель** — компонент `Discrete(N_targets)` с маской по существующим целям;
- **разные типы юнитов в одном боте** — `Dict`: `{"factories": Units(10, Discrete(4)), "robots": Units(200, MultiDiscrete([5, 64])), "global": Discrete(3)}`;
- **GridNet** — частный случай `Units(H*W, ...)`: юнит = клетка;
- **`only_if={компонент: (родитель, {значения})}`** — компонент учитывается (log-prob, энтропия, KL, лосс), только если выбранное значение родителя входит в множество. Пример: цель `sap` учитывается, только если тип действия = sap. Родитель — дискретный компонент того же юнита. Гейт — по записанному действию (на воркере — по сэмплу). `only_if` есть только внутри `Units`; боту без юнитов с условной головой («тип + цель») подходит `Units(1, ...)`;
- **идентичность юнитов:** индекс слота назначает среда; фреймворк не связывает слоты между шагами.

**Маски — деревья, повторяющие дискретные части действия.** Нет листа — всё разрешено.
- `Discrete(n)` → `bool[n]`; `MultiDiscrete` → `bool[ΣA]`; `Box` — без маски.
- `Units` → `{"unit": bool[U], "action": bool[U, ΣA_дискретных]}`. `unit=False` — юнита нет или он не действует.
- **Правило пустой строки:**
  - не юнитовый дискретный лист: пустая строка у ходящего места — `EnvContractError` (как в SP1);
  - `Units`: пустая строка компонента у существующего юнита — этот (юнит, компонент) невалиден, без ошибки и без NaN; юнит без единого валидного компонента невалиден целиком.
- Единые правила мест и масок живут в одном модуле (наследник `core/seat_info.py`), его используют `MatchRunner` (блок 5) и `validate`.

**«Решающие» (deciders).** Действие места раскладывается на K решающих: каждый юнит каждой группы `Units` — один решающий; все не юнитовые листья вместе — ещё один (если есть). Для действия без `Units` K = 1.

**Протокол распределения** (`Distribution`):
- `sample() -> tree`, `mode() -> tree`;
- `log_prob(a) -> [B]` — совместный: сумма по валидным решающим;
- `unit_log_prob(a) -> [B, K]`, `unit_entropy(a) -> [B, K]`, `unit_valid(a) -> [B, K]`, `unit_kl(other, a) -> [B, K]`. Действие передаётся везде, потому что из-за `only_if` валидность компонентов зависит от выбранного значения родителя: энтропия и KL дочернего компонента считаются только там, где записанное значение родителя входит в множество;
- `apply_mask(mask_tree)`, `cat(dists)` (для `unroll`).

Невалидные позиции дают 0 через `torch.where`, а не умножение на маску (`0·NaN = NaN`).

**Встроенные распределения:** категориальное, мульти-категориальное, диагональная гауссиана, `UnitsDist` (компоненты юнитов с масками и `only_if`), дерево-композиция. Пользователь может вернуть свой `Distribution` (например, авторегрессионный), реализовав протокол.

**Хелперы голов:** голова юнитов (признаки `[B, U, F]` → параметры компонентов) и GridNet-перекладка (`[B, C, H, W]` → `[B, H*W, A]`).

### Блок 3. Протокол модели и критик

```python
class PolicyModel(nn.Module, ABC):
    def initial_state(self, batch_size, device="cpu") -> State: ...
    @abstractmethod
    def step(self, obs, state, action_mask=None) -> PolicyStep: ...          # (dist, state)
    @abstractmethod
    def unroll(self, obs, state0, reset_after, action_mask=None,
               global_state=None, with_value=True) -> UnrollOutput: ...     # (dist, value | None), time-major [S*B]
    def reset_state(self, state, done) -> State: ...
    def update_normalizers(self, obs_tree, global_state_tree=None) -> None: ...
```

- **`step`** — путь политики: воркер, eval, сабмит на соревнование. **Value воркер больше не считает и не хранит.**
- **`unroll`** — путь лёрнера: политика и value по последовательности слотов чанка; `reset_after[t]` — сброс состояния после слота t. Метод обязателен целиком, хелпера для монолитных моделей нет. `with_value=False` — value не нужен (BC, учитель kickstart): модель возвращает `value=None` и не требует `global_state`.
- Контракт: `unroll` даёт те же распределения политики, что последовательные `step`, с теми же сбросами (контрактный тест SP1 сохраняется для log-prob).

**`ComposedModel(encoder, core, policy, value, critic_encoder=None)`:**
- `encoder(obs_tree)` → `Tensor [B, D]` или `EncoderOutput(latent [B, D], aux: dict[str, Tensor])`. `aux` — признаки, которые идут мимо ядра прямо в голову политики: эмбеддинги юнитов `[B, U, E]`, пространственные карты для GridNet;
- `core` работает только с `latent`, как в SP1 (`NoCore`, `LSTMCore`, `GRUCore`, `WindowAttentionCore`);
- `policy(features, aux) -> Distribution`;
- `value(features ⊕ critic_encoder(global_state))` — если `critic_encoder` задан, value-голова видит признаки ядра и признаки глобального состояния; иначе только признаки ядра.

Конфиг: `networks.critic_encoder_class` (необязательный). Если он задан, а роль агента не объявляет `global_state_space`, — `ConfigError`.

Монолитные модели (`networks.model_class`) реализуют `step` и `unroll` сами.

### Блок 4. Траектории и чанк v2

**Слоты.** Чанк фиксированной длины S (`rollout.chunk_length`, S ≥ 2 — иначе `ConfigError`); все чанки одной формы и батчатся без паддинга. Каждый слот одного из видов:
- **`act`** — решение места: наблюдение, `global_state` (если роль объявила), маска, действие, совместный log-prob поведения и (при K > 1) per-unit log-prob, накопленная награда, флаг `terminal`;
- **`boot`** — только наблюдение и `global_state`; нужен лёрнеру для V bootstrap. Действия и лосса нет;
- **`pad`** — заполнитель, ни на что не влияет.

**Содержимое не-`act` слотов** выбирается так, чтобы прогон модели по ним не давал NaN:
- маска `boot` и `pad` — «всё разрешено» (для `Units` — `unit=False`), действие — нули;
- `pad` копирует наблюдение и `global_state` предыдущего слота, а не нули (нулевой `entity_mask` в пользовательском attention-энкодере дал бы NaN);
- на лёрнере V-trace, лоссы и метрики выбирают слоты через `torch.where` по виду слота, а не умножением на маску (`0·NaN = NaN`).

**Правила записи** (поверх механики SP1: открытые переходы, `pending`, буферы агентов с парковкой):
1. `act` никогда не пишется в последний слот, поэтому за открытым переходом всегда есть место для его `boot`.
2. **Место ходит:**
   - есть открытый переход и свободен ровно один слот → `boot` с текущим наблюдением и `global_state`, чанк запечатывается, новый `act` идёт в следующий буфер (это же наблюдение — его первый слот);
   - открытого перехода нет и свободен ровно один слот → `pad`, чанк запечатывается, `act` идёт в следующий буфер;
   - иначе → `act` в следующий слот (предыдущий переход места закрывается неявно).
3. **Место выбыло или эпизод закончился по правилам:** открытый переход получает `terminal`, `reset_after`.
4. **Эпизод оборван:** после открытого перехода пишется `boot(final_obs, final global_state)` с `reset_after`.
5. **Чанк запечатывается сразу, как только занят последний слот.** По правилу 1 это всегда `boot` или `pad`.

**«Следующий буфер» на границе чанка** — это тот же буфер места после запечатывания и сброса (как `seal → reset` в SP1), **никогда не припаркованный**: последний слот припаркованного буфера сбрасывает состояние, и продолжение эпизода с ненулевым состоянием модели в нём разошлось бы с воркером.

**Парковка (SP1)** сохраняется: паркуется только буфер, последний слот которого заканчивает эпизод (`terminal`-`act` или `boot` с `reset_after`). Взять буфер из пула (сначала припаркованный) можно только когда место начинает собирать для агента на границе эпизода — то есть при начальном состоянии модели.

**Формат `TrajectoryChunk` v2** (numpy-деревья через границы процессов, как в SP1):
- `agent_id`, `policy_version` (версия на первом слоте), `initial_state` (состояние модели перед первым слотом, листья `[1, ...]`). Роли в чанке нет: роли одного агента имеют одинаковые пространства, и чанк может содержать эпизоды разных ролей;
- деревья `[S, ...]` с родными типами: `obs`, `global_state` (или `None`), `actions`, `action_masks` (или `None`);
- плоские: `kind[S]` (`act`/`boot`/`pad`), `reward[S]`, `terminal[S]`, `reset_after[S]`, `behavior_logp[S]`;
- `behavior_unit_logp[S, K]` — только при K > 1.

Поля `values` и `bootstrap_value` удаляются. Сериализация (`to_payload`/`from_payload`, gRPC `transport/serialization.py`) работает с деревьями.

**Счёт данных.** `consumed_samples` и `recorded_transitions` считают `act`-слоты. Бюджет `training.total_timesteps` и прогресс LR по-прежнему считают шаги сред (как в SP1). В распределённом режиме прогресс лёрнера остаётся `consumed_samples / total_timesteps` и теперь смешивает решения с шагами сред — это задокументировано; единая семантика — SP5.

### Блок 5. Воркер и `MatchRunner`

**`MatchRunner` — общее ядро матча** для обучения и eval (переносит в SP2 часть пункта SP4 «унификация eval»):
- держит вектор-среду, сетку мест `[E, P_max]`, текущий `Lineup` каждой среды, состояния моделей мест;
- проверяет контракт (блок 1) и маски (блок 2);
- группирует инференс ходящих мест по паре (агент, сеть) и вызывает `act` (только политика);
- при конце эпизода собирает `MatchResult`, применяет ожидающий `Lineup` и сбрасывает среду с его вариантом и следующим сидом;
- отдаёт события наблюдателю: ход места (наблюдение, маска, `global_state`, действие, log-prob, состояние до шага), награды, выбывание места, конец эпизода (обрыв, `final_obs`, финальный `global_state`, `MatchResult`).

`RolloutLoop` — наблюдатель, пишущий буферы (блок 4) для собирающих мест. Eval — наблюдатель, копящий записи матчей. Точный API событий — в плане.

**Пул моделей передаёт вызывающий:** `MatchRunner` получает отображение (агент, сеть) → экземпляр `PolicyModel` и явные `Lineup`. Поэтому в процессе (eval-API, тесты) за место может играть любой `PolicyModel`, в том числе «случайный легальный игрок» из тестов «учится» — без скриптовых игроков SP3.

**Состав матча.** Три параллельные карты SP1 (`slot_agent_map`, `slot_network_map`, `collect_mask`), `PlayerSlot` и `MatchConfig` заменяются:
```python
@dataclass
class SeatAssignment:
    agent_id: str
    network_id: str          # "latest" | "ckpt_v<N>"
    collect: bool

@dataclass
class Lineup:
    layout: str
    seats: list[SeatAssignment]      # длина = размер варианта
```
Стартовые `Lineup` (по одному на среду, их генерирует координатор) лаунчер передаёт воркеру при запуске, как стартовые карты в SP1. `WorkerCommand` несёт `lineups: list[Lineup | None]` (по одному на среду воркера, `None` — без изменений) и `new_checkpoints`. Новый состав применяется в конце эпизода среды, как в SP1. Отсутствующая сеть заменяется на latest с `collect=True` (правило SP1).

**Роли и агенты.**
- `agents.<id>.roles: [...]` — роли агента. Можно не писать, если у всех ролей игры одинаковые пространства (тогда агент играет все роли).
- У ролей одного агента должны совпадать пространства наблюдений, действий и `global_state` — иначе `ConfigError` с подсказкой «разделите на агентов».
- Сеть агента строится по пространствам его роли; пул буферов — по агенту (формы его роли).
- Сети в одной группе инференса по построению имеют одинаковые пространства.

**Наблюдения** хранятся деревом на место, а не общим массивом `[E, P, ...]`; батч собирается в группе инференса.

**Результат матча:**
```python
SeatResult(seat, role, team, agent_id, network_id, reward, eliminated_step: int | None)
TeamResult(team, rank, score)
MatchResult(match_id, layout, outcome_kind, seats: list[SeatResult], teams: list[TeamResult], episode_length)
```

**Метрики эпизодов** (`metrics.jsonl`, WandB `episodes/...`): длина, return на место, счёт команды, доля выбываний — с разбивкой по варианту и роли. Остальная наблюдаемость SP1 сохраняется и получает разбивку по варианту: W/D/L по типу соперника (latest / past / arena) из `EpisodeAggregator`, консольный прогресс по агентам, записи `ratings` в `metrics.jsonl`.

### Блок 6. Алгоритм (APPO)

**Батч.** Чанки складываются в `[S, B, ...]` по каждому листу дерева. Каждое обновление использует ровно `learner.batch_chunks` чанков (правило SP1).

**V-trace по слотам** (обобщение `algorithms/vtrace.py`):
- значения `V` считаются сетью лёрнера на всех слотах (`unroll`);
- на не-`act` слотах ρ = c = 0, награда 0, `vs = V`; поэтому трасса обрывается на `boot` сама;
- для `act` в слоте t следующее значение — `V` слота t+1 (это `act` того же эпизода или его `boot`); для `terminal` — 0. `pad` следует только за `terminal` или концом эпизода и не участвует;
- скалярный ρ_t для V-trace задаёт `unit_trace` (ниже);
- `gamma` — на решение места, как в SP1.

**Все лоссы и диагностики редуцируются только по `act`-слотам:** policy, value, энтропия, KL kickstart, нормировка advantage (mean/std), `clip_frac`, `approx_kl`, `explained_variance`, `rho_mean` и прочие. `boot` и `pad` в средние не входят.

**Скалярный ρ для V-trace** (`algorithm.unit_trace: auto | joint | geo_mean | none`) — входит только в V-trace (таргеты `vs` и обрезка трассы):
- `joint` — exp(сумма log-ratio по валидным решающим);
- `geo_mean` — exp(среднее log-ratio по валидным решающим);
- `none` — ρ = c = 1 (TD(λ) без коррекции, как value в AlphaStar);
- `auto` = `joint` без `Units`; с `Units` — `geo_mean` до эксперимента критерия 4, после — дефолт по его итогам (ruling).

**Политика** (`algorithm.ratio_mode: auto | joint | per_unit`, `auto` = `per_unit` при наличии `Units`, иначе `joint`). Advantage шага: `A_t = r_t + γ·vs_{t+1} − V(x_t)`.
- `joint` — как в SP1: PPO-clip на совместном ratio, advantage умножается на обрезанный скалярный ρ_t;
- `per_unit` — ratio и clip на каждого решающего с общим `A_t` **без** множителя ρ_t: off-policy-коррекцию политики даёт сам per-unit ratio, а совместный ρ при K=128 подавил бы градиент. Лосс шага = среднее по валидным решающим; затем среднее по `act`-слотам (каждый шаг весит одинаково независимо от числа юнитов; взвешивание шагов числом юнитов у практиков работало плохо, `research/sp2_per_unit_ppo.md` §1.2).

Так эксперимент критерия 4 разделяет два эффекта: `ratio_mode` меняет policy loss, `unit_trace` — только value-таргеты.

**Редукция энтропии и KL по решающим** (`algorithm.entropy_reduction: auto | mean_valid | sum`; `auto` = `sum` при `joint`, `mean_valid` при `per_unit`):

| `ratio_mode` | policy loss шага | энтропия и KL kickstart шага (`auto`) |
|---|---|---|
| `joint` | совместный log-ratio (сумма по решающим) | сумма по валидным решающим |
| `per_unit` | среднее по валидным решающим | среднее по валидным решающим |

Явное `entropy_reduction` меняет только правый столбец. При K = 1 все режимы дают один и тот же результат.

**Value-лосс** — на `act`-слотах. **Нормализаторы** обновляются один раз на шаг обучения по `act`-слотам и `boot`-слотам с `reset_after` (`boot` на конце чанка не берётся: его наблюдение — первый `act` следующего чанка).

**Диагностика** (добавляется к метрикам SP1): `clip_frac` по решающим и совместный; `approx_kl` (среднее по решающим); среднее и p95 `|log ρ|` по решающим и совместного; ESS скалярного ρ; доля клипа ρ и c; среднее и максимум числа валидных решающих; доли `boot` и `pad` слотов.

**Kickstart** — KL по решающим (`unit_kl`) с редукцией из таблицы, только по `act`-слотам; учитель прогоняется `unroll(..., with_value=False)`. Учитель в SP2 остаётся глобальным (`training.kickstart_teacher`, как в SP1): `validate` требует, чтобы сигнатура пространств учителя совпадала с ролями каждого агента, иначе `ConfigError`. Учитель на агента — SP3.

**Offline BC** — `colosseum bc` получает `--agent A`: сеть и роли берутся из конфига этого агента (по умолчанию — единственный агент). Формат данных: `.pt` с деревьями `observations`, `actions`, необязательными `action_masks` и `dones`. Лосс — минус log-prob: совместный при K = 1, при K > 1 — среднее по валидным решающим. Модель прогоняется с `with_value=False`. Остальное поведение BC (окна для моделей с состоянием, нормализаторы) — как в SP1.

### Блок 7. Матчмейкинг и рейтинги

**Владелец данных** ротируется по всем обучаемым агентам, как в SP1. Для каждой среды:
1. **Вариант партии** — по `matchmaking.layouts` (веса). По умолчанию равномерно; всегда только среди вариантов, где у владельца есть место его роли.
2. **Тип матча** — один раз на матч: self-play (вероятность `self_play_ratio`) или arena. Без соперничающих команд тип не важен. `matchmaking.mode: self_play` означает `self_play_ratio = 1` (arena не бывает); `league` — смесь. `training.phase` удаляется: матчмейкер теперь выбирает `matchmaking.mode`.
3. **Команда владельца** — случайная среди команд с местом его роли.
4. **Заполнение команд.** У каждой команды есть «ядро»:
   - у команды владельца — владелец;
   - у каждой другой команды независимо: при self-play — latest владельца (вероятность `latest_prob`) или его случайный чекпоинт, если владелец играет хотя бы одну роль этой команды; иначе (arena, или владелец не играет ни одной роли команды) — агент, выбранный PFSP среди *других* обучаемых агентов, играющих хотя бы одну роль команды (win-rate этого варианта; `f(wr) = (1 − wr)^p`, как в SP1); если таких нет — как при self-play. Выбор делается **один раз на команду**. Поэтому асимметричная игра работает и при `mode: self_play`: команду, роли которой владелец не играет, получает другой агент.
   - **Остальные места команды** (`matchmaking.teammates`):
     - `self` — ядро на всех местах, роль которых оно играет;
     - `mixed` — каждое такое место с вероятностью `teammate_self_prob` достаётся ядру, иначе равномерно одному из кандидатов: latest другого обучаемого агента с этой ролью или чекпоинт ядра.
   - **Место с ролью, которую ядро не играет,** получает latest обучаемого агента, который её играет (равномерно среди таких, владелец тоже кандидат), с `collect=True`.
5. **Сбор.** Собирают все места с latest обучаемых агентов; места с чекпоинтами не собирают.
6. **Перестановка мест** (`matchmaking.shuffle_seats`): команды переставляются только с командами того же состава ролей, внутри команды — места одной роли.

**Проверки конфига** (`validate`): каждая роль каждого включённого варианта играется хотя бы одним агентом; каждому агенту доступен хотя бы один вариант; веса `layouts` ссылаются на существующие варианты.

**Рейтинги — свои таблицы на каждый вариант партии:**
- **≥2 команд:** ELO по парам команд. Каждая пара команд A, B даёт одно сравнение по рангам; его вес `K / (T − 1)` делится поровну между учитываемыми парами участников (a ∈ A, b ∈ B). Сокомандники друг с другом не сравниваются. Сущность рейтинга — (агент, сеть), как в SP1; пары одинаковых сущностей пропускаются и в делитель не входят. Win-rate-матрица (дробная) и `wr_vs_past` (последние 500 пар latest против прошлого себя) строятся из тех же пар участников разных команд, как в SP1.
- **Одна команда (соло, кооператив):** `ScoreTracker` — средний счёт, EMA и 95% CI по агенту; при `teammates: mixed` — матрица cross-play «счёт по составу команды» (мультимножество агентов команды → средний счёт).
- **Асимметрия:** общий ELO плюс win-rate в разрезе ролей.
- `ratings.json`: `{<layout>: {elo, win_rates, wr_vs_past, scores, cross_play}}`; WandB: `ratings/<layout>/...`.

**Конфиг** (раздел `self_play` удаляется):
```yaml
matchmaking:
  mode: league                  # self_play | league
  layouts: {2p: 0.5, 4p: 0.5}   # по умолчанию — все варианты поровну
  self_play_ratio: 0.5
  pfsp_exponent: 1.0
  latest_prob: 0.5
  teammates: self               # self | mixed
  teammate_self_prob: 0.5
  shuffle_seats: true
checkpoint:
  interval: 1000                # было self_play.checkpoint_interval
  pool_size: 20                 # было self_play.pool_size
  save_optimizer: true
agents:
  hunter: {roles: [hunter]}
  prey:   {roles: [prey]}
```

### Блок 8. Eval

- **Ядро** — `MatchRunner` (блок 5); семантика мест, масок и состояний та же, что в обучении.
- **CLI:** `colosseum eval -c cfg.yaml -a A=<ckpt-dir|.pt> [-a B=...] [--layout L ...] --num-matches N [--output r.json] [--deterministic] [--seed S]`. Архитектура и роли агента — из `meta.json` чекпоинта; для `.pt` — из конфига агента с тем же именем, а если такого нет — из глобального `networks` с ролями «все роли игры» (тогда у них должны совпадать пространства). По умолчанию — все варианты, где агентам есть места.
- **In-process API** принимает явные экземпляры `PolicyModel` и явные `Lineup` (через `MatchRunner`, блок 5). Им пользуются тесты «учится» (случайный легальный игрок — это `PolicyModel`) и будущий `tournament` (SP4).
- **Составы (CLI):**
  - ≥2 команд, ≥2 агентов: для каждой пары агентов (a, b) матч m отдаёт команду i ядру `(a, b)[(i + m) % 2]` там, где роли это позволяют; команды заполняются однородно; места — по ролям. Асимметричная пара (охотник и жертва) не ротируется. `--num-matches` — на пару и вариант;
  - ≥2 команд, один агент: все команды — этот агент (соло-режим SP1: средний return и исход по местам);
  - одна команда: каждый агент в однородной команде (`--num-matches` на агента и вариант); при ≥2 агентах и размере команды ≥2 — также смешанные составы для cross-play (`--num-matches` на состав).
- **Отчёт по вариантам:**
  - `wdl`: W/D/L, win-rate и счёт с ничьими как половиной, 95% интервалы Уилсона (как в SP1), разбивка по сторонам;
  - `rank`: средний ранг ± CI, доля первых мест, попарная матрица «кто выше»;
  - `score`: средний счёт ± 95% CI; cross-play-таблица.

  Всё дополнительно разбито по ролям. JSON-вывод сохраняется.

### Блок 9. Конфиг, `validate`, чекпоинты

- **Конфиг:** `env.num_players` удаляется (структура — из `GameSpec`); `env.max_idle_steps` (блок 1); раздел `matchmaking` вместо `self_play`; `training.phase` удаляется; `checkpoint.interval`, `checkpoint.pool_size`; `agents.<id>.roles`; `algorithm.ratio_mode`, `algorithm.unit_trace`, `algorithm.entropy_reduction`; `networks.critic_encoder_class`; `rollout.chunk_length ≥ 2`. `extra="forbid"`, правила id агентов и `--set` из SP1 сохраняются. `scripts/bench_throughput.py::_make_config` обновляется (правило SP1).
- **`validate`:**
  - проверки `GameSpec` (блок 1) и конфига (блоки 5, 7);
  - `reset` каждого включённого варианта, несколько шагов случайными легальными действиями с проверкой контракта и `space.contains`;
  - модель каждого агента: `step` на наблюдениях его роли и `unroll` на синтетическом чанке с `boot`/`pad` и `global_state`.
- **`meta.json` чекпоинта** дополнительно хранит роли агента и сигнатуру их пространств. Resume и eval сверяют сигнатуру; несовпадение — `ConfigError`, указывающий путь. Чекпоинты SP1 несовместимы, и это нормально.

### Блок 10. Демо-среды, примеры, документация, замеры

- **Демо-среды** (`examples/`, чистый numpy, маленькие и быстрые):
  - `coin_grid` — соло, Dict-наблюдения (`uint8`-карта + вектор), искусственный лимит шагов (`truncated`);
  - `tic_tac_toe` — переписан под контракт;
  - `unit_harvest` — две стороны, база (`Discrete`) + рабочие `Units(U_max, ...)`, юниты рождаются и гибнут, список сущностей с маской; `U_max` задаётся параметром (для эксперимента K=8/K=128);
  - `team_tag` — 2v2, локальное окно обзора, `global_state` = вся карта;
  - `tron` — FFA с выбыванием, ранг по порядку выбывания, варианты 2p/3p/4p;
  - `predator_prey` — 1 охотник против 2 жертв, роли с разными пространствами, два агента;
  - `coop_buttons` — кооператив из двух мест.
- **Эталонные примеры:** `space_miners` переписывается как «нормальная соревновательная игра» на новых возможностях — корабли как `Units` (непрерывное ускорение — `Box`-компонент юнита, толчки — дискретные), астероиды списком сущностей с маской, Dict-наблюдения. `chase` (`composite_action`) переписывается под деревья действий. Только `validate` и smoke-`train`.
- **Документация:** `docs/ENV_GUIDE.md` (как писать среду для каждого типа игры, ссылки на демо-среды), README, статус в CLAUDE.md, `docs/GPU_CHECKS.md`.
- **Замеры:** `docs/benchmarks.md` — throughput до и после на той же машине и команде (критерий 5); эксперимент по юнитам (критерий 4).
- **Распределённый режим:** `run-learner`/`run-workers` на чанке v2 и `Lineup`, сериализация деревьев в gRPC (чанк идёт байтовым блобом, `.proto` не меняется). Объём прежний — self-play на latest без координатора: поддерживаются игры, где один агент играет все роли; вариант партии выбирается по `matchmaking.layouts`, все места — latest этого агента. Остальное — `ConfigError` со ссылкой на SP5.

## 7. Порядок работ и процесс

| Часть | Блоки | Что |
|---|---|---|
| P0 | 0 | остатки SP1 |
| P1 | 1, 2 (пространства и деревья) | контракт среды, `GameSpec`, `Units`, деревья, `ObsSpec`/`ActionSpec` v2, маски, вектор-среды со сбросом по команде; удаление `BaseEnv` |
| P2 | 2 (распределения), 3 | распределения и протокол решающих, хелперы голов, протокол модели `step`/`unroll`, `EncoderOutput`, `critic_encoder` |
| P3 | 4, 5 | `MatchRunner`, `RolloutLoop` поверх него, буферы `act`/`boot`/`pad`, чанк v2 и сериализация, `Lineup`, результаты и метрики эпизодов |
| P4 | 6 | V-trace по слотам, режимы юнитов, диагностика, kickstart и BC на новых форматах |
| P5 | 7 | матчмейкинг, рейтинги по вариантам, `ScoreTracker`, cross-play, координатор и лаунчер |
| P6 | 8, 9 | eval на `MatchRunner`, конфиг, `validate`, `meta.json` |
| P7 | 10 | демо-среды и тесты «учится», эталонные примеры, эксперимент по юнитам, бенчмарк, распределённый режим, документация |
| — | — | приёмка по разделу 3, отчёт в `docs/superpowers/reports/`, merge после явного одобрения владельца |

**Набор тестов зелёный после каждой задачи.** Новые модули строятся рядом со старыми; старый путь удаляется в той задаче, где его полностью заменяет новый, и в той же задаче тесты старого поведения переводятся на новый контракт или удаляются. Как разрезать переключение воркера, лёрнера и лаунчера, чтобы набор не краснел, решает план.

**Процесс** (как в SP1, с распределением моделей, заданным владельцем для SP2):
- одна задача плана — один субагент на Opus с high effort: сначала падающие тесты, затем реализация, коммит;
- после каждой задачи — ревью соответствия spec и качества субагентом на Opus с high effort; раунды исправлений с повторным ревью по месту;
- в конце — ревью всей ветки (Opus, high) с одной волной исправлений, затем приёмка;
- поиск в интернете и обзоры, если понадобятся, — субагентами на Sonnet с high effort;
- решения за владельца записываются как rulings («что — почему — цена ошибки»); ветка регулярно пушится в `origin`; merge в `main` — только после явного одобрения отчёта.

## 8. Решения и риски

**Решения брейншторма:**

| Решение | Почему | Цена ошибки |
|---|---|---|
| Приёмка — все типы игр end-to-end; минимум матчмейкинга, рейтингов и eval с командами, ролями и вариантами входит в SP2 | без этого команды и асимметрию нельзя полноценно обучать до SP3 | больший объём SP2 |
| Роль — тип места со своими пространствами; агент играет роли с одинаковыми пространствами; асимметрия — разными агентами; многоролевой агент с разными пространствами не строится | в реальных играх роли с общим пространством кодируются во входе (OpenAI Five, Diplomacy), а с разными — отдельными сетями (AlphaStar, DouZero); разные типы юнитов в одном боте решает `Units` в `Dict` | если такой агент понадобится — новая механика (роль в протоколе модели, смешанные батчи) |
| Команды: по умолчанию однородные, `teammates: mixed` — опция | однородные — стандарт (Pommerman, TiKick); смешанные дают устойчивость к чужим партнёрам и cross-play в кооперативе | — |
| Централизованный критик в SP2, вместе с переносом bootstrap на лёрнер | критично для командных игр (hide-and-seek, MAPPO, baseline победителя Lux S3); перенос bootstrap всё равно меняет протокол модели | память и трафик чанков при больших `global_state` (поле необязательное) |
| Разное число игроков в партиях одной игры через пустые места; вариант выбирает матчмейкер | Orbit Wars (Kaggle 2026): одна сеть на 2p и 4p; переиспользует механику выбывания | — |
| Контракт — свой (`GameSpec` + `MultiAgentEnv`), а не PettingZoo и не массивы | PZ не даёт списка ходящих, исходов и стандарта масок; массивный контракт тяжёл авторам сред и пошаговым играм | готовые PZ-среды нужен адаптер |
| Обратной совместимости нет, легаси удаляется | указание владельца | — |
| Существующие примеры — эталоны сред без порогов обучения | указание владельца | — |

**Уточнения при написании spec** (по сравнению с секциями, показанными в брейншторме):
1. Поле `GameSpec.outcome` убрано: тип исхода выводится из числа команд варианта (1 → `score`, 2 → `wdl`, ≥3 → `rank`). Так одна игра может иметь кооперативные и соревновательные варианты.
2. `Outcome` — на уровне команд (`team_rank`, `team_score`), а не мест: в FFA и соло команда = место.
3. `reset(seed, layout)` без `options`: передавать их пока некому (YAGNI).
4. `per_unit`: лосс шага — среднее по валидным решающим, затем среднее по шагам (шаги весят одинаково).
5. `per_unit` в `Units` поддерживает `Box` и `Dict` компонентов (непрерывное ускорение в `space_miners`, угол в Orbit Wars).

**Уточнения после ревью spec** (ревьюер-субагент на Opus сверил spec с кодом и прошёл правила слотов на конкретных последовательностях):
6. На границе чанка эпизод продолжается в сброшенном буфере места, никогда в припаркованном (иначе расходится состояние LSTM).
7. Маски `boot`/`pad` — «всё разрешено», `pad` копирует предыдущее наблюдение, выбор слотов на лёрнере — через `torch.where` (защита от NaN).
8. Все лоссы и метрики — только по `act`-слотам.
9. `per_unit` не умножает advantage на скалярный ρ; `unit_trace` влияет только на value-таргеты. `entropy_reduction: auto` (сумма при `joint`, среднее при `per_unit`).
10. Награда в шаге выбывания разрешена; шаг без решений допустим с защитой `env.max_idle_steps`; наблюдения ждущих мест игнорируются.
11. Исход по умолчанию — среднее наград по местам команды, а не сумма.
12. `unroll(..., with_value=False)` для BC и учителя kickstart; хелпера для монолитных моделей нет.
13. `training.phase` удалён, `matchmaking.mode: self_play` = `self_play_ratio = 1`.
14. Eval: in-process API с явными `PolicyModel` и `Lineup`; правила для `.pt`, одного агента и кооператива.
15. Kickstart остаётся глобальным с проверкой сигнатуры; `colosseum bc --agent`.
16. Распределённый режим — только игры, где один агент играет все роли.

**Изменения правил SP1:**
- `info["active"]`, `info["action_mask"]`, `terminal_observation` → поля `StepResult`;
- truncation-bootstrap на воркере (`γ·V(final_obs)` в награду) → `boot`-слот и V сети лёрнера;
- воркер не считает value; контракт «лёрнер воспроизводит log-prob и value воркера» → только log-prob;
- `self_play.*` → `matchmaking.*` и `checkpoint.*`; `env.num_players` и `training.phase` удалены;
- `PlayerSlot`, `MatchConfig`, карты мест → `SeatAssignment`, `Lineup`;
- рейтинги — по вариантам партии и по парам команд.

**Риски:**

| Риск | Смягчение |
|---|---|
| Дефолт `unit_trace` при сотнях юнитов — прецедента нет | эксперимент критерия 4; запасной вариант — `joint` |
| Деревья и dict на место в Python замедлят воркер | критерий 5 (≤10%); если не укладываемся — горячие пути на заранее выделенные массивы по роли |
| Пороги обучения `team_tag`, `predator_prey`, `coop_buttons` могут не достигаться за бюджет | подстройка размеров сред; изменение порога — ruling с замерами |
| Объём SP2 больше SP1 | части P0–P7, ревью после каждой задачи |
| Регрессии гарантий SP1 (жизненный цикл, resume, чекпоинты) | тесты SP1, переведённые на новый контракт, остаются регрессионной сеткой |
| Размер `global_state` | поле необязательное; замер на `team_tag` в `docs/benchmarks.md` |
