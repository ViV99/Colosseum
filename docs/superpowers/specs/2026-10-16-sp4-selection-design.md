Четвёртый из шести подпроектов (см. «Roadmap» в CLAUDE.md), идёт параллельно с SP5. SP3 дал арену: обучаемые, замороженные и скриптовые игроки в одной лиге, PFSP по снимкам, якоря. Но выбрать из неё лучшего бота надёжно нельзя:
- онлайн-ELO считается по агентам (снимок засчитывается своему агенту), без неопределённости, зависит от порядка партий;
- результаты матчей живут только в памяти (10 000 последних) и при переполнении очереди теряются молча;
- eval сравнивает только пары агентов в одном процессе, без общей сводки и без отбора;
- снимки хранятся только по версии;
- мониторинг — консоль, `metrics.jsonl` и WandB.

SP4 вводит журнал матчей как источник правды, рейтинги снимков с доверительными интервалами, турнир с контролируемым дизайном и двухэтапным отбором, хранение снимков по рейтингу с ограничением диска, оценку снимков во время обучения, HTML-отчёт и живой дашборд. **Конфиги, чекпоинты и папки запусков SP3 продолжают работать.**

## 1. Цель

Финальный этап соревнования работает от начала до конца:

1. **Журнал.** Каждый матч обучения, турнира и оценки во время обучения попадает в журнал запуска (`runs/<name>/matches.db`). Размер журнала ограничен по построению: старые обучающие матчи сжимаются в счётчики, а свободное место на диске охраняется.
2. **Рейтинги.** Рейтинги снимков (Bradley–Terry с доверительными интервалами) считаются из журнала. Живой рейтинг виден по ходу обучения. По желанию отдельный процесс прогоняет каждый новый снимок через фиксированное поле соперников (несмещённая оценка во время обучения).
3. **Турнир и отбор.** `colosseum tournament` сравнивает кандидатов — снимки запусков, замороженные чекпоинты любой архитектуры и скриптовых ботов — по контролируемому дизайну (общие seed, ротация мест). Он выбирает лучшего в два этапа: отбор, затем подтверждение на свежих seed. Итог — отчёт с интервалами и числом игр.
4. **Хранение.** Снимки хранятся не только по версии: top-k по нижней границе рейтинга, закреплённые и потолок общего числа снимков.
5. **Наблюдаемость.** `colosseum report` собирает самодостаточный HTML-отчёт, а `colosseum dashboard` показывает то же вживую. В обоих есть:
   - рейтинги во времени и матрица результатов;
   - результаты против якорей и фактическая смесь соперников;
   - здоровье обучения;
   - матчи;
   - итоги турниров.

Попутно — отложенные пункты метрик:
- срезанная масса весов V-trace вместо `rho_clip_frac` / `c_clip_frac` (ответ владельца на Q2);
- монотонный `dropped_reward_episodes`;
- сжатая таблица PFSP в записях `ratings`;
- рейтинги и статистика лиги переживают resume;
- финальные снимки не раздувают пул при частых resume.

## 3. Критерии готовности

1. **Тесты.** Полный быстрый набор (`pytest -m "not gpu and not slow"`) зелёный, 0 предупреждений; `ruff check .` чистый. Соглашения SP1–SP3 соблюдены: файлы только в `tmp_path`, ≤ 2 воркер-процесса, процессы через `tests/cli_runner.py`.
2. **Контрактные тесты** (раздел 6) зелёные. В том числе:
   - каждый матч обучения попадает в журнал ровно один раз либо учтён в `dropped_match_results`, с версиями весов мест в начале и конце эпизода; потеря результата никогда не молчаливая (счётчик + WARNING);
   - сжатие журнала не меняет рейтинги (до и после сжатия совпадают в пределах допуска); размер журнала остаётся в пределах окна; при нехватке места журнал переходит на счётчики, обучение продолжается;
   - Bradley–Terry восстанавливает силы синтетических игроков (1v1 со стороной, команды, FFA, ничьи, асимметричные роли с мостом и без): истинные разности с якорем внутри группы ролей и компоненты (в той же шкале) попадают в 95 % интервалы с частотой не ниже номинальной за вычетом допуска; синтетика с ≥ 200 сравнениями на сущность, приор и гладкость — значения модуля; отдельные тесты — оценка не уходит на бесконечность при малом числе игр, а для асимметричных ролей без моста межгрупповые сравнения не выводятся;
   - хранение снимков: top-k по нижней границе, закреплённые, потолок `max_snapshots`, защита новых снимков до набора игр, `keep_last` / `keep_every` / финальный — по правилам блока 4;
   - турнир: у всех кандидатов одни и те же seed, места ротируются поровну; этап подтверждения не использует seed отбора;
   - оценка во время обучения: процесс получает каждый новый снимок, его матчи попадают в журнал с источником `pulse`, процесс живёт и умирает вместе с запуском;
   - resume из папки запуска продолжает журнал, рейтинги и статистику PFSP.
3. **Лесенка ботов (главный критерий отбора).** Набор скриптовых ботов известной силы (один бот с разной долей случайных ходов) на двух демо-играх: 1v1 и FFA или командной. `colosseum tournament --mode select` ставит их в истинном порядке и выбирает сильнейшего, BT-интервалы соседей не противоречат порядку. Число игр и допуски замеряются в плане и фиксируются как rulings.
4. **Конвейер (slow).** На демо-игре: `train` с оценкой во время обучения (`evaluation.every` для этого теста — ruling плана) → рейтинг снимков растёт по версиям (тренд положительный, порог — ruling плана) → `tournament --mode select` по снимкам запуска с полем из якорей выбирает снимок, подтверждённый на свежих seed, и он выигрывает у `RandomBot` не меньше порога медленных тестов SP3. HTML-отчёт этого запуска собирается.
5. **Диск.** Длинный прогон на `tic_tac_toe` (больше окна журнала): `matches.db` не превышает окно + запас (ruling плана), счётчики полны (рейтинги по журналу совпадают с рейтингами, посчитанными по полной таблице сравнений в памяти — тестовый режим журнала без удаления), число снимков не превышает `max_snapshots`.
6. **Скорость.** Throughput на `tic_tac_toe` (`scripts/bench_throughput.py`, журнал включён, оценка во время обучения выключена) не хуже `main` (SP3 + GPU-правки), замеренного в тех же условиях на той же машине, более чем на 5 % при 1 / 2 / 4 воркерах. Если часы машины скачут (WSL2, отчёт GPU-проверок), замер идёт по счётчикам, а не по окнам `ts`.
7. **Отчёт и дашборд.**
   - `colosseum report` собирает HTML для запусков демо-игр всех видов исхода (`wdl`, `rank`, `score`); файл открывается без сети, все разделы на месте (тест по данным и разметке).
   - `colosseum dashboard` отдаёт ту же страницу и данные вживую.
   - Владелец смотрит отчёт с телефона при приёмке.
8. **Совместимость с SP3.** Конфиги `configs/examples/` проходят `validate` без правок. Папка запуска SP3 (без `matches.db`) возобновляется. Чекпоинты SP3 играют в турнире как снимки и как frozen-агенты.
9. **Распределённый режим.** Тесты SP2/SP3 зелёные. Новые настройки SP4 в распределённых командах дают `ConfigError` с указанием на SP5, кроме тех, что работают локально в каждом процессе.
10. **Документация:**
    - новый `docs/ARENA_GUIDE.md` (рус.): журнал, рейтинги, турнир и рецепт выбора сабмита, хранение, оценка во время обучения, отчёт и дашборд;
    - README и статус в CLAUDE.md описывают реальное состояние;
    - список метрик обновлён.
11. **Slow-набор** зелёный целиком (тесты SP2/SP3 и новые).

## 4. Принципы

- **Журнал — источник правды.** Рейтинги, матрицы и отчёты — функции журнала. Онлайн-ELO SP2 остаётся индикатором прогресса без изменений. Отбор и хранение опираются на Bradley–Terry с интервалами.
- **Отбор — контролируемый эксперимент.** Обучающие партии смещены (соперников выбирает PFSP, latest меняется), поэтому итоговое решение принимается по турниру с заранее заданным полем и общими seed. Выбранного подтверждают на свежих seed (проклятие победителя).
- **Диск ограничен по построению.** У каждого растущего хранилища есть предел и поведение при его достижении:
  - журнал: окно подробных записей + счётчики;
  - снимки: `max_snapshots`;
  - защита свободного места.

  Обучение из-за этого не падает.
- **Без новых обязательных зависимостей.** Только stdlib (`sqlite3`, `http.server`) и numpy. Отчёт и дашборд без CDN, работают офлайн.
- **Удобный конфиг.**
  - Минимальный конфиг не растёт.
  - Дефолты: журнал включён, top-k и оценка во время обучения выключены, дашборд — отдельная команда.
  - `validate` показывает итоговые настройки, ошибки — `ConfigError` с подсказкой.
- **Границы с SP5.**
  - Журнал, рейтинги и турнирное расписание — библиотеки без привязки к очередям процессов: на входе записи матчей, на выходе таблицы.
  - Схему записи матча задаёт SP4, транспорт — SP5.
- **Порядок — по счётчикам, не по часам.** `env_steps`, номер записи и версия упорядочивают данные. Метки времени только информационные (часы WSL2 скачут, отчёт GPU-проверок).
- **Ошибки громкие** (как в SP2/SP3): молчаливых фолбэков нет, кроме описанных здесь и унаследованных.
- **Решения SP1–SP3 в силе,** если этот документ явно их не меняет (список — раздел 8). Перед правкой области проверяются rulings в отчётах приёмки SP1, SP2 и SP3.
- **Тесты вперёд:** контрактные тесты пишутся до переделки потока результатов и хранения снимков.

## 5. Дизайн по блокам

### Блок 1. Журнал матчей

**Запись матча.** `MatchResult` и `SeatResult` получают новые поля. У всех есть значения по умолчанию, поэтому старый код и тесты, создающие их напрямую, работают.

- `MatchResult`:
  - `uid` — глобально уникальный ключ: id запуска, источник, воркер, среда, номер эпизода. Нынешний `match_id` уникален только внутри запуска.
  - `source`: `train` | `tournament` | `pulse`.
  - `seed` — seed эпизода, если он задан.
  - `env_steps` — глобальный счётчик шагов в момент приёма результата (главный процесс, позже хаб SP5); у pulse — `env_steps` снимка из `meta.json`, у турнира — `None`.
  - `block` — блок дизайна турнира (общий seed и ротации мест), у обучающих матчей `None`.
- `SeatResult`:
  - `version_start`, `version_end` — версия весов места в начале и в конце эпизода. Для latest это версия агента на воркере (веса меняются по таймеру и посреди эпизода тоже), для снимка `ckpt_v<N>` это `N`, для скриптового и замороженного `None`.
  - `rating_version` — версия, которой засчитывается партия (блок 2).

`MatchRunner` получает необязательную функцию «текущая версия агента»; `RolloutLoop` передаёт свои `policy_versions`. Eval и турнир берут версии из id сетей.

**Хранилище.** `runs/<name>/matches.db` — SQLite (stdlib):
- режим WAL: отчёт, дашборд и турнир читают, пока обучение пишет;
- `auto_vacuum = INCREMENTAL`: освобождённое место возвращается на диск;
- `synchronous = NORMAL`, `journal_size_limit` и `wal_checkpoint(TRUNCATE)` после каждого прохода чистки; читатели не держат транзакции дольше одного запроса;
- писателей может быть два (обучение и турнир): `busy_timeout`, транзакции не дольше одной пачки, пачки чистки ≤ 10 000 матчей;
- агенты, сети, роли и источники хранятся числовыми id через таблицу `entities`; первичный ключ матча — целое число, `uid` — уникальный индекс.

| Таблица | Содержимое |
|---|---|
| `runs` | id запуска, имя, родитель (resume), игра, хэш конфига, `checkpoint.interval` (ширина корзины версий), время создания |
| `matches` | `uid`, запуск, источник, раскладка, вид исхода, длина, seed, `env_steps`, блок, воркер, время (информационно) |
| `seats` | матч, место, команда, роль, агент, сеть, вид игрока, `version_start`, `version_end`, `rating_version`, награда, шаг выбывания, категория соперника (`source` SP3) |
| `teams` | матч, команда, ранг, очки |
| `entities` | числовые id агентов, сетей, ролей и источников |
| `counts` | сжатые матчи по парам команд: раскладка, источник, команда A (номер, участники `агент@rating_version` с ролями), команда B (то же) → число матчей `n`, сумма весов `Σw` и сумма взвешенных исходов `Σw·y` (вес `1/(T−1)`, исход 1 / 0.5 / 0, как в блоке 2); для `score` — состав команды → число, сумма и сумма квадратов очков |
| `meta` | версия схемы |

Индексы создаются сразу: по агенту и версии, по матчу (без индекса по матчу соединения на миллионе матчей не завершаются, `research/sp4_selection_practice.md` §4.2).

**Запись.** Журнал — библиотека (`MatchLog`), её вызывает тот, кто принимает результаты: главный процесс обучения, команда `tournament`, позже хаб SP5.
- В главном процессе обучения запись и сжатие идут в отдельном потоке со своим соединением. Главный цикл только ставит пачку результатов в очередь потока.
- Одна транзакция на пачку.
- Очередь результатов от воркеров увеличивается (10 000). Её переполнение больше не молчит: воркер считает потерянные результаты, в записи `system` появляется монотонный `dropped_match_results`, при первой потере — WARNING.
- Очередь потока-писателя ограничена (100 000 результатов). При переполнении результат считается в `dropped_match_results` и даёт WARNING (как очередь воркеров); главный цикл не блокируется.
- При остановке писатель дописывает очередь, прерывает чистку между пачками и закрывает соединение в пределах `SHUTDOWN_GRACE_SEC`; недописанное считается в `dropped_match_results` и попадает в лог. При SIGKILL теряется очередь писателя (до 100 000 результатов).

**Своевременная чистка (решение владельца).**
1. **Турнир и оценка во время обучения** (`tournament`, `pulse`) хранятся подробно всегда. Их мало: тысячи–десятки тысяч, это мегабайты.
2. **Обучающие матчи хранятся подробно в окне.** Когда подробные обучающие матчи занимают больше `match_log.detail_window_mb` (по умолчанию 512 МБ ≈ 1 млн матчей; оценка по числу строк и среднему размеру; файл + WAL показываются в «Системе»), самые старые обучающие матчи пачками сворачиваются в `counts` и удаляются, затем выполняется `incremental_vacuum`.
   - `counts` — достаточная статистика для рейтингов блока 2 (точечная оценка и гессиан совпадают точно), поэтому рейтинги до и после сжатия совпадают. Bootstrap по `counts` — пуассоновские веса по строкам; корреляция пар внутри одного матча FFA при этом теряется, поэтому интервалы по сжатым обучающим партиям FFA приближённые.
   - Теряются только подробности старых матчей: seed, длина, награды мест.
   - Размер `counts` зависит от числа разных пар команд, а не от числа матчей и соперников в матче: для 1v1 — сущности × соперники × 2 стороны (порядка `корзины × соперники × 2`; 1 000 корзин × 100 соперников ≈ 200 тыс. строк ≈ 20 МБ). `counts` и подробные матчи турниров и pulse не сжимаются; их объём входит в размер файла, а число строк `counts` показывается в разделе «Система».
   - Части файла, которые чистка не трогает (`counts`, турниры, pulse), окно не уменьшают. Если они растут быстрее ожидаемого — WARNING один раз.
3. **Матчи вытесненного снимка** сворачиваются на ближайшем проходе чистки.
4. **Защита диска.** Если свободного места на диске журнала меньше `match_log.min_free_disk_mb` (по умолчанию 2048), новые обучающие матчи сразу идут в `counts`; при первом переходе — WARNING, в `system` — флаг. Когда место появляется, подробная запись возобновляется. Турнир при нехватке места пишет как обычно: его матчей мало.
5. **Обучение из-за журнала не падает:** ошибка записи — ERROR в лог и счётчик, кроме ошибок схемы при старте (`ConfigError`).

Ориентиры (замер в плане): крестики-нолики (~2 000 матчей/с) заполняют окно за десятки минут и дальше не растут; игра вроде Lux (~20 матчей/с) доходит до окна примерно за сутки.

**Resume из папки запуска.** Новый запуск создаёт свой `matches.db` с родителем в `runs` и импортирует из журнала исходного запуска `counts`, матчи турниров и pulse. Подробные обучающие матчи родителя при импорте сворачиваются в `counts` нового журнала; подробности остаются в журнале родителя, и отчёт ссылается на него по `runs.parent`. Каждый resume добавляет на диск только `counts` и турниры, а не окно. У папки запуска SP3 журнала нет: новый журнал начинается пустым, в логе INFO.

**Конфиг.**

```yaml
match_log:
  enabled: true            # false: только онлайн-ELO SP2; top-k и pulse требуют журнала (ConfigError)
  detail_window_mb: 512
  min_free_disk_mb: 2048
  compact_interval_sec: 60
```

Секции `match_log`, `ratings`, `evaluation` и новые ключи `checkpoint` — только глобальные; переопределений на агента в SP4 нет (агентов pulse выбирает `evaluation.agents`).

**API для чтения** (отчёт, дашборд, турнир, хаб SP5): матчи с фильтрами (агент, версия, раскладка, источник, исход, диапазон `env_steps`); сравнения для рейтинга — пары команд с исходами и числом из подробных матчей и `counts` вместе; открытие только для чтения.

### Блок 2. Рейтинги снимков (Bradley–Terry)

**Сущности.**
- **Обучаемый агент:** `агент@v<B>`, где `B` — `rating_version` места.
  - Снимок `ckpt_v<N>` засчитывается версии `N`.
  - Latest засчитывается корзине: `B = ⌊version_start / checkpoint.interval⌋ · checkpoint.interval`, то есть снимку, сохранённому в начале этого отрезка обучения (у корзины `v0` снимка нет: это сущность рейтинга, не снимок).
  - Корзина — смесь: снимок `B` и latest после `B` (обычно сильнее), поэтому рейтинг снимка `v<B>` слегка завышен; турнир играет чистые снимки.
  - Финальный снимок с версией не кратной `interval` — своя сущность.
- **Скриптовый и замороженный агент** — своя сущность по имени (`агент`).
- **Линия** сущности — её `agent_id`. Средние по полю считаются по линиям, а не по снимкам: иначе сотни снимков одной линии раздувают оценку.
- **Партии против себя.** Партия, где обе стороны — одна сущность, входит в подгонку только как данные о `b`. В счёт игр сущности (таблица, `top_k_min_games`, «мало игр») она не идёт.

**Модель.** Рейтинги считаются отдельно для каждой раскладки, как в SP2/SP3.
- **Источники.** Живой рейтинг, top-k и раздел «Рейтинги» отчёта считаются по `train` и `pulse`. Турнир считает рейтинги только по своим матчам (`source = tournament`, свой id турнира) и показывает их в своём отчёте. Матчи турниров в рейтинги запуска не входят. Сущность `-a имя=путь` в журнале — `имя#<хэш пути>`, в отчёте — `имя`.
- Единица — пара команд матча с T ≥ 2 командами, вес `1/(T−1)`, исход 1 / 0.5 / 0 по рангам. Это те же правила, что у нынешних `member_pairs`, только на уровне команд.
- Сила команды = среднее сил участников + поправка `b[раскладка, номер команды]`. Роли мест в раскладке фиксированы, поэтому номер команды задаёт и её роли: поправка ловит преимущество стороны (первый ход в крестиках-ноликах, стартовая позиция в tron) и асимметрию ролей (хищник/жертва). Ограничение: сумма `b` по командам раскладки равна 0. Партии сущности против самой себя (например, latest против latest одной корзины) несут информацию только о `b`.
- **Группы ролей.** Сущности, игравшие в раскладке одни и те же роли (по журналу), образуют группу. Шкалы разных групп сравнимы, только если есть мост: сущность, игравшая обе роли. Иначе разность групп поглощается `b`, и рейтинги сравниваются только внутри группы. Таблицы, `P(лучший)`, `P(в top-k)` и якорь считаются по группам; отчёт подписывает группу (например, «роль hunter»).
- **Компоненты связности.** Если граф сравнений раскладки распадается на компоненты, каждая получает свой якорь (правило якоря применяется внутри компоненты); сравнение между компонентами не выводится.
- `P(A бьёт B) = σ(S_A − S_B)`, ничья вносит 0.5 (логистическое правдоподобие с дробным исходом).
- Гауссов приор на силы (против бесконечных оценок у «всегда проигрывающих»).
- Мягкий штраф гладкости между соседними версиями одной линии: малоигравшие снимки опираются на соседей, но реальные скачки видны.
- Шкала: показывается в Elo-единицах (`400 / ln 10` на логит). Ноль — якорь `ratings.anchor` внутри каждой группы ролей и компоненты связности раскладки:
  - по умолчанию — агент с `colosseum.players.RandomBot` (первый в порядке конфига, если их несколько);
  - иначе среднее скриптовых и замороженных агентов;
  - иначе первая корзина (`v0`, стартовые веса) первого обучаемого агента группы — эта точка со временем не сдвигается.

  Якорь, не игравший в раскладке, группе или компоненте, заменяется следующим по правилу, с INFO в логе. `ratings.anchor` — имя агента конфига, иначе `ConfigError`. Якорь делает шкалу сравнимой между запусками с тем же полем.
- Раскладки с одной командой (`score`) не дают попарных сравнений. Для них рейтинг — средний счёт сущности и состава с 95 % ДИ (как `ScoreTracker` / cross-play SP2), из подробных матчей и `counts`.

**Подгонка.** Своя реализация на numpy, без новых зависимостей: метод Ньютона по логистическому правдоподобию с приором и гладкостью, с тёплым стартом от прошлого решения.
- Неопределённость в двух режимах:
  - быстрая (Лаплас: обратный гессиан MAP-оценки; `P(лучший)` и `P(в top-k)` — по выборкам из `N(θ̂, H⁻¹)`) — для живого рейтинга, top-k и дашборда;
  - bootstrap (по умолчанию 200 реплик с тёплым стартом) — для отчёта, турнира и `--snapshots top:N`. Реплики берутся по матчам для обучения и по блокам «seed + ротации» для турнира и оценки во время обучения, так как игры блока коррелируют.
- В FFA и при частых ничьих быстрые интервалы приближённые (композитное правдоподобие по парам); итоговый выбор — турнир (bootstrap по блокам).
- На выходе для каждой сущности:
  - рейтинг и 95 % ДИ;
  - нижняя граница `LCB` (квантиль `checkpoint.top_k_quantile`, блок 4);
  - число игр;
  - `P(лучший)` и `P(в top-k)` — среди снимков агента и, отдельно, среди всех сущностей группы ролей.
- Диагностика нетранзитивности: девианс `G² = 2·(LL_пары − LL_BT)` по парам с не менее чем 20 сравнениями против χ² с числом степеней свободы «пары − параметры». При p < 0.01 отчёт помечает «возможны циклы» и показывает 5 пар с наибольшими остатками. Порог числа игр — ruling плана.

**Живой рейтинг.** В главном процессе обучения подгонка повторяется раз в `ratings.refit_interval_sec` (по умолчанию 60) в фоновом потоке. Данные — таблица сравнений в памяти с ключом и значениями `counts` (блок 1). Поток-писатель пополняет её каждой записанной пачкой. Журнал читается целиком один раз, при старте (resume). Сжатие таблицу не меняет. BLAS главного процесса ограничен одним потоком (переменные окружения ставятся до импорта numpy в `colosseum train`). От порядка партий результат не зависит. Куда он попадает:
- `ratings.json = {"env_steps", "layouts", "bt": {раскладка: {группа: [...]}}}` — сущности, рейтинг, ДИ, игры; ключи `layouts` не меняются;
- сжатая запись `ratings` в `metrics.jsonl`: по агенту — рейтинг его последней корзины и лучшего снимка;
- строка консоли: `bt <рейтинг> ± <ДИ>`;
- дашборд.

Онлайн-ELO, win-rate-матрицы, `wr_vs_past` и таблицы PFSP SP2/SP3 остаются без изменений. PFSP по-прежнему выбирает соперников по EMA-счёту; перевод PFSP на рейтинг — позже, по необходимости.

**Конфиг.**

```yaml
ratings:
  anchor: null               # имя агента-якоря; null: RandomBot конфига, иначе среднее фиксированных агентов, иначе v0 первого агента
  refit_interval_sec: 60
  bootstrap_samples: 200
```

Секция только глобальная (блок 1).

Сила приора и гладкости — константы модуля, выбираются в плане по кросс-валидации на журналах демо-игр и фиксируются как rulings. Ручки появятся, только если замер покажет, что одной пары значений мало.

### Блок 3. `colosseum tournament` и отбор лучшего

**Участники.**
- **Кандидаты:**
  - `-a имя=путь` — каталог чекпоинта или `.pt`, как в `eval`;
  - `-a имя` — скриптовый или замороженный агент конфига;
  - `--run [алиас=]runs/x [--agent main] [--snapshots all | last:N | top:N | every:K]` — снимки запуска (повторяемый; у каждого `--run` свои `--agent` и `--snapshots`). `top:N` берёт N лучших по нижней границе рейтинга из журнала запуска; он требует журнала (у папки SP3 его нет — `ConfigError`; `all | last | every` работают). Имена сущностей — `main@v1200`, как в блоке 2, у второго и следующих запусков — `<алиас>/main@v1200`.
- **Поле** (`--field a,b,…`) — фиксированные соперники для `gauntlet`: агенты конфига, `-a`-игроки или снимки. По умолчанию — все скриптовые и замороженные агенты конфига. Поле без участников — `ConfigError` с подсказкой.

**Дизайн матчей.**
- **Блок** — один seed, один состав (кандидат + участники поля по командам) и все допустимые ротации команд: циклические сдвиги назначения команд, при которых каждый игрок сидит только на своих ролях:
  - 1v1 — два матча со сменой сторон;
  - T симметричных команд — T матчей;
  - асимметричные роли — только допустимые сдвиги, иногда один.

  Блок — единица расписания, повтора и bootstrap.
- **Seed** выводятся из `--seed` с разделением доменов (`SeedSequence([seed, этап, …])`); у pulse — свой домен `P`, не пересекающийся с A и B:
  - набор A (отбор) и набор B (подтверждение) не пересекаются по построению;
  - у всех кандидатов одни и те же seed блоков (общие случайные числа): это убирает дисперсию «карт».
  - Бот на скриптовом месте сидируется от seed эпизода, как в SP3.
  - `play_lineups` и `MatchRunner` получают явный seed на состав.
- **FFA и N игроков** в `gauntlet`: кандидат занимает одну команду, остальные T−1 команд — участники поля. Составы перебираются по кругу: все сочетания из F участников по T−1 при F ≥ T−1, иначе все мультимножества размера T−1. `--blocks` — число блоков на состав, поэтому каждый участник поля встречает кандидата одинаковое число раз.
- **Асимметричные роли:** кандидат играет только свои роли, остальные роли заполняет поле. Если допустимого состава нет — `ConfigError` с перечнем ролей. Кандидаты ранжируются внутри группы ролей (блок 2): `select` выбирает лучшего для каждой группы (например, лучшего охотника и лучшую жертву). Смешанные группы в одной таблице — `ConfigError` с перечнем групп.
- **Несколько раскладок.** Результат и отбор считаются по каждой раскладке; итог `select` — среднее по раскладкам с весами `matchmaking.layouts` агента (по умолчанию равными) на тех же bootstrap-репликах блоков. `--layout` сужает набор.
- **`--deterministic`** — жадные политики; по умолчанию стохастические, как в `eval`. Если в паре «кандидат — участник поля» все блоки дали один исход и одну длину, отчёт помечает «игры повторяются: недостаточно случайности». Такие пары в ДИ и `confirmed` считаются одним блоком.

**Режимы (`--mode`).**

| Режим | Что делает |
|---|---|
| `gauntlet` (по умолчанию) | каждый кандидат играет `--blocks` блоков против каждого участника поля |
| `round-robin` | все пары участников (кандидаты и поле) — матрица результатов |
| `halving` | successive halving по результату `gauntlet`: в каждом раунде нижняя половина (⌊n/2⌋, но не ниже `--finalists`) выбывает, число блоков удваивается, пока не останется `--finalists`; результаты прошлых раундов накапливаются |
| `select` | этап A — `halving` на наборе seed A до `--finalists` (по умолчанию 3); этап B — подтверждение: `gauntlet` финалистов на свежих seed B (`--confirm-blocks`); итог — по этапу B |

- **Результат кандидата** — средний попарный счёт против каждой команды поля (1 / 0.5 / 0 по рангам, как в блоке 2; в 1v1 это победа / ничья / поражение). Каждый участник поля весит одинаково, снимки одной линии вместе весят как одна линия. Рядом выводятся худший соперник и BT-рейтинг.
- **Раскладки `score`** (одна команда): блок — один seed и однородная команда кандидата. С `--field` добавляются составы «кандидат + участник поля» (по одному месту, ротация мест, как cross-play SP2). Результат кандидата — средний счёт команды с 95 % ДИ (bootstrap по блокам); `select`, `halving` и `confirmed` работают на этом счёте. Счёт и вероятность победы не смешиваются: в игре с раскладками обоих видов итог `select` требует `--layout`.
- **Итог `select`.**
  - Победитель — кандидат с лучшим результатом на этапе B.
  - `confirmed: true`, если его превосходство над вторым различимо: 95 % ДИ разности по bootstrap блоков этапа B не содержит 0.
  - Bootstrap парный и стратифицированный: в каждой реплике номера блоков выбираются заново внутри каждого участника поля (или состава), одинаково для всех финалистов (общие seed).
  - Иначе `confirmed: false` и список неразличимых финалистов. Решение остаётся за владельцем, тихого выбора нет.
  - Игры этапа A в оценку этапа B не входят (проклятие победителя).
  - Оценка победителя на этапе B смещена вверх отбором среди финалистов; ДИ разности корректен (строка в отчёте).
- Размеры по умолчанию (`--blocks`, начальный блок `halving`, `--confirm-blocks`) замеряются в плане на «лесенке ботов» (критерий 3.3) и фиксируются как rulings.

**Исполнение.**
- `--num-workers W` локальных процессов, по `--num-envs` сред в каждом. Каждый процесс — `MatchRunner` с ленивой загрузкой моделей и LRU-кэшем: снимков одной архитектуры может быть много.
- Главный процесс турнира раздаёт блоки, собирает результаты, пишет журнал (`source=tournament`, id турнира и блока) и считает отчёт.
- Распределённое исполнение — SP5.
- **Прерванный турнир продолжается:** повторный запуск с тем же `--name` сверяет итоговые настройки с `tournament.yaml` (различие — `ConfigError` со списком полей) и пропускает блоки, записанные целиком. Блок пишется одной транзакцией, когда сыграны все его матчи, поэтому частичных блоков в журнале не бывает. `uid` турнирного матча детерминирован: id турнира, этап, номер блока, состав, ротация.
- `--name` по умолчанию — `<mode>-<YYYYmmdd-HHMMSS>`.
- Проверка конфига — в области «play», как у `eval`.
- Код загрузки игроков и расписания общий с `eval`. Заодно убираются дубли SP3: разбор `-a`, правило округления числа матчей, двойная загрузка frozen-агентов, наложение `.pt`-настроек frozen-записи на чужой путь.

**Куда пишет.**
- С `--run runs/x`: матчи — в `runs/x/matches.db` (с несколькими `--run` — в журнал первого `--run`); отчёты — в `runs/x/tournaments/<name>/` (`report.json`, `report.txt`, `report.html`, `tournament.yaml` с итоговыми настройками и seed).
- Без `--run`: всё в `--output DIR`, включая свой `matches.db`.
- Турнир можно запускать, пока идёт обучение того же запуска: журнал в режиме WAL. На старте снимки-кандидаты и снимки поля жёстко связываются (иначе копируются) в `runs/x/tournaments/<name>/snapshots/`, поэтому вытеснение во время турнира им не мешает. Секция `env` конфига турнира должна совпадать с `config.resolved.yaml` запуска (иначе `ConfigError`); без `-c` берётся конфиг запуска.

**Отчёт** (общий рендерер с блоком 5), по каждой раскладке:
- таблица кандидатов: результат против поля с 95 % ДИ, худший соперник и его счёт, BT-рейтинг с ДИ по матчам этого турнира (bootstrap по блокам), `P(лучший)`, число игр;
- матрица «кандидат × участник поля» с ДИ;
- для `halving` и `select` — кто выбыл в каком раунде;
- для `select` — победитель, `confirmed` и неразличимые финалисты;
- флаг нетранзитивности (блок 2);
- seed, число игр, время.

Пример:

```bash
colosseum tournament -c cfg.yaml --run runs/harvest --snapshots top:20 --field greedy,random,prev_sub \
  --mode select --num-workers 4 --seed 7 --pin
```

**Закрепление.** `--pin` (только с `--run`) закрепляет победителя `select` в хранилище запуска (блок 4). Для ручного управления есть `colosseum pin runs/x main@v1200 [--remove]` и `colosseum pin runs/x --list`.

`colosseum eval` остаётся как есть: та же CLI и те же отчёты по парам.

### Блок 4. Хранение снимков: top-k, закреплённые, потолок

**Правило удержания** (на агента). Набор `keep` строится так:
1. **Всегда:**
   - `keep_last` новейших;
   - финальный снимок **текущего** запуска;
   - закреплённые;
   - только что сохранённый.
2. **`keep_every`:** версия кратна `interval · keep_every` — как в SP3.
3. **`keep_top_k`** (по умолчанию 0 — выключено): k снимков с наибольшей нижней границей рейтинга (`LCB`, квантиль `top_k_quantile`, по умолчанию 0.1, лапласовского распределения живой подгонки; блок 2).
   - Оценка снимка — BT-рейтинг по соревновательным раскладкам агента со средним по весам `matchmaking.layouts`, вычисленным на каждой выборке; в игре только с раскладками `score` — средний счёт (блок 2).
   - Квантили для top-k считаются в шкале, где среднее линии агента равно 0 (контрасты внутри линии), чтобы разброс якоря не влиял на порядок.
4. **Защита новых снимков** (только при `keep_top_k > 0`): снимок вне окна `keep_last`, у которого меньше `top_k_min_games` оценённых игр (по умолчанию 200), не вытесняется, пока не наберёт их.
   - Оценённые игры — сравнения с другой сущностью (блок 2). Снимку `v<B>` засчитываются и партии latest из его корзины против других сущностей (снимков, якорей, соперников, pulse); партии latest против latest той же корзины не считаются.

**Потолок** `max_snapshots` (решение владельца; по умолчанию 100 на агента). Если набор `keep` больше потолка, вытесняются незащищённые снимки (не из п. 1), в таком порядке:
1. снимки только по п. 2 (`keep_every`): при `keep_top_k = 0` и в распределённом лёрнере — от старых к новым (FIFO, без рейтинга), при `keep_top_k > 0` — по возрастанию `LCB`, неоценённые — от старых к новым;
2. снимки только по п. 4 — от старых к новым;
3. снимки top-k — по возрастанию `LCB`.

Если одних защищённых больше потолка — WARNING один раз, защищённые остаются.

**Финальные снимки при resume.** Защиту «финальный» получает только финальный снимок текущего запуска. Финальные снимки, импортированные из родительских запусков, становятся обычными и подчиняются п. 2–4 и потолку. Это закрывает пункт SP3 «частые stop/resume раздувают пул».
- `meta.json` нового снимка получает `run_id` запуска. Финальный — `final: true` и `run_id` текущего запуска; у снимков SP3 `run_id` нет, и они считаются импортированными.

**Закрепление** хранится в `meta.json` снимка (`"pinned": true`, атомарная перезапись) и переживает resume (импорт пула сохраняет поле). Его пишут `colosseum pin` и `tournament --pin`. Закреплённый снимок никогда не вытесняется.

**Когда применяется.**
- При каждом сохранении снимка — как в SP3.
- После каждой подгонки живого рейтинга, потому что рейтинги меняются: поток подгонки публикует оценки, удержание и `on_evict` выполняет главный цикл.
- Вытеснение по-прежнему идёт через `on_evict`: воркеры выгружают модель, PFSP забывает статистику (решения SP3 №24 и №50), журнал сворачивает матчи снимка (блок 1).
- Удержание — чистая функция «записи + оценки + правила → что оставить» в отдельном модуле. `CheckpointManager` вызывает её с поставщиком оценок; хранилище SP5 сможет вызывать её же.

**Конфиг.**

```yaml
checkpoint:
  interval: 1000
  keep_last: 20
  keep_every: 10
  keep_top_k: 0            # > 0 включает top-k по нижней границе рейтинга (нужен match_log)
  top_k_quantile: 0.1
  top_k_min_games: 200
  max_snapshots: 100       # на агента; null — без потолка (как в SP3)
  save_optimizer: true
```

- Новые ключи `checkpoint` — только глобальные (блок 1).
- `validate` печатает итоговое правило удержания для каждого агента.
- `keep_last + pinned` больше `max_snapshots` — WARNING в `validate`; `max_snapshots < keep_last` — `ConfigError`.

### Блок 5. Отчёт и дашборд

**Решение владельца:** HTML-отчёт одним файлом и живой сервер на stdlib; WandB остаётся зеркалом временных рядов.

**Команды.**
- `colosseum report runs/x [-o FILE]` собирает самодостаточный HTML (по умолчанию `runs/x/report.html`):
  - данные вшиты в страницу как JSON, CSS и JS — свои;
  - графики рисуются собственным SVG-кодом, без библиотек и CDN;
  - файл открывается без сети, его можно переслать на телефон;
  - если в запуске есть турниры, их отчёты входят в страницу.
- `colosseum dashboard runs/x [--host 127.0.0.1] [--port 8765] [--refresh 10]` показывает ту же страницу вживую:
  - `http.server` (stdlib), JSON по разделам на `/api/<раздел>`, страница обновляется раз в `--refresh` секунд;
  - журнал открывается только для чтения;
  - BT-рейтинг берётся из `ratings.json` (раздел `bt`), если обучение идёт; иначе считается по журналу и кэшируется до изменения журнала;
  - по умолчанию слушает только `127.0.0.1`, без авторизации: с другой машины или телефона — через SSH-туннель (рецепт в `ARENA_GUIDE.md`).

**Разделы страницы** (одинаковы в отчёте и дашборде):

| Раздел | Что показывает | Источник |
|---|---|---|
| Сводка | состояние запуска (идёт / завершён), шаги и доля бюджета, агенты и их виды, BT ± ДИ и ELO по агенту, `wr_vs_past`, скорость | `metrics.jsonl`, `ratings.json` |
| Рейтинги | таблица сущностей (BT, ДИ, игры, `P(лучший)`), фильтр по агенту и раскладке; график «рейтинг по версиям» с полосой ДИ и линиями якорей | журнал, блок 2 |
| Матрица результатов | тепловая карта по линиям, упорядоченная по рейтингу: цвет — счёт, серым — мало игр, по нажатию — счёт, ДИ, число игр; та же карта по снимкам выбранного агента | журнал |
| Якоря | счёт против каждого якоря по версиям; по оценке во время обучения, если она включена, иначе по обучающим партиям (с пометкой «смещено PFSP») | журнал |
| Соперники | фактическая смесь категорий соперников по `env_steps`; верх таблицы PFSP | `episodes`, `ratings.json` |
| Обучение | ряды по `train_step` для каждого агента: лоссы, энтропия, KL, `clip_fraction`, `explained_variance`, `rho_trunc_mass`, ESS, LR, kickstart; выбор рядов | `metrics.jsonl` (`train`) |
| Система | шаги/с, обновления/с, глубины очередей, потерянные результаты и эпизоды, размер журнала, режим «только счётчики», свободное место | `metrics.jsonl` (`system`) |
| Матчи | последние матчи с фильтрами (агент, раскладка, источник, исход): состав, версии, seed, длина, ссылка на реплей, если её дала среда | журнал |
| Турниры | список турниров запуска и их отчёты (блок 3) | `tournaments/` |

- Для раскладок `score` разделы «Рейтинги» и «Матрица результатов» показывают средний счёт с ДИ и таблицу cross-play вместо BT и тепловой карты.
- Состояние запуска в «Сводке»: лаунчер пишет `runs/x/run_state.json` (`running` / `finished` / `failed`, pid); дашборд проверяет, жив ли pid (не по меткам времени).
- **Размер страницы ограничен:**
  - ряды прореживаются до 2 000 точек;
  - таблица сущностей — до 2 000 строк;
  - в разделе «Матчи» — последние 1 000 матчей;
  - тепловая карта по снимкам — до 100 снимков.

  Подробности — через фильтры дашборда.
- Порядок рядов — по `train_step` и `env_steps`, а не по `ts` (принцип 4).
- Страница читается с телефона (одна колонка, широкие таблицы прокручиваются внутри себя), светлая и тёмная темы.
- WandB получает новые числовые ряды (`rho_trunc_mass`, BT последней корзины агента); новых таблиц и матриц в WandB нет (таблица PFSP туда не идёт с SP3, win-rate-матрица SP2 остаётся как есть).

### Блок 6. Оценка снимков во время обучения (pulse)

**Решение владельца:** опция конфига, по умолчанию выключена.

**Зачем.** Обучающие партии смещены: соперников выбирает PFSP, latest всё время меняется. Pulse прогоняет каждый новый снимок через фиксированное поле на одних и тех же seed, как ruler-пул OpenAI Five. Кривая «результат против поля по версиям» несмещённая, а соседние версии сравниваются на одинаковых seed.

**Конфиг.**

```yaml
evaluation:
  enabled: false
  agents: null               # какие обучаемые агенты; null — все
  field: null                # участники поля; null — все скриптовые и замороженные агенты конфига
  layouts: null              # null — все включённые раскладки агента; для score — однородная команда снимка и составы с полем (блок 3)
  every: 1                   # каждый k-й сохранённый снимок
  blocks: 25                 # блоков на участника поля (1v1: 50 игр)
  num_envs: 8
  deterministic: false
  max_backlog: 4             # снимков в очереди; при переполнении пропускаются старые
```

- Секция только глобальная (блок 1); агентов pulse выбирает `evaluation.agents`.
- `evaluation.agents` — только обучаемые агенты; `evaluation.field` — только имена агентов конфига (SP3 ruling 9: в конфиге на снимки не ссылаются).

**Исполнение.**
- Лаунчер запускает дочерний процесс `pulse` с теми же правилами жизни, что у воркеров:
  - не реагирует на SIGINT;
  - умирает вместе с родителем;
  - если он упал, запуск останавливается с указанием на его лог;
  - пишет лог `logs/pulse.log`.
- После каждого сохранения снимка главный процесс отправляет `pulse` его веса numpy-словарём, как воркерам. Вытеснение снимка с диска оценке не мешает.
- `pulse` играет `gauntlet` блока 3 на своём фиксированном наборе seed `P` (свой домен, блок 3), одинаковом для всех снимков. Его места не собирают данные.
- Результаты идут через очередь результатов с `source = pulse`, попадают в журнал и рейтинги. В отчёте это отдельная кривая. Pulse кладёт результаты с ожиданием (не `put_nowait`): его матчей мало, терять их нельзя.
- Реплики bootstrap для pulse — по блокам, как у турнира.
- Очередь снимков ограничена `max_backlog`: если оценка не успевает, пропускаются старые снимки. Это INFO в логе и счётчик в `system`, новейшие важнее.
- Финальный снимок оценивается, только если запуск дал на это время. Неоценённые снимки в отчёте помечены.
- `pulse` занимает CPU (один процесс, `num_envs` сред). Это написано в документации; бенчмарк критерия 3.6 идёт с выключенной оценкой.
- `validate` проверяет поле (агенты есть, роли покрывают раскладки) и печатает итоговые настройки.

### Блок 7. Метрики и отложенные пункты

1. **Срезанная масса весов V-trace** (ответ владельца на Q2). Метрики `train` `rho_trunc_mass = Σ max(ρ − ρ̄, 0) / Σ ρ` и `c_trunc_mass = Σ max(ρ − c̄, 0) / Σ ρ` по ACT-слотам заменяют `rho_clip_frac` и `c_clip_frac`.
   - `ρ` — тот же, по которому V-trace считает следы (`unit_trace`).
   - `ρ̄` и `c̄` — те же, что применяет V-trace (при `unit_trace: none` ρ ≡ 1 и масса ровно 0).
   - On-policy метрика равна 0 с точностью до погрешности float (~1e-7) и растёт с тем, сколько V-trace реально срезает.
   - Старые имена удаляются. Обновляются список метрик в README, тесты APPO, упоминания в `GPU_CHECKS.md`, `scripts/units_experiment.py`, `scripts/measure_amp_logratio.py` и `docs/benchmarks.md`.
2. **Монотонные счётчики потерь.** `dropped_reward_episodes` и новый `dropped_match_results` в `system` — счётчики на весь запуск. Воркер шлёт накопленное значение, агрегатор берёт максимум по воркеру и суммирует по всем воркерам, которые когда-либо отчитывались.
3. **Сжатая запись `ratings`.**
   - Полная таблица PFSP остаётся только в `ratings.json`.
   - В запись `metrics.jsonl` вместо неё идёт сводка по хозяину: число записей, минимальный и максимальный счёт.
   - Добавляется краткий BT (блок 2).
   - Остальные поля записи (ELO, win-rate, `wr_vs_past`, роли, `score`) не меняются, их размер ограничен числом агентов.
   - Снимок рейтингов строится только на такте записи, а не на каждом проходе главного цикла (пункт SP2).
4. **Состояние лиги переживает resume.**
   - `runs/<name>/league_state.json`: полное состояние `RatingBook` (включая таблицы по ролям и окно `wr_vs_past`) и `PfspStats` (со списком забытых снимков) по раскладкам; агенты, которых нет в новом конфиге, отбрасываются с INFO, новые начинают пустыми. Состояние своего матчмейкера (`on_result`) не сохраняется (документировано).
   - Пишется атомарно на каждом такте метрик и в конце запуска.
   - Resume из папки запуска загружает файл исходного запуска. У папки SP3 его нет — статистика начинается пустой, в логе INFO.
   - Для resume из отдельного чекпоинта поведение SP3 не меняется.
5. **`colosseum bc` пишет в лог своё устройство** (мелочь из GPU-проверок).

### Блок 8. Граница с SP5

- Журнал (`MatchLog`), рейтинги (подгонка, bootstrap, сущности), расписание и логика турнира, правило удержания, построители данных отчёта — библиотеки без очередей процессов и без привязки к лаунчеру.
  - Сегодня их вызывают главный процесс обучения и команда `tournament`; хаб SP5 вызовет их же.
- Схема записи матча (блок 1) — контракт SP4. Транспорт этой записи между машинами — SP5.
- **Распределённые команды** (`run-learner`, `run-workers`) в SP4:
  - результатов матчей там по-прежнему нет, журнал не пишется (документировано);
  - `evaluation.enabled` и `checkpoint.keep_top_k > 0` дают `ConfigError` с указанием на SP5 (`distributed.check_distributed_scope`);
  - `max_snapshots` работает и в распределённом лёрнере: без рейтингов вытесняются самые старые незащищённые снимки.
- `MatchmakerContext` и контракт матчмейкера в SP4 не меняются.

  - `MatchResult` и `SeatResult` без новых полей создаются, как раньше.
- **Контрактные тесты:**
  - **поток результатов:** каждый обучающий матч попадает в журнал ровно один раз либо учтён в `dropped_match_results`; версии мест в начале и конце эпизода верны, когда веса меняются посреди эпизода; при искусственно переполненной очереди воркера или писателя потеря считается и даёт WARNING; при остановке очередь писателя дописывается;
  - **журнал:**
    - сжатие не меняет рейтинги: подгонка по журналу совпадает с подгонкой по полной таблице сравнений в памяти (тестовый режим без удаления) в пределах допуска; сжатие сохраняет номер команды;
    - размер подробного окна остаётся в пределах (тест с маленьким окном); части, которые чистка не трогает, окно не схлопывают;
    - защита диска (подменяемая функция свободного места) переключает на счётчики и обратно;
    - импорт при resume сворачивает подробное окно родителя в `counts`;
    - открытие только для чтения, пока идёт запись; два писателя (обучение и турнир) не теряют записи;
  - **Bradley–Terry:**
    - на синтетических данных с известными силами (1v1 со стороной, команды, FFA, ничьи, асимметричные роли с мостом и без) истинные разности с якорем внутри группы ролей и компоненты попадают в 95 % интервалы не реже номинала за вычетом допуска (≥ 200 сравнений на сущность, приор и гладкость — значения модуля);
    - поправка `b` ловит преимущество стороны; партии против себя не идут в счёт игр;
    - асимметричные роли без моста: межгрупповые сравнения не выводятся; несвязный граф — свой якорь в каждой компоненте;
    - якорь даёт 0; правило якоря по умолчанию (первый `RandomBot`, среднее фиксированных, `v0` первого агента), замена неигравшего якоря, `ConfigError` на чужое имя;
    - гладкость сглаживает малоигравшие версии;
    - «всегда проигрывающий» и сущность с малым числом игр получают конечную оценку;
    - флаг нетранзитивности (G²) не срабатывает на транзитивной синтетике с редкими парами и срабатывает на цикле;
    - раскладки `score` — средний счёт с ДИ;
  - **удержание снимков:** табличные тесты чистой функции — `keep_last`, финальный только текущего запуска (по `run_id`), закреплённые, `keep_every`, top-k по `LCB`, защита новых до `top_k_min_games`, потолок и порядок вытеснения (FIFO при `keep_top_k = 0`), WARNING при переполнении защищёнными; закрепление переживает resume; проверки `max_snapshots` в `validate`;
  - **турнир:**
    - у всех кандидатов одинаковые seed блоков;
    - ротации мест поровну, только допустимые для ролей;
    - наборы A, B и `P` не пересекаются;
    - в FFA каждая пара «кандидат — участник поля» встречается поровну (сочетания и мультимножества);
    - асимметричные роли: отбор внутри группы ролей, смешанные группы — `ConfigError`;
    - несколько раскладок и раскладки `score`;
    - несколько `--run` с алиасами;
    - frozen и скриптовые игроки в роли тиммейтов (пункт SP3);
    - продолжение прерванного турнира пропускает только целые блоки; смена настроек под тем же `--name` — `ConfigError`;
    - снимки турнира переживают вытеснение обучением; несовпадение `env` с запуском — `ConfigError`;
    - повторяющиеся детерминированные игры помечаются и считаются одним блоком;
    - логика `halving` и `select` (на подменённом источнике результатов);
    - `confirmed` выставляется по правилу блока 3 (парный стратифицированный bootstrap);
  - **оценка во время обучения:** `pulse` получает каждый новый снимок; его матчи в журнале с `source = pulse` и одинаковыми seed для разных снимков; переполнение очереди снимков пропускает старые; процесс умирает с запуском, а его падение останавливает запуск;
  - **resume:** журнал продолжается, состояние лиги (`league_state.json`) восстанавливается;
  - **отчёт и дашборд:** построители данных для `wdl`, `rank` и `score` (для `score` — средний счёт и cross-play); HTML содержит данные и все разделы; сервер на свободном порту отдаёт JSON разделов; состояние запуска по `run_state.json`;
  - **распределённый режим:** `evaluation.enabled` и `keep_top_k > 0` дают `ConfigError` с указанием на SP5; `max_snapshots` в распределённом лёрнере вытесняет старые.
- **Быстрые интеграционные:**
  - `tournament` на `tic_tac_toe` с короткой «лесенкой» из трёх ботов (без порогов);
  - `report` и `dashboard` на коротком запуске;
  - смоук-тесты обучения на демо-конфигах проверяют журнал.
- **Медленные:**
  - «лесенка ботов» на двух играх (критерий 3.3);
  - конвейер с оценкой во время обучения и `select` (критерий 3.4);
  - длинный прогон `tic_tac_toe` с маленьким окном (критерий 3.5);
  - 10 тестов SP2/SP3 без изменения порогов.
- **Бенчмарк:** изменения схемы конфига обновляют `scripts/bench_throughput.py::_make_config` (правило SP1, охранный тест). На машине со скачущими часами скорость считается по счётчикам (как в отчёте GPU-проверок).

## 8. Решения и риски

**Решения владельца** (брейншторм 2026-10-16):

| Решение | Почему | Цена ошибки |
|---|---|---|
| Журнал — SQLite, все матчи, со своевременной чисткой | источник правды; диск на машинах для соревнований не бесконечен | окно и защита диска — новая логика с тестами |
| Top-k по нижней границе рейтинга + закреплённые | «лучшие» без шума: граница и защита новых снимков; закрепление по итогам турнира | вытеснение по рейтингу необратимо (защита новых, `keep_every`, потолок) |
| Дашборд — HTML-отчёт + живой сервер на stdlib | без зависимостей, офлайн, на телефон, тот же код для хаба SP5 | свой фронтенд дороже в разработке |
| Оценка во время обучения — опция конфига | несмещённая кривая силы по ходу обучения | CPU у воркеров (выключено по умолчанию) |
| Потолок `max_snapshots` | диск под снимками растёт с `keep_every` без предела | при малом потолке теряются старые снимки для PFSP |
| `rho_trunc_mass` вместо `rho_clip_frac` (Q2 GPU-проверок) | доля «ρ > 1» читается 0.41–0.52 в любом режиме | ряды WandB меняют имена |

**Решения контроллера при написании спеки** (владелец проверяет при ревью):
1. Bradley–Terry — своя реализация на numpy. OpenSkill не берётся: живой рейтинг — тот же BT по таймеру, и это не новая зависимость и не второй рейтинг.
2. Онлайн-ELO, win-rate и PFSP SP2/SP3 не меняются. PFSP по-прежнему выбирает по EMA-счёту.
3. Партии latest засчитываются корзине `⌊v / interval⌋ · interval`.
4. Сила команды — среднее участников плюс поправка `b[раскладка, номер команды]` (сторона и роли; сумма по раскладке 0). Ничья — 0.5, FFA — по парам команд. Модели Davidson и Plackett–Luce — позже.
5. Якорь шкалы по умолчанию — `RandomBot` конфига; без фиксированных агентов — `v0` первого обучаемого агента (точка не дрейфует).
6. Результат кандидата в турнире — средний попарный счёт против поля с равным весом линий. `confirmed` выставляется, только если ДИ разности со вторым на этапе B не содержит 0. Тихого выбора между неразличимыми нет.
7. Турнир с `--run` пишет в журнал запуска (WAL), отчёты кладёт в `runs/x/tournaments/<name>/`. Матчи турнира в рейтинги запуска не входят: турнир считает рейтинги только по своим матчам.
8. Статистика лиги переживает resume через `league_state.json` (сохранённое состояние), а не через переигрывание журнала: точно и дёшево.
9. Старые имена `rho_clip_frac` и `c_clip_frac` удаляются, а не оставляются псевдонимами.
10. `max_snapshots` по умолчанию 100 на агента.
11. Дашборд по умолчанию слушает только `127.0.0.1` и без авторизации. Внешний доступ — через SSH-туннель.
12. Очередь результатов — 10 000 мест. Потери считаются, но воркер не блокируется: обучение важнее одного результата.
13. Сила приора и гладкости, а также размеры турнира по умолчанию — из замеров плана (rulings).

**Уточнения после ревью спеки** (ревьюер-субагент на Opus сверил спеку с кодом и прошёл механизмы на шести демо-играх; владелец проверяет при ревью):
1. Поправка силы команды — по номеру команды в раскладке, а не по ролям: так она ловит и первый ход в симметричных играх (блок 2).
2. `counts` хранит статистику по парам команд (`n`, `Σw`, `Σw·y`): размер не растёт с числом соперников в FFA, сторона сохраняется (блок 1).
3. Группы ролей и компоненты связности: шкалы без моста не сравниваются, якорь — в каждой группе и компоненте; `select` выбирает лучшего в каждой группе (блоки 2, 3).
4. Живой рейтинг — из таблицы сравнений в памяти, журнал читается только при старте; BLAS главного процесса — один поток (блок 2).
5. Неопределённость живого рейтинга и top-k — лапласовская (выборки из `N(θ̂, H⁻¹)`); bootstrap — для отчёта, турнира и `top:N` (блоки 2, 4).
6. Источники рейтингов: запуск — `train` и `pulse`; турнир — только свои матчи; `-a имя=путь` в журнале — `имя#хэш` (блок 2).
7. Партии сущности против себя идут только в `b`, в счёт игр и `top_k_min_games` — нет (блоки 2, 4).
8. Якорь по умолчанию без фиксированных агентов — `v0` первого обучаемого агента; первый `RandomBot` при нескольких; проверка `ratings.anchor` (блок 2).
9. Турнир: блоки с допустимыми ротациями, составы FFA по сочетаниям, попарный счёт, несколько раскладок, раскладки `score` (блок 3).
10. Прерванный турнир продолжается целыми блоками; смена настроек под тем же именем — `ConfigError`; детерминированный `uid` (блок 3).
11. Снимки турнира жёстко связываются на старте; `env` турнира сверяется с запуском (блок 3).
12. Потолок без top-k вытесняет `keep_every`-снимки по FIFO, как распределённый лёрнер; `run_id` в `meta.json` отличает финальный текущего запуска (блок 4).
13. Удержание и `on_evict` выполняет главный цикл, не поток подгонки; очередь писателя ограничена 100 000, сброс при остановке (блоки 1, 4).
14. Окно считается по подробным обучающим матчам; WAL учитывается и усекается (блок 1).
15. Resume не копирует подробное окно родителя, а сворачивает его в `counts` (блок 1).
16. Флаг нетранзитивности — G²-тест по парам с достаточным числом игр, а не сравнение log-loss на тех же данных (блок 2).
17. Несколько `--run` в одном турнире, с алиасами (блок 3).
18. Повторяющиеся детерминированные игры помечаются и считаются одним блоком (блок 3).
19. Тест покрытия BT — по разностям с якорем в той же шкале (критерий 3.2, раздел 6).

**Изменения правил SP1–SP3:**
- `MatchResult` и `SeatResult` получают новые поля (со значениями по умолчанию);
- метрики `train` `rho_clip_frac` и `c_clip_frac` заменены на `rho_trunc_mass` и `c_trunc_mass`;
- в записи `ratings` файла `metrics.jsonl` полная таблица PFSP заменена сводкой; полная — только в `ratings.json`. Обновляется тест SP2, закрепляющий ключи;
- защиту «финальный снимок» получает только финальный снимок текущего запуска (SP3: любой финальный);
- у числа снимков появляется потолок, по умолчанию 100 на агента (SP3: без предела);
- статистика лиги переживает resume из папки запуска (SP3 §8 п. 8: начиналась заново);
- очередь результатов — 10 000 мест вместо 1 000; в `system` новые поля;
- в `meta.json` снимка появляются `run_id` и `pinned`;
- ссылки на снимки `агент@v<N>` в CLI (`tournament --field`, `pin`); в конфиге — только имена (SP3 ruling 9 в силе);
- `eval` / `record` больше не накладывают `.pt`-настройки frozen-записи на `-a имя=путь`;
- `MatchRunner` принимает явный seed на состав (eval сохраняет прежнее сидирование).

**Риски:**

| Риск | Смягчение |
|---|---|
| Запись в SQLite тормозит обучение | поток-писатель, пачки, одна транзакция на пачку; бенчмарк критерия 3.6 |
| Подгонка BT медленная на тысячах сущностей | метод Ньютона с плотным гессианом до ~2 000 сущностей, дальше — итеративный решатель; замер в плане; живой рейтинг по таймеру в фоновом потоке по таблице в памяти; bootstrap не на горячем пути: живой рейтинг и top-k — лапласовские |
| Фронтенд дашборда разрастается | фиксированный набор разделов, данные строятся в Python, тесты по данным и разметке, без библиотек |
| Рейтинг по смещённым обучающим партиям вводит в заблуждение | итоговый выбор — только турниром; пометка «смещено PFSP»; оценка во время обучения |
| Повреждение журнала при аварии | WAL переживает падение процесса; если файл не открывается — переименовать его, начать новый журнал, ERROR в лог |
| `pulse` отнимает CPU у воркеров | выключено по умолчанию; `num_envs`, `every`; документация |
| Окно журнала по умолчанию не подходит машине | `detail_window_mb`, защита диска, рецепт в `ARENA_GUIDE.md` |
| Скачки часов (WSL2) | порядок по счётчикам; бенчмарк по счётчикам |
| Объём SP4 (9 блоков) | части P0–P8, ревью после каждой задачи |
| Регрессии гарантий SP1–SP3 | их тесты остаются регрессионной сеткой; slow-набор при приёмке |
