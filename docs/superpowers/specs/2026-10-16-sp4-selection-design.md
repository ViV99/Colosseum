Четвёртый из шести подпроектов (см. «Roadmap» в CLAUDE.md), идёт параллельно с SP5. SP3 дал арену: обучаемые, замороженные и скриптовые игроки в одной лиге, PFSP по снимкам, якоря. Но выбрать из неё лучшего бота надёжно нельзя:
- онлайн-ELO считается по агентам (снимок засчитывается своему агенту), без неопределённости, зависит от порядка партий;
- результаты матчей живут только в памяти (10 000 последних) и при переполнении очереди теряются молча;
- eval сравнивает только пары агентов в одном процессе, без общей сводки и без отбора;
- снимки хранятся только по версии;
- мониторинг — консоль, `metrics.jsonl` и WandB.

SP4 вводит журнал матчей как источник правды, рейтинги снимков с доверительными интервалами, турнир с контролируемым дизайном и двухэтапным отбором, хранение снимков по рейтингу с ограничением диска, оценку снимков во время обучения, HTML-отчёт и живой дашборд. **Конфиги, чекпоинты и папки запусков SP3 продолжают работать.**

## 1. Цель

Финальный этап соревнования работает от начала до конца:

1. **Журнал.** Каждый матч обучения, турнира и оценки во время обучения попадает в журнал запуска (`runs/<name>/matches.db`). Размер журнала ограничен по построению: старые обучающие матчи сжимаются в счётчики, а свободное место на диске охраняется.
2. **Рейтинги.** Рейтинги снимков (Bradley–Terry с доверительными интервалами) считаются из журнала. Живой рейтинг виден по ходу обучения. По желанию отдельный процесс прогоняет каждый новый снимок через фиксированное поле соперников (несмещённая оценка во время обучения).
3. **Турнир и отбор.** `colosseum tournament` сравнивает кандидатов — снимки запусков, замороженные чекпоинты любой архитектуры и скриптовых ботов — по контролируемому дизайну (общие seed, ротация мест). Он выбирает лучшего в два этапа: отбор, затем подтверждение на свежих seed. Итог — отчёт с интервалами и числом игр.
4. **Хранение.** Снимки хранятся не только по версии: top-k по нижней границе рейтинга, закреплённые и потолок общего числа снимков.
5. **Наблюдаемость.** `colosseum report` собирает самодостаточный HTML-отчёт, а `colosseum dashboard` показывает то же вживую. В обоих есть:
   - рейтинги во времени и матрица результатов;
   - результаты против якорей и фактическая смесь соперников;
   - здоровье обучения;
   - матчи;
   - итоги турниров.

Попутно — отложенные пункты метрик:
- срезанная масса весов V-trace вместо `rho_clip_frac` / `c_clip_frac` (ответ владельца на Q2);
- монотонный `dropped_reward_episodes`;
- сжатая таблица PFSP в записях `ratings`;
- рейтинги и статистика лиги переживают resume;
- финальные снимки не раздувают пул при частых resume.

## 3. Критерии готовности

1. **Тесты.** Полный быстрый набор (`pytest -m "not gpu and not slow"`) зелёный, 0 предупреждений; `ruff check .` чистый. Соглашения SP1–SP3 соблюдены: файлы только в `tmp_path`, ≤ 2 воркер-процесса, процессы через `tests/cli_runner.py`.
2. **Контрактные тесты** (раздел 6) зелёные. В том числе:
   - каждый матч обучения попадает в журнал ровно один раз, с версиями весов мест в начале и конце эпизода; потеря результата никогда не молчаливая (счётчик + WARNING);
   - сжатие журнала не меняет рейтинги (до и после сжатия совпадают в пределах допуска); размер журнала остаётся в пределах окна; при нехватке места журнал переходит на счётчики, обучение продолжается;
   - Bradley–Terry восстанавливает силы синтетических игроков (1v1, команды, FFA, ничьи, асимметричные роли): истинные значения в 95 % интервалах с частотой не ниже номинальной за вычетом допуска;
   - хранение снимков: top-k по нижней границе, закреплённые, потолок `max_snapshots`, защита новых снимков до набора игр, `keep_last` / `keep_every` / финальный — по правилам блока 4;
   - турнир: у всех кандидатов одни и те же seed, места ротируются поровну; этап подтверждения не использует seed отбора;
   - оценка во время обучения: процесс получает каждый новый снимок, его матчи попадают в журнал с источником `pulse`, процесс живёт и умирает вместе с запуском;
   - resume из папки запуска продолжает журнал, рейтинги и статистику PFSP.
3. **Лесенка ботов (главный критерий отбора).** Набор скриптовых ботов известной силы (один бот с разной долей случайных ходов) на двух демо-играх: 1v1 и FFA или командной. `colosseum tournament --mode select` ставит их в истинном порядке и выбирает сильнейшего, BT-интервалы соседей не противоречат порядку. Число игр и допуски замеряются в плане и фиксируются как rulings.
4. **Конвейер (slow).** На демо-игре: `train` с оценкой во время обучения → рейтинг снимков растёт по версиям (тренд положительный, порог — ruling плана) → `tournament --mode select` по снимкам запуска с полем из якорей выбирает снимок, подтверждённый на свежих seed, и он выигрывает у `RandomBot` не меньше порога медленных тестов SP3. HTML-отчёт этого запуска собирается.
5. **Диск.** Длинный прогон на `tic_tac_toe` (больше окна журнала): `matches.db` не превышает окно + запас (ruling плана), счётчики полны (рейтинги по журналу совпадают с рейтингами без сжатия), число снимков не превышает `max_snapshots`.
6. **Скорость.** Throughput на `tic_tac_toe` (`scripts/bench_throughput.py`, журнал включён, оценка во время обучения выключена) не хуже `main` (SP3 + GPU-правки), замеренного в тех же условиях на той же машине, более чем на 5 % при 1 / 2 / 4 воркерах. Если часы машины скачут (WSL2, отчёт GPU-проверок), замер идёт по счётчикам, а не по окнам `ts`.
7. **Отчёт и дашборд.**
   - `colosseum report` собирает HTML для запусков демо-игр всех видов исхода (`wdl`, `rank`, `score`); файл открывается без сети, все разделы на месте (тест по данным и разметке).
   - `colosseum dashboard` отдаёт ту же страницу и данные вживую.
   - Владелец смотрит отчёт с телефона при приёмке.
8. **Совместимость с SP3.** Конфиги `configs/examples/` проходят `validate` без правок. Папка запуска SP3 (без `matches.db`) возобновляется. Чекпоинты SP3 играют в турнире как снимки и как frozen-агенты.
9. **Распределённый режим.** Тесты SP2/SP3 зелёные. Новые настройки SP4 в распределённых командах дают `ConfigError` с указанием на SP5, кроме тех, что работают локально в каждом процессе.
10. **Документация:**
    - новый `docs/ARENA_GUIDE.md` (рус.): журнал, рейтинги, турнир и рецепт выбора сабмита, хранение, оценка во время обучения, отчёт и дашборд;
    - README и статус в CLAUDE.md описывают реальное состояние;
    - список метрик обновлён.
11. **Slow-набор** зелёный целиком (тесты SP2/SP3 и новые).

## 4. Принципы

- **Журнал — источник правды.** Рейтинги, матрицы и отчёты — функции журнала. Онлайн-ELO SP2 остаётся индикатором прогресса без изменений. Отбор и хранение опираются на Bradley–Terry с интервалами.
- **Отбор — контролируемый эксперимент.** Обучающие партии смещены (соперников выбирает PFSP, latest меняется), поэтому итоговое решение принимается по турниру с заранее заданным полем и общими seed. Выбранного подтверждают на свежих seed (проклятие победителя).
- **Диск ограничен по построению.** У каждого растущего хранилища есть предел и поведение при его достижении:
  - журнал: окно подробных записей + счётчики;
  - снимки: `max_snapshots`;
  - защита свободного места.

  Обучение из-за этого не падает.
- **Без новых обязательных зависимостей.** Только stdlib (`sqlite3`, `http.server`) и numpy. Отчёт и дашборд без CDN, работают офлайн.
- **Удобный конфиг.**
  - Минимальный конфиг не растёт.
  - Дефолты: журнал включён, top-k и оценка во время обучения выключены, дашборд — отдельная команда.
  - `validate` показывает итоговые настройки, ошибки — `ConfigError` с подсказкой.
- **Границы с SP5.**
  - Журнал, рейтинги и турнирное расписание — библиотеки без привязки к очередям процессов: на входе записи матчей, на выходе таблицы.
  - Схему записи матча задаёт SP4, транспорт — SP5.
- **Порядок — по счётчикам, не по часам.** `env_steps`, номер записи и версия упорядочивают данные. Метки времени только информационные (часы WSL2 скачут, отчёт GPU-проверок).
- **Ошибки громкие** (как в SP2/SP3): молчаливых фолбэков нет, кроме описанных здесь и унаследованных.
- **Решения SP1–SP3 в силе,** если этот документ явно их не меняет (список — раздел 8). Перед правкой области проверяются rulings в отчётах приёмки SP1, SP2 и SP3.
- **Тесты вперёд:** контрактные тесты пишутся до переделки потока результатов и хранения снимков.

## 5. Дизайн по блокам

### Блок 1. Журнал матчей

**Запись матча.** `MatchResult` и `SeatResult` получают новые поля. У всех есть значения по умолчанию, поэтому старый код и тесты, создающие их напрямую, работают.

- `MatchResult`:
  - `uid` — глобально уникальный ключ: id запуска, источник, воркер, среда, номер эпизода. Нынешний `match_id` уникален только внутри запуска.
  - `source`: `train` | `tournament` | `pulse`.
  - `seed` — seed эпизода, если он задан.
  - `env_steps` — глобальный счётчик шагов на конце эпизода, как его видит воркер.
  - `block` — блок дизайна турнира (общий seed и ротации мест), у обучающих матчей `None`.
- `SeatResult`:
  - `version_start`, `version_end` — версия весов места в начале и в конце эпизода. Для latest это версия агента на воркере (веса меняются по таймеру и посреди эпизода тоже), для снимка `ckpt_v<N>` это `N`, для скриптового и замороженного `None`.
  - `rating_version` — версия, которой засчитывается партия (блок 2).

`MatchRunner` получает необязательную функцию «текущая версия агента»; `RolloutLoop` передаёт свои `policy_versions`. Eval и турнир берут версии из id сетей.

**Хранилище.** `runs/<name>/matches.db` — SQLite (stdlib):
- режим WAL: отчёт, дашборд и турнир читают, пока обучение пишет;
- `auto_vacuum = INCREMENTAL`: освобождённое место возвращается на диск.

| Таблица | Содержимое |
|---|---|
| `runs` | id запуска, имя, родитель (resume), игра, хэш конфига, `checkpoint.interval` (ширина корзины версий), время создания |
| `matches` | `uid`, запуск, источник, раскладка, вид исхода, длина, seed, `env_steps`, блок, воркер, время (информационно) |
| `seats` | матч, место, команда, роль, агент, сеть, вид игрока, `version_start`, `version_end`, `rating_version`, награда, шаг выбывания, категория соперника (`source` SP3) |
| `teams` | матч, команда, ранг, очки |
| `counts` | сжатые матчи: раскладка, источник, канонический состав (команды → участники `агент@rating_version` с ролями), исход (ранги команд) → число матчей; для `score` — число, сумма и сумма квадратов очков |
| `meta` | версия схемы |

Индексы создаются сразу: по агенту и версии, по матчу (без индекса по матчу соединения на миллионе матчей не завершаются, `research/sp4_selection_practice.md` §4.2).

**Запись.** Журнал — библиотека (`MatchLog`), её вызывает тот, кто принимает результаты: главный процесс обучения, команда `tournament`, позже хаб SP5.
- В главном процессе обучения запись и сжатие идут в отдельном потоке со своим соединением. Главный цикл только ставит пачку результатов в очередь потока.
- Одна транзакция на пачку.
- Очередь результатов от воркеров увеличивается (10 000). Её переполнение больше не молчит: воркер считает потерянные результаты, в записи `system` появляется монотонный `dropped_match_results`, при первой потере — WARNING.

**Своевременная чистка (решение владельца).**
1. **Турнир и оценка во время обучения** (`tournament`, `pulse`) хранятся подробно всегда. Их мало: тысячи–десятки тысяч, это мегабайты.
2. **Обучающие матчи хранятся подробно в окне.** Когда файл больше `match_log.detail_window_mb` (по умолчанию 512 МБ ≈ 2.5 млн матчей), самые старые обучающие матчи пачками сворачиваются в `counts` и удаляются, затем выполняется `incremental_vacuum`.
   - `counts` — достаточная статистика для рейтингов блока 2, поэтому рейтинги до и после сжатия совпадают.
   - Теряются только подробности старых матчей: seed, длина, награды мест.
   - Размер `counts` зависит от числа разных составов, а не матчей: 100 снимков × 100 соперников ≈ 10 тыс. строк.
3. **Матчи вытесненного снимка** сворачиваются на ближайшем проходе чистки.
4. **Защита диска.** Если свободного места на диске журнала меньше `match_log.min_free_disk_mb` (по умолчанию 2048), новые обучающие матчи сразу идут в `counts`; при первом переходе — WARNING, в `system` — флаг. Когда место появляется, подробная запись возобновляется. Турнир при нехватке места пишет как обычно: его матчей мало.
5. **Обучение из-за журнала не падает:** ошибка записи — ERROR в лог и счётчик, кроме ошибок схемы при старте (`ConfigError`).

Ориентиры: крестики-нолики (~4 000 матчей/с) заполняют окно за ~10 мин и дальше не растут; игра вроде Lux (~20 матчей/с) не доходит до окна и за сутки.

**Resume из папки запуска.** Новый запуск создаёт свой `matches.db` с родителем в `runs` и импортирует из журнала исходного запуска `counts`, матчи турниров и оценки, а также подробное окно. Объём не больше окна. У папки запуска SP3 журнала нет: новый журнал начинается пустым, в логе INFO.

**Конфиг.**

```yaml
match_log:
  enabled: true            # false: только онлайн-ELO SP2; top-k и pulse требуют журнала (ConfigError)
  detail_window_mb: 512
  min_free_disk_mb: 2048
  compact_interval_sec: 60
```

**API для чтения** (отчёт, дашборд, турнир, хаб SP5): матчи с фильтрами (агент, версия, раскладка, источник, исход, диапазон `env_steps`); сравнения для рейтинга — пары команд с исходами и числом из подробных матчей и `counts` вместе; открытие только для чтения.

### Блок 2. Рейтинги снимков (Bradley–Terry)

**Сущности.**
- **Обучаемый агент:** `агент@v<B>`, где `B` — `rating_version` места.
  - Снимок `ckpt_v<N>` засчитывается версии `N`.
  - Latest засчитывается корзине: `B = ⌊version_start / checkpoint.interval⌋ · checkpoint.interval`, то есть снимку, сохранённому в начале этого отрезка обучения.
  - Финальный снимок с версией не кратной `interval` — своя сущность.
- **Скриптовый и замороженный агент** — своя сущность по имени (`агент`).
- **Линия** сущности — её `agent_id`. Средние по полю считаются по линиям, а не по снимкам: иначе сотни снимков одной линии раздувают оценку.

**Модель.** Рейтинги считаются отдельно для каждой раскладки, как в SP2/SP3.
- Единица — пара команд матча с T ≥ 2 командами, вес `1/(T−1)`, исход 1 / 0.5 / 0 по рангам. Это те же правила, что у нынешних `member_pairs`, только на уровне команд.
- Сила команды = среднее сил участников + поправка `b[раскладка, роли команды]`. Поправка ловит преимущество первого хода и асимметрию ролей (хищник/жертва).
- `P(A бьёт B) = σ(S_A − S_B)`, ничья вносит 0.5 (логистическое правдоподобие с дробным исходом).
- Гауссов приор на силы (против бесконечных оценок у «всегда проигрывающих»).
- Мягкий штраф гладкости между соседними версиями одной линии: малоигравшие снимки опираются на соседей, но реальные скачки видны.
- Шкала: показывается в Elo-единицах (`400 / ln 10` на логит). Ноль — якорь `ratings.anchor`:
  - по умолчанию это агент с `colosseum.players.RandomBot`, если он есть в конфиге;
  - иначе среднее скриптовых и замороженных агентов;
  - иначе среднее всех.

  Якорь делает шкалу сравнимой между запусками с тем же полем.
- Раскладки с одной командой (`score`) не дают попарных сравнений. Для них рейтинг — средний счёт сущности и состава с 95 % ДИ (как `ScoreTracker` / cross-play SP2), из подробных матчей и `counts`.

**Подгонка.** Своя реализация на numpy, без новых зависимостей: метод Ньютона по логистическому правдоподобию с приором и гладкостью, с тёплым стартом от прошлого решения.
- Неопределённость в двух режимах:
  - быстрая (обратный гессиан) — для живого рейтинга;
  - bootstrap — для отчёта, турнира и top-k (по умолчанию 200 реплик с тёплым стартом). Реплики берутся по матчам для обучения и оценки во время обучения и по блокам «seed + ротации» для турнира, так как игры блока коррелируют.
- На выходе для каждой сущности:
  - рейтинг и 95 % ДИ;
  - нижняя граница `LCB` (квантиль `checkpoint.top_k_quantile`, блок 4);
  - число игр;
  - `P(лучший)` и `P(в top-k)`.
- Диагностика нетранзитивности: log-loss модели против долей по парам на тех же данных. Большой разрыв в отчёте помечается как «возможны циклы».

**Живой рейтинг.** В главном процессе обучения подгонка повторяется раз в `ratings.refit_interval_sec` (по умолчанию 60) в фоновом потоке по журналу. От порядка партий результат не зависит. Куда он попадает:
- `ratings.json`: новый раздел `bt` по раскладкам — сущности, рейтинг, ДИ, игры;
- сжатая запись `ratings` в `metrics.jsonl`: по агенту — рейтинг его последней корзины и лучшего снимка;
- строка консоли: `bt <рейтинг> ± <ДИ>`;
- дашборд.

Онлайн-ELO, win-rate-матрицы, `wr_vs_past` и таблицы PFSP SP2/SP3 остаются без изменений. PFSP по-прежнему выбирает соперников по EMA-счёту; перевод PFSP на рейтинг — позже, по необходимости.

**Конфиг.**

```yaml
ratings:
  anchor: null               # имя агента-якоря; null: RandomBot конфига, иначе среднее фиксированных агентов
  refit_interval_sec: 60
  bootstrap_samples: 200
```

Сила приора и гладкости — константы модуля, выбираются в плане по кросс-валидации на журналах демо-игр и фиксируются как rulings. Ручки появятся, только если замер покажет, что одной пары значений мало.
