# SP5: Распределённый режим — дизайн

- **Дата:** 2026-10-17
- **Статус:** разделы 1–7 приняты владельцем по частям в брейншторме 2026-10-17; ревью субагента, раунд 1 (5 critical, 22 important, 22 minor) — исправления внесены, ответы владельца на три вопроса ревью учтены (один порт; что можно перенести в SP5b; продолжение на месте). Документ целиком ждёт одобрения владельца.
- **Ветка:** `sp5-distributed` (от `main` `d61eb02`, слияние SP4)
- **Основание:**
  - брейншторм 2026-10-17 (решения владельца — раздел 8);
  - исследования `research/sp5_distributed_architectures.md` (control plane: 16 систем, варианты hub-and-nodes) и `research/sp5_data_plane.md` (веса, траектории, сериализация, сжатие, общая память; замеры на этой машине);
  - досье кода `sp5-distributed` = `main` `d61eb02` (рабочий каталог SDD; выводы перенесены сюда — введение, блоки 4–7, разделы 8 и 9);
  - отложенные пункты SP1–SP4 с адресатом SP5 (CLAUDE.md «Open items», отчёты приёмки SP2–SP4), блок 8 спеки SP4 «Граница с SP5», §2 спек SP3 и SP4.

Пятый из шести подпроектов (см. «Roadmap» в CLAUDE.md). После SP4 всё, что нужно для соревнования, работает на одной машине: лига с обучаемыми, скриптовыми и замороженными игроками, warm start, журнал матчей, рейтинги снимков, турнир с отбором, отчёт и дашборд. Распределённый режим остался на уровне SP2:
- роли `serve-weight-store` / `run-learner` / `run-workers` без лиги, журнала, рейтингов, метрик и resume;
- три разных смысла бюджета (на воркер, на машину, по решениям);
- номера воркеров, id матчей и seed совпадают на разных машинах — при записи в журнал совпавшие матчи были бы молча потеряны;
- падение хранилища весов, по всей видимости, убивает лёрнер и воркеры; перезапущенный лёрнер с версии 0 воркеры игнорируют;
- нет шифрования и аутентификации; `deployment/` запускает устаревшую семантику.

SP5 делает обучение распределённым так, чтобы пользователь легко взял новый ноутбук, старый ПК, арендованную облачную VM и раскатил обучение на всём этом. **На одной машине `colosseum train` остаётся одной командой с прежним поведением и скоростью; конфиги и папки запусков SP3 и SP4 продолжают работать.**

## 1. Цель

1. **Хаб и узлы.** Отдельный процесс-хаб владеет прогоном (лига, журнал, рейтинги, хранилище снимков, оценка, метрики, бюджет). На каждой машине работает один узел, который запускает назначенные ему воркеры, лёрнеры и оценщиков. Лёрнер одного агента стоит на любой машине; хаб расставляет агентов по устройствам.
2. **Машины подключаются легко и надолго.** Одной командой на самой машине или по SSH с главной машины; узел получает от хаба код проекта и собирает окружение через uv; машину достаточно подключить к хабу один раз — узел сам берёт следующие прогоны этого хаба. Linux, macOS, Windows через WSL2. Снаружи должен быть доступен один порт — порт хаба.
3. **Все возможности SP3/SP4 на нескольких машинах.** Скриптовые и замороженные игроки, PFSP по снимкам, асимметричные роли, агенты, играющие не все роли, warm start (`init`, прогрев критика, kickstart, DAgger), журнал, рейтинги BT, top-k, pulse и турнир — без ограничений `check_distributed_scope`.
4. **Динамика.** Машины и агенты добавляются и убираются во время прогона.
5. **Отказоустойчивость.** Потеря машины с воркерами и падение лёрнера не останавливают прогон; перезапуск хаба — короткий перерыв, после которого узлы сами продолжают тот же прогон.
6. **Безопасность по умолчанию.** Шифрование и аутентификация включены и не требуют настройки.
7. **Попутно** закрываются отложенные пункты SP5 (раздел 9): один бюджет, resume распределённого лёрнера, кэш весов на машину, метрики распределённых ролей, уникальные id и seed, `max_policy_lag`, формат передачи.

**Можно перенести в SP5b без новой спеки** (решение владельца; если SP5 затянется, план ставит эти части в конец, и они уходят в продолжение целиком): агенты на лету (`agents …`, блок 6.1–6.3), `nodes update-code` (блок 6.4), SSH-режим (`nodes add`, блок 2.2), манифесты K8s (блок 10). Без них: состав агентов и код меняются перезапуском хаба `--resume` с новым конфигом (узлы подтягивают код сами); машины подключаются командой `join` или однострочником.

## 3. Критерии готовности

Пороги зафиксированы до замеров. Пункт, который проверить нельзя, в отчёте приёмки — «не проверено» с причиной, а не PASS. Пункт перенесённой в SP5b части (раздел 2) — «перенесено в SP5b».

**На одной машине:**

1. **Тесты.** Быстрый набор (`pytest -m "not gpu and not slow"`) зелёный, 0 предупреждений; `ruff check .` чистый. Соглашения SP1–SP4: файлы только в `tmp_path` (каталоги идентичности хаба и узлов тоже), процессы через `tests/cli_runner.py`, ни один тест не проверяет время по настенным часам. В быстром тесте не больше 2 загруженных CPU-процессов (воркеры, оценщики, лёрнеры; процессы хаба и узлов, в основном простаивающие, не считаются), в slow-тесте — не больше 3. Slow-набор зелёный целиком. У каждого пункта блоков 1–9 есть зелёный контрактный тест (таблица в отчёте).
2. **Скорость на одной машине.** `colosseum train` (хаб + локальный узел) на нагрузке бенчмарка SP4 (`scripts/bench_throughput.py`, крестики-нолики, журнал включён, pulse выключен, CPU-лёрнер) — не меньше 95 % от `main` (`d61eb02`) при 1 / 2 / 4 воркерах; по счётчикам, прогоны по очереди, по два на вариант (правило критерия 3.6 SP4).
3. **Хаб держит нагрузку.** На localhost 20 синтетических узлов по 16 воркеров (без сред) в течение 60 с. Смесь: спека крестиков-ноликов, 4 обучаемых и 2 фиксированных агента, по 50 снимков у каждого обучаемого в составах, журнал, живые рейтинги (`ratings.refit_interval_sec` 20) и top-k включены. Пороги: хаб принимает ≥ 20 000 результатов/с, потерь 0; ответ на запрос составов — p95 ≤ 200 мс; максимальная задержка ответа на запрос составов во время подгонки BT на ~2 000 сущностей ≤ 1 с.
4. **Кэш весов.** На каждую новую версию — ровно одно сетевое скачивание на (машину, агента) при любом числе воркеров (счётчик). Чтение воркером модели 50 МБ из общей памяти (`mmap` + `np.frombuffer` всех листьев, без `load_state_dict`) при публикации лёрнером 2 раза в секунду — p95 ≤ 100 мс.
5. **Формат передачи.** Разбор чанка из 256 слотов (~260 КБ, размер `space_miners`) вместе с проверками враждебного ввода и проверкой чанка не меньше чем в 10 раз быстрее нынешнего npz+JSON с `validate_chunk_payload`; тесты враждебного ввода зелёные.
6. **Совместимость.** Папка запуска SP4 продолжается на месте (`train --resume`) и дочерним прогоном (`training.resume_from`); конфиги `configs/examples/` проходят `validate` и обучаются на одной машине без правок; старые команды `serve-weight-store` / `run-learner` / `run-workers` дают ошибку с подсказкой; `validate` печатает план расстановки; два `train` на одной машине одновременно работают.
7. **Безопасность.** Без токена, с неверным токеном, без сертификата узла от хаба или с неверным отпечатком сертификата подключиться нельзя; без `--insecure` нельзя подключиться без TLS; с `--insecure` токен всё равно обязателен; отозванный узел (`--ban`) не подключается снова.

**На двух машинах** (ПК с GPU и ноутбук, обе машины — Windows + WSL2, локальная сеть). Топология — на ПК `colosseum hub` и `colosseum join` (узел ПК — отдельный процесс, не ребёнок хаба), на ноутбуке `colosseum join`; снаружи открыт только порт хаба на ПК, поэтому чанки ноутбука к лёрнеру ПК идут через порт хаба (путь данных указан в отчёте):

8. **Подключение.** Ноутбук без установленного colosseum подключается однострочником хаба. Несовпадение версии кода отвергается с понятным сообщением, а узел сам скачивает новый код и подключается. SSH-режим `nodes add` — на ноутбуке, если в его WSL будет sshd, иначе на контейнере или localhost (в отчёте сказано, где; часть SP5b, если SSH-режим перенесён).
9. **Масштабирование.** Нагрузка выбирается в плане по правилу: ПК в одиночку упирается в воркеров (классификатор узкого места бенчмарка), а ёмкость лёрнера, замеренная подачей готовых чанков, не меньше 1.2 × (a + b). Здесь a — шагов среды/с ПК в одиночку, b — воркеры ноутбука при лёрнере на ПК (воркеры ПК выключены). Две машины вместе дают ≥ 0.85 × (a + b); по счётчикам, прогоны по очереди, по два на вариант.
10. **Обучение.** Конвейер README (`configs/examples/unit_harvest_league.yaml`: агент `main`, якоря `greedy` и `random`, pulse на оценщике ноутбука — у ПК `--evaluators 0`, турнир `select` через `--hub`) на двух машинах проходит пороги SP3/SP4: победа над `random` ≥ 0.95, счёт против `greedy` ≥ 0.40, ρ pulse ≥ 0.85 (`RHO_MIN`). В журнале — матчи с обеих машин; повторы пачек отсеяны хабом, поэтому `duplicates` журнала = 0; по каждому узлу «отправлено = в журнале + учтённые потери»; `dropped_match_results` = 0.
11. **Отказы:**
    - ноутбук без сети 5 с — работа продолжается, идентичность узла и ячейки те же;
    - ноутбук без сети 60 с — ПК продолжает обучение, ноутбук сам подключается в течение 30 с после возврата сети;
    - `kill -9` лёрнера — поднимается с точки восстановления в течение 60 с, номера версий не идут назад, другие процессы узла не зависают;
    - `kill -9` воркера — узел перезапускает его, остальные воркеры и лёрнер работают, id матчей и seed не повторяются;
    - `kill -9` хаба и `hub --resume` — узлы подключаются в течение 30 с; лёрнер (узел ПК — отдельный процесс) во время перерыва учился, а воркеры получали его новые версии; результаты, не подтверждённые до падения, доставлены, повторов в журнале нет;
    - агент с `learner.device: cpu` и `learner.placement.node: <ноутбук>` (предпочтение), ноутбук отключён дольше `learner_relocate_after_sec` (120 с) — лёрнер переезжает на CPU-слот ПК;
    - Ctrl+C на хабе — за 30 с остановлено всё на обеих машинах (`shutdown_grace_sec` 20 с), финальные снимки сохранены.
12. **Агенты на лету** (часть SP5b, если перенесена). Конфиг конвейера с `opponents.anchors` > 0 и `match_refresh_interval_sec` 30: скриптовый агент, добавленный посреди прогона с весом якоря, появляется в составах за одно обновление ячеек; обучаемый — получает лёрнер, его версии растут; `freeze` и `remove` работают; `nodes update-code` с изменённым ботом перезапускает воркеры, прогон продолжается, у всех узлов новый хэш кода.
13. **Отчёт и дашборд.** Раздел «Узлы» есть; отчёт распределённого прогона собирается; владелец смотрит его с телефона.
14. **Упаковка.** Образ узла собирается; compose (хаб + 2 узла) доводит крестики-нолики до бюджета с кодом 0 — если на ПК включена интеграция Docker Desktop с WSL, иначе «не проверено». Манифесты K8s проходят статическую проверку (часть SP5b, если перенесены).
15. **Документация.** Быстрый старт `docs/DISTRIBUTED_GUIDE.md` повторён дословно на двух машинах; флаги совпадают с `--help`; README и CLAUDE.md описывают реальное состояние.

**Что понадобится от владельца на приёмке** (конфиги машин контроллер не меняет):
- на ПК один раз открыть для локальной сети TCP-порт 47100 (порт хаба): режим `mirrored` в `.wslconfig` + правило брандмауэра Hyper-V для 47100 или `netsh portproxy` 47100 + правило брандмауэра Windows (рецепт в `DISTRIBUTED_GUIDE`);
- на ноутбуке: выполнить однострочник подключения, на минуту выключить Wi-Fi, один раз закрыть терминал узла;
- по желанию: sshd в WSL ноутбука (SSH-режим, критерий 8) и интеграция Docker Desktop с WSL на ПК (критерий 14).

## 4. Принципы

- **Хаб — отдельная роль, не лёрнер.** Хаб не обучает и GPU ему не нужен; лёрнеров много, на разных машинах. На одной машине хаб и узел — разные процессы с тем же протоколом, что у удалённых узлов: путь кода один и проверяется локально.
- **Тонкий control plane, прямой data plane.** Хаб раздаёт работу и собирает результаты, траекторий не разбирает. Чанки и веса идут между узлами напрямую; через хаб — только для машины, недоступной снаружи (пересылка без распаковки).
- **Один порт снаружи.** Всё, что нужно другим машинам от машины хаба (сессия, большие данные, установщик, данные лёрнеров этой машины), идёт через порт хаба.
- **Узел просит работу сам** (pull): пропавшая машина просто перестаёт просить, её ячейки и недоигранные матчи исчезают.
- **Воркеры — расходный материал, лёрнер сохраняется, хаб — на диске.** Состояние хаба пишется в каталог прогона; перезапуск хаба = продолжение на месте.
- **Между перезапускаемыми процессами нет общих блокировок.** Каждый процесс говорит со своими получателями по собственным соединениям; смерть процесса не может заблокировать соседей.
- **Логика лиги, журнала, рейтингов и хранения SP3/SP4 не меняется.** Меняются только источники входа (сеть вместо очередей процессов) и состав агентов (динамический).
- **Безопасно по умолчанию, без настройки.** TLS (взаимный, с сертификатами от хаба) и токен включены. Pickle по сети не ходит.
- **Простота для пользователя важнее изящества.** Одна команда на машину; никаких обязательных Ray, Redis, K8s; ошибки — с подсказкой, что сделать.
- **Порядок — по счётчикам, время — по `time.monotonic()`.** Часы разных машин нигде не сравниваются (часы WSL2 скачут).
- **Ошибки громкие:** потеря данных всегда учтена счётчиком и WARNING; молчаливых фолбэков нет, кроме описанных здесь и унаследованных.
- **Решения SP1–SP4 в силе,** если этот документ явно их не меняет (раздел 8). Перед правкой области проверяются rulings отчётов приёмки SP1–SP4.
- **Тесты вперёд:** контрактные тесты потока результатов, составов и хранения пишутся до переноса главного процесса в хаб.

## 5. Дизайн по блокам

### Блок 1. Роли и топология

**Хаб** — `colosseum hub -c cfg.yaml` (один процесс на прогон):
- владеет каталогом прогона (`runs/<name>/`) и всем его состоянием: реестр узлов, матчмейкер, PFSP, онлайн-ELO, хранилище снимков с удержанием и закреплением, журнал матчей и живые рейтинги BT, планирование pulse и турниров, метрики (`metrics.jsonl`, WandB, консоль), `run.json`, `run_state.json`, `league_state.json`, `ratings.json`, `hub_state.json` (счётчики, блок 4.4), бюджет и остановка;
- по сути — нынешний главный процесс `Launcher` без порождения детей, с реестром узлов и gRPC-сервером;
- каталог прогона есть только на машине хаба;
- слушает все интерфейсы на `distributed.port` (47100); `--listen ADDR` сужает до одного адреса.

**Узел** — по одному на машину (`colosseum join …`, однострочник или `colosseum nodes add …`, блок 2):
- сообщает хабу железо; получает код и окружение; запускает назначенное: воркеры, лёрнеры агентов, оценщиков (pulse, блоки турниров);
- держит кэш весов в общей памяти для своих воркеров (блок 4.6), маршрутизирует чанки между машинами (блок 4.7), пачками отправляет хабу результаты и метрики, перезапускает упавшие процессы (блок 7);
- процесс узла — родитель своих воркеров, лёрнеров и оценщиков (они умирают вместе с ним).

**Лёрнер** — один на агента, как сейчас; стоит на любом узле:
- хаб расставляет агентов по слотам: `learner.device` `cuda` / `cuda:N` — слот GPU; `cpu` — CPU-слот; `auto` — слот GPU, если в кластере есть GPU-узел, иначе CPU (как `auto` локально);
- `learner.placement.node` (имя узла) и `learner.placement.tags` — предпочтение; при переезде (блок 7) допускается другой подходящий узел, если не `learner.placement.strict: true`;
- лёрнер не переезжает, пока жива его машина.

**`colosseum train -c cfg.yaml`** = хаб + локальный узел на этой машине: процесс `train` — хаб, локальный узел — его дочерний процесс (умирает вместе с хабом; упавший `train` продолжается `train --resume RUN`, блок 5.4).
- Без `--listen` хаб слушает только loopback на свободном порту (два `train` на одной машине не мешают друг другу); адрес пишется в `runs/<name>/hub.json` и в реестр работающих хабов машины (`~/.local/share/colosseum/hub/running/<pid>.json`).
- `train --listen [ADDR]` открывает `distributed.port` и печатает команду подключения; к идущему `train` подключаются другие машины.
- `rollout.num_workers` и прочие локальные настройки относятся к локальному узлу; локальный узел пишет логи в `runs/<name>/logs/`, как сейчас.
- Запомненные SSH-узлы и постоянные узлы (блок 2) используются только `hub` и `train --listen`, никогда — обычным `train`.

**`colosseum hub --idle -c cfg.yaml`** — хаб без обучаемых агентов: узлы подключаются только для оценки (турнир на кластере после обучения, блок 5.3); каталог — новый (`runs/<name>/`), как у прогона.

### Блок 2. Подключение машин и окружение

**2.1. Идентичность и доверие — на машину хаба, не на прогон.**
- Ключ хаба — корень доверия (CA, ECDSA P-256, самоподписанный) и секрет — лежат в `~/.local/share/colosseum/hub/` (XDG data dir), не в каталоге прогона. Хаб выпускает этим ключом свой серверный сертификат (имя `colosseum-hub`) и сертификаты узлов.
- Токен подключения `cst1.<секрет>.<отпечаток CA>` одинаков для всех прогонов этой машины. `colosseum hub token` печатает его; `--rotate` выпускает новый CA и секрет — все узлы отозваны.
- Машину подключают к хабу один раз: при первой регистрации узел создаёт свой ключ, хаб по токену подписывает ему клиентский сертификат (имя — id узла) и запоминает узел (`nodes.json` в каталоге идентичности, переживает перезапуски хаба). Узел хранит ключ и сертификат в `~/.local/share/colosseum/node/<отпечаток CA>/` и при переподключении остаётся тем же узлом (то же имя и номер).
- Токен в аргументах виден в истории оболочки: `--token-file FILE` и переменная `COLOSSEUM_TOKEN` — альтернативы `--token`.

**2.2. Способы подключения** (оба — решение владельца):
- **команда на машине:** хаб при старте печатает `colosseum join <адрес>:<порт> --token cst1…` для каждого своего адреса; узлу не нужны ни конфиг, ни адреса других машин;
- **однострочник для машины без colosseum:** хаб печатает команду целиком, например `printf '\0\0\0\0\0' | curl -fsS --http2 -k --pinnedpubkey 'sha256//<ключ>' -H 'content-type: application/grpc' -H 'te: trailers' --data-binary @- https://<адрес>:47100/colosseum.v1.Bootstrap/Script | tail -c +6 | COLOSSEUM_TOKEN='cst1…' sh`. Установщик отдаёт gRPC-метод того же порта хаба (решение владельца: один порт); ключ закреплён — подменить скрипт по дороге нельзя. Скрипт проверяет, что получил целый скрипт (контрольная строка в конце), ставит uv (если нет; с `astral.sh`), затем выполняет `join`. Если трюк с `curl` не заработает на прототипе (P6), контроллер возвращается к владельцу с вариантами (второй порт или без однострочника);
- **SSH с главной машины** (часть SP5b, если перенесена): `colosseum nodes add user@host [--workers N] [--evaluators N] [--name NAME] [--tags a,b]` — команда работающему хабу; хаб сам держит процесс системного `ssh` (`~/.ssh/config`, ключи и агент подхватываются; `ExitOnForwardFailure=yes`; `ssh` умирает вместе с хабом): передаёт установщик через stdin, пробрасывает обратным туннелем только порт хаба (`-R 0:127.0.0.1:<порт хаба>`, выделенный удалённый порт читается из вывода `ssh`), так что машине за NAT ничего настраивать не нужно; все данные этой машины идут через порт хаба. Обрыв SSH — туннель поднимается заново с нарастающей паузой. Хаб запоминает SSH-узлы в каталоге идентичности и поднимает их при старте `hub` / `train --listen` (пока не `nodes remove`). Список при старте: `--nodes hosts.txt` (строка — `user@host [флаги]`);
- `colosseum nodes list` — машины, железо, роли, состояние, путь данных, последний пульс; `colosseum nodes remove NAME [--ban]` — доиграть текущие матчи, остановить узел; `--ban` вносит узел (id и `machine-id` машины) в список запрещённых, так что повторная регистрация тем же токеном отвергается; полный отзыв — `hub token --rotate`.

**2.3. Код узла.**
- `colosseum join` — тонкий загрузчик: говорит с хабом только через минимальный версионированный сервис `Bootstrap` (версия протокола, хэш кода, список зависимостей, архив кода), собирает окружение и перезапускает себя (`exec`) как агент узла из окружения этого кода. Агент узла перезапускает себя так же при каждой смене хэша кода (новый прогон, `update-code`). Локально установленный colosseum другой версии на работу узла не влияет.
- Архив кода состоит из исходников пакета `colosseum` (каталог `colosseum.__file__`), каталога проекта (рабочий каталог хаба; он уже кладётся в `sys.path`) и исходников пакетов, установленных в окружение хаба как редактируемые из локальных путей вне проекта. Из проекта исключаются `runs/`, `.venv/`, `.git/`, `__pycache__/`, `.superpowers/`, файлы больше `distributed.bundle.max_file_mb` (10) и пути `distributed.bundle.exclude`; `distributed.bundle.include` добавляет пути. Хэш архива — идентичность кода.
- Узел хранит архивы в кэше по хэшу (`~/.cache/colosseum/bundles/<хэш>/`) и задаёт `PYTHONPATH` своим процессам на конкретный архив (не `.pth` в окружении: на одной машине одновременно могут работать два архива — два хаба или перезапуск по очереди). Рабочий каталог процессов узла — каталог проекта архива (боты читают файлы по относительным путям).
- Веса frozen-агентов, `init`, учителей и снимков в архив не входят — они идут по протоколу (блок 4.6).

**2.4. Зависимости на узле.**
- По умолчанию — точный список версий из окружения хаба (`importlib.metadata`) без `torch`, `nvidia-*`, `triton`, самого `colosseum` и пакетов из локальных путей (их исходники — в архиве); `distributed.requirements: <файл>` заменяет список своим.
- Python той же версии `major.minor`, что у хаба (uv ставит его сам при необходимости).
- `torch` той же версии, что у хаба, сборка — по железу узла: CUDA-колесо, если есть NVIDIA GPU и драйвер поддерживает сборку хаба (иначе ближайшая поддерживаемая CUDA-сборка той же версии; иначе CPU с WARNING); CPU-колесо на Linux без GPU; обычное колесо на macOS (CPU / MPS).
- Окружение — `~/.cache/colosseum/envs/<хэш зависимостей>/` (uv; общий кэш пакетов). Нужен доступ узла в интернет к PyPI, индексу PyTorch и `astral.sh` (или заранее установленный uv). Пакет без колеса для платформы узла — ошибка с именем пакета и подсказкой про `distributed.requirements`.

**2.5. Проверки при регистрации.** Хаб сверяет: версию протокола (несовпадение major — отказ), хэш кода (отказ с указанием: узел скачивает новый архив, перезапускается и регистрируется снова), версию Python `major.minor` (отказ), версию `torch` (отказ при другой версии, WARNING при другой сборке), платформу (отказ для нативного Windows), свободное место в `/dev/shm` и на диске кэша под ожидаемые веса (отказ с подсказкой).

**2.6. Ресурсы и расстановка.**
- Узел сообщает: логические и физические ядра (с учётом ограничений cgroup и привязки процесса), память, GPU (CUDA: имя, память; macOS: MPS), ОС, версии.
- Воркеры: по умолчанию физические ядра − 1 (минимум 1), `join --workers N`. На локальном узле `train` — `rollout.num_workers`, как сейчас.
- Оценщики: по умолчанию 1 на машинах с ≥ 4 физическими ядрами, иначе 0; `--evaluators N`.
- Слоты лёрнеров: GPU — по одному на GPU (`--gpus LIST` ограничивает); CPU — `join --cpu-learners N`, по умолчанию 1 на машинах с ≥ 4 физическими ядрами, иначе 0 (CPU-лёрнер делит ядра с воркерами, как сейчас на одной машине); `--no-learners` запрещает лёрнеры на машине.
- Агент без подходящего слота ждёт (`pending`): его места не собирают данные; соперником он играет последними весами, если они есть (resume или `init`), иначе не выдаётся в составы.

### Блок 3. Сеть и безопасность

**3.1. Порты.** Хаб: `distributed.port` (47100) — gRPC (HTTP/2, TLS): сессии, большие данные, установщик, пересылка. Узел: `distributed.data_port` (47102; при занятости — следующий свободный) — gRPC приём чанков и раздача весов своих агентов; узел пробует открыть его на всех интерфейсах и объявляет хабу. Снаружи должна быть доступна только машина хаба и только порт 47100; если порт данных узла другим недоступен, работает пересылка через хаб (блок 4.8). Узел машины хаба тоже получает чанки удалённых машин через порт хаба (локальная пересылка), пока владелец сам не откроет его порт данных. Набор портов проверяется (`port` ≠ `data_port`).

**3.2. TLS.** Все соединения — взаимный TLS с сертификатами от CA хаба: узел проверяет хаб и узлы-получатели по CA, закреплённому отпечатком в токене (имя сервера фиксировано — `colosseum-hub` / `colosseum-node`, переопределение имени цели в gRPC, поэтому адреса, туннели и `127.0.0.1` не важны; перед первым соединением узел получает сертификат хаба и сверяет отпечаток). Хаб и узлы принимают только клиентов с сертификатом от того же CA и не из списка запрещённых. Первая регистрация — по токену (секрет в метаданных поверх TLS с закреплённым CA), после неё — по сертификату узла. Пользователь сертификатами не занимается.

**3.3. Режимы.**
- `--insecure` (доверенная LAN): без TLS; секрет токена и ключ узла передаются в метаданных открытым текстом. В документации: ключи можно перехватить, данные — подменить; только для доверенной сети.
- Loopback (`train` без `--listen`): без TLS, токен из локального каталога идентичности.
- Админ-команды (`nodes …`, `agents …`, `tournament --hub`, `hub token`) выбирают хаб так: `--hub ADDR` (+ токен); иначе `--run RUN` (адрес из `runs/<name>/hub.json`); иначе единственный работающий хаб этой машины из реестра; несколько работающих — ошибка со списком. На машине хаба идентичность берётся из локального каталога; токен — полный доступ владельца.

**3.4. Модель угроз.** Защищаемся от: перехвата весов и кода ботов (в соревновании — ценность), подмешивания траекторий и результатов, чужих подключений, скачивания кода посторонними. Узел выполняет только код от хаба, которому доверяет по отпечатку; хаб никогда не выполняет код с узлов; данные разбираются без pickle с ограничениями размеров до выделения памяти (блок 4.9); результаты проверяются при приёме (блок 4.3); состояние тренера (`torch.save`) читается только с `weights_only=True`. Все узлы считаются машинами владельца: узел с украденным ключом можно только отозвать.

**3.5. WSL2.** Хаб проверяет, что работает в WSL2 в режиме NAT (`wslinfo --networking-mode` или `/proc/version` + адрес из 172.16.0.0/12), и печатает: снаружи его не видно, рецепт — `docs/DISTRIBUTED_GUIDE.md` (`mirrored` + правило брандмауэра Hyper-V, `netsh portproxy` + правило брандмауэра Windows, или Tailscale). Узлу в WSL2-NAT ничего не нужно: он звонит наружу.

**3.6. Зависимости фреймворка:** добавляется `cryptography` (выпуск сертификатов); на узлах — uv. `grpcio` уже есть.

### Блок 4. Протокол

**4.1. Каналы и сообщения.**
- **Сессия:** один постоянный двунаправленный gRPC-поток узел ↔ хаб для управления; большие данные по ней не идут.
- **Большие данные** (веса, снимки, frozen, архив кода, чекпоинты, точки восстановления) — отдельные вызовы с передачей по частям.
- **Пересылка** — отдельный долгоживущий поток `RelayInbox` от узла-получателя к хабу (блок 4.8), не сессия.
- **Порт данных узла** — потоки чанков от других узлов и раздача весов его агентов (`GetLatest(agent, since_version)` — «не изменилось» без тела или кадр весов).

Сообщения сессии:

| Направление | Сообщение | Смысл |
|---|---|---|
| узел → хаб | `Hello` | id узла, id сессии (новый при каждом старте процесса узла), версия протокола, хэш кода, железо, живые ячейки, накопительные счётчики, последние подтверждённые номера пачек |
| хаб → узел | `Welcome` | номер узла, `run_id`, полный снимок состояния: состав агентов, реестр версий, вытеснения, назначенные роли (лёрнеры с поколениями, оценщики) |
| узел → хаб | `Heartbeat` | раз в `distributed.heartbeat_sec` (1 с): накопительные шаги среды узла, состояние процессов, загрузка, версии в кэше |
| узел → хаб | `LineupRequest` | ячейки, которым нужен состав |
| хаб → узел | `LineupGrant` | ячейка, состав, срок (TTL), эпоха ячейки (блок 4.2) |
| узел → хаб | `ResultBatch` / `MetricsBatch` | номер пачки в сессии, результаты / метрики `train` и статистика воркеров |
| хаб → узел | `Ack` | подтверждённые номера пачек (результаты — после записи в журнал) |
| узел → хаб | `VersionAnnounce` | агент, поколение, версия, размер, хэш, где взять |
| узел → хаб | `Event` | смерть процесса, ошибка, хвост лога (блок 7.7) |
| хаб → узел | `Command` | запустить / остановить лёрнер (агент, поколение, ссылки на веса и состояние) или оценщика; отпустить узел; стоп прогона; обновить код |
| хаб → узел | `Announce` | новые версии, вытеснения снимков, изменения состава агентов, глобальный счётчик шагов среды |

**Возобновление сессии.** Обрыв потока — узел переподключается с нарастающей паузой (0.5 → 10 с) и шлёт `Hello` с тем же id узла и последними подтверждёнными номерами; хаб отвечает полным `Welcome`, узел переотправляет неподтверждённые пачки; хаб отсеивает повторы по (узел, сессия, номер пачки). Узел, молчащий `distributed.node_lost_after_sec` (10 с), считается потерянным (блок 7); вернувшийся раньше — продолжает с теми же ячейками.

**4.2. Ячейки и составы (pull).**
- Ячейка — (узел, воркер, среда). При каждой выдаче состава хаб даёт ячейке **эпоху** — номер, уникальный в прогоне, монотонный, сохраняемый в `hub_state.json`; новая эпоха — для каждой новой инкарнации воркера и после каждого продолжения прогона.
- Хаб выдаёт состав со сроком (`rollout.match_refresh_interval_sec`, 30 с; 0 — состав на весь прогон); узел отслеживает срок по своим монотонным часам и, когда он истёк, одним запросом берёт новые составы для всех таких ячеек; хаб по своим часам считает только потерю узлов и сроки заданий оценщиков.
- Узел передаёт состав воркеру, только когда все веса, которые он называет (latest, снимки, frozen), уже лежат в кэше машины; до этого среда играет прежним составом. Новый состав, как и сейчас, применяется в конце эпизода (`MatchRunner.set_next_lineup`).
- Не удалось скачать веса снимка (вытеснен и уже удалён) — состав отбрасывается, ячейка доигрывает прежний и просит снова, счётчик `lineup_fetch_failed`. Подмены снимка на latest с `collect=True` нет (меняет решение SP3, раздел 8).
- Вытесненный снимок хаб держит доступным для скачивания (жёсткая ссылка в `checkpoints/.evicted/`), пока на него ссылается выданный состав, но не дольше 2 × `match_refresh_interval_sec` после вытеснения.
- **Ротация владельцев.** Владельцами ячеек бывают только агенты с работающим лёрнером. На каждый запрос хаб назначает владельца каждой ячейке по дефициту: целевая доля × число живых собирающих ячеек − ячейки, которыми агент уже владеет; при равенстве — агент, следующий в порядке конфига за прежним владельцем этой ячейки. На одном узле с одновременным истечением всех ячеек это даёт сегодняшнюю последовательность `trainable[(g + round) % n]` (контрактный тест P0 остаётся зелёным); доли агентов не зависят от числа машин.
- Пока ни один агент не может собирать данные, хаб не выдаёт обучающих ячеек (бюджет не расходуется впустую).
- Матчмейкер (`MixtureMatchmaker` или `matchmaking.matchmaker_class`), PFSP и перестановка мест (`shuffle_seats`) — в хабе, как локально. `Coordinator.generate_lineups` не вызывается без обучаемых агентов (`hub --idle`, все агенты заморожены или убраны).
- Ячейки пропавшей машины исчезают; недоигранные матчи не засчитываются (нет результата — нет смещения PFSP).

**4.3. Результаты.**
- Узел собирает результаты своих воркеров в пачки (до `distributed.results_batch` 256 или раз в `distributed.results_flush_sec` 0.25 с) и шлёт их по сессии; держит неподтверждённые пачки до `Ack` в ограниченном буфере (`distributed.node_result_buffer_mb`, 256 МБ), в том числе всё время, пока хаба нет; переполнение учитывается в `dropped_match_results` (WARNING на первый).
- Хаб подтверждает пачку после того, как писатель журнала записал её результаты; падение хаба теряет только неподтверждённое, а его узлы переотправят.
- id матча глобально уникален: `match_id` = `w<W>_e<E>_g<эпоха>_ep<K>`, uid = `<run_id>/train/n<узел>/<match_id>`; seed эпизода зависит от эпохи (блок 7.6), поэтому перезапуск воркера, узла или продолжение прогона не повторяют ни id, ни seed.
- Журнал: новая колонка `node` (NULL у строк SP4), версия схемы в `meta`, миграция на месте при продолжении папки SP4 и при импорте; `worker` по-прежнему из `match_id`.
- Проверка при приёме: раскладка, места, роли, агенты (известные или исторические), конечные числа, поколение каждого места (результат места, сыгранного устаревшим поколением лёрнера, — блок 7.2). Неверный результат отбрасывается и учитывается (`dropped_match_results`, причина `invalid` / `stale_generation`, WARNING один раз на узел); результаты убранных агентов принимаются. Ошибка в результате никогда не роняет хаб.
- `env_steps` к результату ставит хаб при приёме, как сейчас.

**4.4. Бюджет.** Каждый узел шлёт накопительный счётчик шагов среды своей сессии; хаб хранит последнее значение на (узел, сессия) и считает глобальный счётчик как сохранённую базу + приросты с последнего сохранения. Хаб сохраняет глобальный счётчик и последние значения по сессиям в `hub_state.json` на каждом такте метрик; при продолжении прогона приросты считаются от сохранённых значений — шаги не теряются и не считаются дважды. Хаб — единственный, кто решает об остановке (`training.total_timesteps`), и рассылает её. Лёрнеры получают глобальный счётчик от хаба через узел (расписание LR; у агента, добавленного посреди прогона, — от его стартовой точки, блок 6). Перебор бюджета — около одного интервала пульса работы всех машин. Продолжение на или за бюджетом без нового `training.total_timesteps` — WARNING.

**4.5. Ход версий.** Лёрнер публикует новую версию в кэш своей машины и объявляет хабу (агент, поколение, версия, размер, хэш). Хаб хранит реестр «агент → поколение → последняя версия → где взять» и рассылает объявления. Номера версий никогда не идут назад: после перезапуска лёрнер продолжает с (максимальная объявленная версия + 1), даже если веса откатились к точке восстановления. Объявления, чекпоинты и точки восстановления устаревшего поколения хаб отвергает (блок 7.2). Пока хаба нет, узлы спрашивают последнюю версию прямо у порта данных машины лёрнера (`GetLatest`), так что воркеры получают новые веса и без хаба; лёрнер, доступный только через пересылку, после `distributed.hub_lost_collect_sec` (300 с) без хаба перестаёт получать данные: узлы снимают сбор с его мест (WARNING).

**4.6. Веса на машине.**
- Каждый узел раз в `rollout.weight_sync_interval_sec` сверяет версии своих агентов по объявлениям хаба (без хаба — по `GetLatest`); при новой — скачивает веса с порта данных машины лёрнера (или через хаб) один раз и публикует в общую память машины. Воркеры читают только общую память.
- Кадр весов несёт `agent_id`, поколение, `policy_version` и `teacher_active` (DAgger выключает опрос учителя у удалённых воркеров так же, как у локальных); веса frozen-агентов, учителей и `init` несут ещё описание архитектуры (содержимое `meta.json` или `networks`).
- Общая память: неизменяемые сегменты по версиям плюс файл-указатель на текущий; имена — `colosseum-<отпечаток CA, 8>-<run_id, 8>-n<узел>-<агент>-v<N>` (два хаба и тесты на одной машине не пересекаются); рядом файл-замок узла с его pid. Чтение — `os.open` + `mmap` (не `multiprocessing.shared_memory`: на Python 3.12 сторонний процесс удаляет чужой сегмент, `research/sp5_data_plane.md` §2.6.2; не seqlock: голодание читателей). Удаление сегмента после `mmap` читателя безопасно (POSIX); читатель, не нашедший сегмент по указателю, перечитывает указатель. Узел удаляет только сегменты, чей владелец мёртв (замок с pid). На macOS — `mmap` файлов во временном каталоге.
- На локальном узле `train` кэш заменяет почтовые ящики весов «лёрнер → каждый воркер» (закрывает «newest-wins eviction unpickles the stale payload»).
- Снимки-соперники, frozen-агенты, веса учителя и `init` хранятся в хабе и неизменны: узел скачивает их по id, когда они нужны в полученных составах (или назначенному лёрнеру), и держит в кэше машины; вытесненный снимок хаб объявляет, узел выбрасывает его, когда на нём не осталось составов.
- `/dev/shm` или диск кэша переполнены — ERROR с подсказкой (`docker --shm-size`, `emptyDir: Memory`); узел проверяет место при регистрации и перед публикацией сегмента.

**4.7. Траектории и связь процессов на машине.**
- **Без общих блокировок.** Каждый процесс узла (воркер, лёрнер, оценщик) говорит со своими получателями по собственным соединениям Unix-сокетов (`multiprocessing.connection` с ключом аутентификации), а не через общие очереди процессов и не через общие `mp.Value` / `mp.Event`: смерть процесса посреди передачи портит только его соединение. У каждой инкарнации лёрнера — свой адрес приёма; узел сообщает его воркерам. Счётчики шагов среды — накопительные по каждому воркеру через его соединение с узлом; остановка — сообщением, не общим событием.
- **Внутри машины:** воркер сериализует готовый чанк в кадр (блок 4.9) и отправляет его прямо лёрнеру по своему соединению; лёрнер принимает соединения от воркеров и от узла (чанки с других машин) и читает их через `multiprocessing.connection.wait`. Путь приёма у лёрнера один для локальных и сетевых чанков: кадр → разбор → проверка → пакет.
- **Между машинами:** воркер отдаёт кадр локальному узлу; узел держит по одному gRPC-потоку к каждой машине с лёрнерами и пересылает кадры, не распаковывая; узел-получатель передаёт кадр лёрнеру по соединению.
- Обратное давление сквозное: лёрнер не успевает → его соединения не читаются → отправители ждут (как сейчас на одной машине); между машинами — управление потоком gRPC.
- Доставка — не более одного раза: обрыв теряет чанки в пути; все потери учитываются по причинам (`dropped_chunks`: `disconnect`, `no_learner`, `stale`, `stale_generation`, `invalid`, `overflow`).
- У агента без лёрнера (`pending`, `failed`, переезд) хаб выдаёт составы, где его места не собирают данные; чанки, шедшие к упавшему лёрнеру или к устаревшему поколению, сбрасываются со счётом.
- **`learner.max_policy_lag`** (в версиях; `null` — выключено, по умолчанию): лёрнер сбрасывает чанки с `policy_version` старше `текущая − max_policy_lag` (`dropped_chunks.stale`). Лаг (`текущая − policy_version`) p50 / p95 / max пишется в `train` всегда.
- Скорость на одной машине (критерий 2) проверяется именно на этой схеме.

**4.8. Пересылка через хаб.** Достижимость решает отправитель: подключение к объявленным адресам порта данных; не удалось за `distributed.connect_timeout_sec` (5 с) — поток идёт через хаб. Узел-получатель держит к хабу отдельный поток `RelayInbox`; хаб пересылает кадры, не распаковывая, с ограниченным буфером на пару узлов и сквозным управлением потоком (переполнение — `dropped_chunks.overflow`); веса через хаб — частями, как большие данные. Чанки удалённых машин к лёрнерам машины хаба всегда идут так (локальная пересылка), если порт данных этой машины недоступен снаружи. Выбор пути виден в `nodes list` и логе (WARNING один раз на пару узлов); объём — в `system` (`relay_bytes`). `distributed.relay: false` запрещает пересылку (недостижимая машина тогда получает только роли без входящих данных, WARNING).

**4.9. Формат передачи.**
- **Кадр массивов** (чанки, веса, снимки, frozen, точки восстановления): `магия + версия формата (8 Б) | длина заголовка (8 Б) | JSON-заголовок | выровненные (64 Б) сырые буферы`. Заголовок: дерево (теги `dict` / `list` / `tuple` / `namedtuple` / `nd` как в SP1-формате), для листа — `dtype`, `shape`, смещение, длина; метаданные (agent_id, поколение, policy_version, `teacher_active`, uid, сжатие, архитектура для frozen / учителя / `init`). Раскладка в стиле safetensors, но с вложенными деревьями и без зависимости от библиотеки.
- Проверки враждебного ввода: длина заголовка ≤ 1 МиБ; сумма объявленных размеров ≤ `payload_byte_cap` до выделения памяти; смещения в пределах кадра и не пересекаются; dtype из белого списка (числовые и bool; без `object`); имена namedtuple — только уже загруженные классы; без pickle.
- Проверка чанка на лёрнере: структура слотов (`validate_slot_structure`), формы и dtype листьев наблюдений по спеке роли агента, конечный `behavior_logp`, нулевые награды на `boot` / `pad`, `teacher_action` в пределах пространства действий, `has_teacher` — bool.
- Сжатие lz4 — флаг кадра, адаптивно на агента: проба на первых чанках и раз в 10 минут, включается при коэффициенте ≥ 1.3; для весов по умолчанию выключено (float32 не сжимается: lz4 ×1.00, `research/sp5_data_plane.md`).
- Разбор — `np.frombuffer` по смещениям без копий там, где можно.
- **Управляющие сообщения** (таблица 4.1) — типизированный protobuf; схема `MatchResult` повторяет контракт записи матча SP4 (блок 1 спеки SP4) плюс поколение места и номер узла. Версия протокола — в `Hello` и в `Bootstrap`; `policy_version` и счётчики — `int64`.

**4.10. Что уходит.** Роли `serve-weight-store`, `run-learner`, `run-workers`, модуль `distributed.py` в нынешнем виде, `transport/` и `weight_store/` (кроме того, что переиспользуется), `LocalTransport`, `SharedMemoryWeightStore`, `proto/colosseum.proto` в нынешнем виде. Старые команды — ошибка (exit 2) с подсказкой «используйте `colosseum hub` / `join` / `nodes`». Ключи `transport.mode` / `transport.grpc_port` принимаются во входном YAML с одним WARNING и игнорируются; `transport.grpc_max_message_mb` переводится в `distributed.max_message_mb` (правило перевода SP2/SP3: старый и новый ключ вместе — `ConfigError`). Логирование хаба и узла начинается до проверок конфига (предупреждения проверок попадают в лог, а не только в консоль).

### Блок 5. Хаб: лига, хранилище, рейтинги, оценка

**5.1. Без изменения логики.** В хабе работают `Coordinator` (матчмейкер, PFSP, онлайн-ELO), `CheckpointManager` с удержанием SP4 и `colosseum pin`, `MatchLogWriter` и `LiveRatings`, `MetricsHub` / `MetricsWriter` / WandB, `league_state.json`, `pulse_state.json`, `ratings.json`, `run.json`, `run_state.json` (pid хаба), `colosseum report` / `dashboard` по каталогу прогона. Входы меняются: результаты, метрики, чекпоинты — из сессий узлов вместо очередей процессов. `league_state.json` хранит номер последней строки журнала, учтённой в ELO и PFSP.

**5.2. Чекпоинты и точки восстановления.**
- Лёрнер отправляет снимки (каждые `checkpoint.interval` версий и финальный) хабу; хаб — единственный, кто пишет `checkpoints/` (как сейчас главный процесс).
- **Точка восстановления:** модель + состояние тренера раз в `learner.recovery_interval_sec` (300 с) — хранится в хабе (`runs/<name>/recovery/<agent>/`), перезаписывается, в пул соперников не входит. Перезапуск лёрнера теряет не больше этого интервала. Перезапуск до первой точки восстановления — старт с `init` (или со снимка resume), номера версий всё равно продолжаются с максимальной + 1; в линии версий агента после такого перезапуска веса `v(M+1)` старше `vM` (гладкость BT по линии, ARENA_GUIDE).
- Состояние тренера (`torch.save`) хаб хранит байтами, не распаковывая; лёрнер читает его только с `weights_only=True`.

**5.3. Оценщики, pulse, турниры.**
- Оценщик — процесс узла, который берёт у хаба задания-блоки (блок SP4: seed + состав + повороты мест) и возвращает их результаты; движок блока — тот же `play_lineups` / расписание SP4.
- Блок выдаётся со сроком по часам хаба (`distributed.block_lease_sec`, 600 с) и выдаётся снова после его истечения или потери узла. Результат блока принимается только целиком и только один раз: первый полный выигрывает, поздние учитываются и отбрасываются.
- **Pulse:** `PulseFeeder` хаба нарезает оценку каждого `evaluation.every`-го снимка на блоки; блоки играются параллельно на разных машинах; правила SP4 те же (домен seed P, `max_backlog`, результаты только в журнал, финальный снимок локального прогона не оценивается). Снимок, выброшенный по `max_backlog`, снимает свои выданные блоки (результаты отбрасываются со счётом). Оценщиков нет — pulse ждёт, INFO; оценка снимка завершена, когда сыграны все его блоки.
- **Турнир на работающем хабе:** `colosseum tournament --hub … …` отправляет описание турнира хабу. Ведёт турнир хаб: расписание, отсев, подтверждение и отчёты; состояние — в `tournaments/<name>/` каталога прогона хаба; продолжение после `hub --resume`. Блоки идут в очередь оценщиков впереди pulse. Клиент после отправки показывает ход; Ctrl+C отсоединяет его (турнир идёт дальше), `--cancel NAME` отменяет. Коды клиента: 0 — турнир завершён (в том числе `confirmed: false`), 130 — отсоединён, 1 — турнир отменён или упал. Кандидаты из других каталогов прогонов (`--run`) читаются на машине хаба; веса уходят оценщикам по протоколу. Без `--hub` турнир работает локально, как в SP4.
- **`hub --idle`** — хаб без обучаемых агентов для турниров на кластере после обучения; отчёты турниров по чужим прогонам (`--run runs/x`) пишутся в `runs/x/tournaments/`, только если `runs/x` не принадлежит работающему хабу (иначе — ошибка с подсказкой отправить турнир тому хабу).

**5.4. Продолжение на месте** (решение владельца).
- `colosseum hub --resume RUN [-c cfg.yaml] [--set k=v …]` и `colosseum train --resume RUN [...]` продолжают **тот же** каталог и `run_id`: журнал дописывается, `run_state.json` снова `running`, логи дописываются, `config.resolved.yaml` переписывается (прежний сохраняется рядом с номером).
- Отказ (`ConfigError`), пока `run_state.json` называет живой процесс (два хаба на одном каталоге невозможны).
- Конфиг: без `-c` — сохранённый конфиг прогона плюс состав агентов (`agents_state.json`, блок 6); с `-c` — новый конфиг (можно добавить и убрать агентов; у оставшихся проверяется сигнатура ролей и архитектура, как при строгом resume), WARNING с разницей против сохранённого. `--set` действует в обоих случаях (например, новый `training.total_timesteps`).
- Восстанавливаются: счётчики из `hub_state.json` (блок 4.4), эпохи ячеек, лига (`league_state.json`; строки журнала после учтённого номера доигрываются в ELO и PFSP), снимки, точки восстановления; узлы сами переподключаются к тому же прогону (по `run_id`); лёрнеры стартуют с последней точки восстановления или снимка с `trainer_state.pt`.
- Папка SP4 (без `hub_state.json`, `agents_state.json`, колонки `node`) продолжается на месте: журнал мигрирует (версия схемы), состав — из конфига, счётчик — из журнала и `metrics.jsonl`, лёрнеры — со снимков.
- `training.resume_from` сохраняет семантику SP3/SP4: новый дочерний прогон с импортом родителя (rulings R4-06 / R5-13 не меняются для него).
- Закрывает «distributed learner resume».

### Блок 6. Агенты и код на лету

Блок можно перенести в SP5b целиком (раздел 2).

**6.1. Состав агентов прогона** — источник правды; хранится в каталоге прогона (`agents_state.json`: агенты, их фрагменты конфига, статус `active` / `frozen` / `removed`, точка старта в шагах среды, история) и переживает перезапуск хаба. Порядок старшинства при продолжении — блок 5.4.

**6.2. Команды:**
- `colosseum agents add --id X -c fragment.yaml` — обучаемый, скриптовый или frozen-агент. Хаб проверяет фрагмент как `validate` (модель и `unroll`, роли, бот в легальной игре, frozen-веса) в отдельном процессе, не в главном потоке хаба. Обучаемому ищет слот лёрнера; агент участвует в составах со следующего обновления ячеек. Веса frozen-агента или `init` из локального файла команда отправляет хабу. При `match_refresh_interval_sec: 0` — отказ (составы не обновляются).
- `colosseum agents freeze X` — лёрнер сохраняет финальный снимок и останавливается; этот снимок становится frozen-сущностью `X@v<N>` (рейтинг продолжается под ней); X больше не владеет ячейками; удержание снимков X останавливается (хранятся как есть); строки PFSP других агентов против X сохраняются.
- `colosseum agents remove X` — агент больше не выдаётся в составы; его снимки и история в журнале и рейтингах остаются; результаты с его участием, пришедшие после удаления, принимаются.
- `colosseum agents list` — состав, статус, где стоит лёрнер, поколение, версия, скорость.

**6.3. Динамическое членство.**
- `RatingBook`, `PfspStats`, `MetricsHub`, `LiveRatings` и ротация владельцев добавляют и выводят агентов во время прогона (сейчас берут состав при построении).
- Матчмейкер: новый крючок `BaseMatchmaker.on_agents_changed(context)`; по умолчанию хаб строит матчмейкер заново со свежим `MatchmakerContext` (пользовательские матчмейкеры, кэширующие список агентов, остаются правильными без правок; блок 8 спеки SP4 не нарушается — старый API не меняется).
- Расписания агента, добавленного посреди прогона (LR, λ kickstart, доли с расписанием по шагам среды), считаются от его точки старта.

**6.4. `colosseum nodes update-code`** — хаб собирает новый архив кода; узлы по очереди скачивают его и перезапускают воркеров и оценщиков в конце текущих эпизодов (агент узла перезапускает себя, блок 2.3). Отказ с подсказкой «перезапустите хаб с `--resume`», если изменились `GameSpec`, сигнатуры ролей, раскладки или код, который исполняет сам хаб (матчмейкер, проверки). Лёрнер перезапускается (с точки восстановления) только если изменились исходные файлы модулей, где определены классы из `networks` / `algorithm` агента, или пакет `colosseum` (`--restart-learners` — всегда). Изменённый скриптовый бот сохраняет имя сущности: чтобы сравнить старую и новую версии, новую добавляют под новым id (ARENA_GUIDE).

### Блок 7. Отказы и жизненный цикл

**7.1. Что автоматизируется:**

| Отказ | Поведение |
|---|---|
| Процесс воркера / оценщика умер без отчёта (segfault, OOM, сигнал) | узел перезапускает его, до 3 раз за 10 минут, с новыми соединениями и новой эпохой ячеек; лог узла + WARNING в хабе + `worker_restarts`; лимит исчерпан — слот выключен, узел сообщает хабу |
| `EnvContractError` / `PlayerError` (ошибка в коде среды или бота) | прогон останавливается, как сейчас: exit 1, хаб печатает ошибку с машиной, воркером, средой, местом, шагом эпизода, раскладкой и путём к логу |
| Машина с воркерами пропала (`node_lost_after_sec`, 10 с) | её ячейки и недоигранные матчи снимаются; остальные работают; машина вернулась — подключается сама и получает работу заново |
| Процесс лёрнера упал (CUDA OOM, исключение) | узел перезапускает его с точки восстановления, до 3 раз за 30 минут, с новым адресом приёма; лимит исчерпан — агент `failed`: обучение по нему остановлено, остальные учатся, ERROR в хабе и на дашборде, в конце прогона exit 1 |
| Машина с лёрнером пропала | хаб ждёт `distributed.learner_relocate_after_sec` (120 с), затем назначает лёрнер (новое поколение) на свободный слот подходящего устройства (предпочтение `placement` — блок 1; точка восстановления из хаба); слота нет — агент на паузе (`pending`) |
| Разрыв сети при живой машине | возобновление сессии (блок 4.1); вернулась за `node_lost_after_sec` — продолжает без потерь |
| Хаб упал / перезапускается | узлы продолжают текущие составы сверх срока; чанки и веса между машинами идут напрямую (версии — через `GetLatest`, блок 4.5) — лёрнеры учатся, воркеры получают новые веса; неподтверждённые результаты ждут в буфере; после `--resume` узлы переподключаются и переотправляют; хаба нет `distributed.hub_lost_timeout_sec` (1800 с) — узлы останавливают свои процессы и продолжают переподключаться с паузой 30–60 с (до `--once`, `nodes remove` или Ctrl+C) |
| Узел прислал испорченные данные | кадр или результат отбрасывается, счётчик по причине, WARNING один раз на узел |
| Нехватка `/dev/shm` или диска узла | ERROR с подсказкой; узел не берёт работу |

**7.2. Поколения лёрнеров.** Каждое назначение лёрнера агенту имеет номер поколения (растёт с каждым назначением, хранится в `hub_state.json`). Объявления версий, чекпоинты, точки восстановления, кадры весов и чанков, места в результатах несут поколение; хаб отвергает объявления, чекпоинты и результаты мест устаревшего поколения (`stale_generation`), лёрнер — чанки устаревшего поколения. Если после разрыва сети на старой машине продолжает работать прежний лёрнер, при переподключении хаб велит его остановить. Так одна и та же версия с разными весами не попадает в рейтинги, PFSP и метрики лага.

**7.3. Не автоматизируется:** перезапуск хаба фреймворком (ошибка в коде хаба дала бы цикл; рецепт `systemd` / `docker --restart`), дублирование хаба, соблюдение бюджета во время отсутствия хаба (перебор — не больше того, что машины сделали за перерыв).

**7.4. Остановка.** По бюджету, Ctrl+C или SIGTERM хаб рассылает stop; лёрнеры отправляют финальные снимки, воркеры досылают результаты, узлы гасят свои процессы и остаются на связи (если не `--once`). Локальная гарантия SP1 (на одной машине всё закрыто за 10 с, `SHUTDOWN_GRACE_SEC` 7 с) сохраняется; распределённая остановка — `distributed.shutdown_grace_sec` (20 с): финальные снимки едут по сети. Финальный снимок отправляется отдельным вызовом больших данных и не теряется из-за полной очереди (закрывает пункт SP5 о потере финального чекпоинта).

**7.5. Коды выхода.**
- `hub` / `train`: 0 — бюджет достигнут; 1 — ошибка конфига, ошибка контракта, агент `failed`, фатальная ошибка хаба; 2 — неверные аргументы; 130 — SIGINT; 143 — SIGTERM.
- `join`: 0 — нормальная остановка (`--once` после прогона, `nodes remove`); 1 — несовпадение версий без возможности обновиться, отказ в доступе, фатальная ошибка; 2 — неверные аргументы; 130 / 143 — сигналы (в том числе Ctrl+C после остановки процессов).
- `nodes …`, `agents …`, `hub token`: 0 / 1 (ошибка хаба или отказ) / 2 (аргументы); `tournament --hub` — блок 5.3.

**7.6. Время и seed.** Все таймауты — `time.monotonic()`; хаб по своим часам считает потерю узлов и сроки блоков, узел — сроки составов своих ячеек; часы машин не сравниваются. Seed ячейки — `derive_seed(training.seed, эпоха ячейки, узел, воркер, среда)` (закрывает «одинаковые seed на разных машинах»); seed эпизода — `SeedSequence([seed ячейки, эпизод])`. Seed блоков pulse и турниров — домены SP4 (A / B / P), не зависят от машины.

**7.7. Логи.** Удалённые узлы пишут логи в `~/.cache/colosseum/logs/<отпечаток CA, 8>/<run_id>/` (узел, воркеры, лёрнеры, оценщики). При смерти процесса узел отправляет хабу последние 64 КБ его лога; хаб кладёт их в `runs/<name>/logs/nodes/<узел>/<процесс>.log.tail` и называет в ERROR / WARNING оба пути. Локальный узел `train` пишет в `runs/<name>/logs/`, как сейчас.

**7.8. Переносимость.** Linux-специфичные места получают переносимую замену: смерть детей вместе с родителем (`PR_SET_PDEATHSIG` на Linux; на macOS — сторож-поток в ребёнке, проверяющий родителя), живость процесса (`/proc/<pid>/stat` на Linux; на macOS — `os.kill(pid, 0)` + время старта процесса из `ps`), общая память (`/dev/shm` на Linux; на macOS — `mmap` файлов во временном каталоге), короткие пути Unix-сокетов (на macOS — не длиннее 104 символов). Хаб работает на Linux и в WSL2 (macOS — по дизайну, не проверяется в приёмке).

### Блок 8. Метрики, отчёт и дашборд

- Статистика воркеров — по ключу (узел, воркер); монотонные счётчики (`dropped_reward_episodes`, `dropped_match_results`) остаются монотонными при подключении и уходе машин и при перезапусках воркеров (накопительные значения по инкарнациям суммируются).
- `system` (старые ключи сохраняются, контракт `REQUIRED_KEYS` расширяется): `nodes` (сейчас на связи), `nodes_lost` (накопительно), `by_node` (на узел: воркеры, шаги среды/с, результаты/с, загрузка, последний пульс, путь данных), `relay_bytes`, `dropped_chunks` по причинам, `dropped_match_results` по причинам, `lineup_fetch_failed`, `worker_restarts`, `learner_restarts`, `pending_agents`.
- `train` на агента: `policy_lag_p50` / `p95` / `max`, `dropped_stale_chunks`, `learner_node`, `generation`.
- `runs/<name>/nodes.json` — снимок реестра узлов на каждом такте метрик (для отчёта и дашборда).
- В отчёте и дашборде — раздел **«Узлы»**: машины, железо, роли, загрузка, скорость, когда последний раз на связи, путь данных (напрямую / через хаб); в разделе «Обучение» — лаг политики. Хаб может сам отдавать дашборд (`hub --dashboard [PORT]`, порт по умолчанию 8765, адрес по умолчанию 127.0.0.1, SSH-туннель — как в SP4).
- Консоль хаба: строка на агента (как сейчас) + строка узлов (число, суммарные шаги среды/с, потерянные).

## 6. Тестирование

- **Контрактные тесты до переноса** (P0): поток результатов главного процесса (каждый результат — в журнал ровно раз или в счётчик), выдача составов и ротация владельцев (`test_owner_rotates_with_global_env_index_and_round` и соседи), удержание снимков и вытеснения, resume папки SP4 — на нынешнем коде; после переноса в хаб те же тесты зелёные (ротация — через правило блока 4.2).
- **Формат кадра:** круговая сериализация всех деревьев чанка v2, весов (с `teacher_active`, поколением), состояний; враждебный ввод (огромный заголовок, пересекающиеся и выходящие за кадр смещения, `object` dtype, lz4-бомба, неизвестный namedtuple, отрицательные размеры); проверки чанка блока 4.9; совпадение с npz-форматом по содержимому; замер критерия 5 — скрипт плана.
- **Хаб с поддельными узлами в процессе:** регистрация и проверки (версии, хэш кода, платформа, токен, сертификат, запрет); сессия, возобновление, повторы пачек, подтверждение после записи журнала, потеря узла; составы, эпохи, ротация по дефициту при приходе и уходе узлов, ячейки без собирающих агентов; вытеснение снимка между выдачей состава и скачиванием; приём и проверка результатов (`invalid`, `stale_generation`); бюджет и сохранение счётчиков; реестр версий и поколения; пересылка; блоки оценщиков (срок, повторная выдача, только целый и первый результат); турнир в хабе; продолжение на месте (папка SP5 и SP4, отказ при живом хабе, доигрывание журнала в ELO / PFSP); агенты на лету и `on_agents_changed`; `idle`.
- **Узел с поддельным хабом:** расстановка процессов; кэш весов (одно скачивание на версию, сегменты и указатель, повтор чтения при пропавшем сегменте, удаление только мёртвых сегментов, имена двух хабов не пересекаются); состав не отдаётся воркеру до кэша; маршрутизация чанков, соединения процессов и обратное давление; `kill -9` каждого вида перезапускаемых процессов (воркер, лёрнер, оценщик) не блокирует остальных; буфер результатов без хаба; `GetLatest` без хаба; перезапуски по лимитам; DAgger-учитель выключается на удалённом воркере; самоперезапуск агента узла при новом хэше кода.
- **Несколько узлов на localhost** (интеграция): разные идентичности узлов на одной машине (каталоги идентичности под `tmp_path`); не больше 2 загруженных CPU-процессов на быстрый тест; внедрение отказов через TCP-прокси в тестах (обрыв, задержка, разрыв на 5 с и 30 с), убийство узла, лёрнера и хаба с `--resume`; поколения лёрнеров при разделении сети; два `train` на одной машине.
- **Безопасность:** взаимный TLS обязателен без `--insecure`; неверные токен, сертификат, отпечаток — отказ; `--insecure` без токена — отказ; `--ban`, `--rotate`; `--token-file` / `COLOSSEUM_TOKEN`.
- **Окружение:** состав архива и хэш (редактируемые пакеты вне проекта); список зависимостей (исключения); выбор сборки torch по железу (подмена проб); установщик в изолированном каталоге (с подменой uv, без сети); прототип однострочника `curl` против gRPC-метода (P6, первым делом); SSH-режим с подменой `ssh`; определение ядер с учётом cgroup.
- **Конфиг:** блок 9.1 (значения по умолчанию, перевод, `ConfigError`, `--set`, порты, `_make_config`).
- **Slow (не больше 3 загруженных CPU-процессов):** распределённый конвейер на localhost (хаб + 2 узла: лига с якорями, pulse на оценщике, `tournament --hub`, отчёт с разделом «Узлы»); нагрузка на хаб от 20 синтетических узлов × 16 воркеров (критерий 3; генератор — скрипт плана). Остальные slow-тесты SP2–SP4 — на `train` (хаб + локальный узел).
- **Docker** (`-m docker`, пропускаются без Docker): сборка образа, compose до бюджета.
- **Две машины** — приёмка (критерии 8–15): прогоны запускает контроллер с ПК; действия владельца на ноутбуке перечислены в разделе 3.
- Соглашения SP1–SP4 (раздел 3, критерий 1); порядок данных — по счётчикам.

**Процесс** — как в SP4:
- предварительная проверка согласованности плана (P-rulings);
- одна задача — один субагент-реализатор на Opus с high effort (TDD, коммит, push); независимые задачи — параллельно в git worktree;

## 8. Решения и риски

**Решения владельца** (брейншторм 2026-10-17 и ответы на вопросы ревью):

| Решение | Почему | Цена ошибки |
|---|---|---|
| Хаб — отдельная роль, не склеенный с лёрнером (вместо «хаб внутри `train`») | хабу не нужен GPU; лёрнеров несколько и на разных машинах; «хаб там, где первый лёрнер» — слабое основание | хаб и узел — разные процессы и на одной машине: результаты и составы идут по loopback-gRPC (критерий 2 следит за скоростью) |
| Пересылка через хаб для недоступных машин | машина с лёрнером за NAT тоже работает | трафик и GIL хаба (виден в `relay_bytes`) |
| Один порт снаружи; установщик — gRPC-метод того же порта | один порт для проброса на WSL2 и в облаке | однострочник с `curl` по HTTP/2 — «трюк»; проверяется прототипом первым делом |
| Оба способа подключения: команда на машине и SSH с главной | ноутбук рядом — команда; облачная VM — SSH; NAT не мешает | два пути бутстрапа |

| ОС: Linux, macOS, Windows через WSL2; первые проверки — две машины Windows + WSL2 | машины владельца | WSL2-NAT требует настройки на машине хаба; Mac проверяется отдельным шагом |
| Шифрование включено по умолчанию, невидимо (оценка контроллера, принята) | веса и код ботов — ценность в соревновании; защита от подмешивания и чужих подключений; цена TLS ничтожна | зависимость `cryptography`; `--insecure` для LAN |
| Автоматизировать: потерю машины с воркерами, падение лёрнера (перезапуск, переезд); хаб — перезапуск руками с самоподключением узлов | выбор владельца + решение контроллера по просьбе «подумай сам» | дублирования хаба нет |

| Доступ к хабу — на машину, узлы постоянные | машину подключают один раз | `--rotate` отзывает все узлы разом |
| Продолжение `--resume` — на месте (тот же каталог и `run_id`); `training.resume_from` — дочерний прогон, как раньше | узлы сами возвращаются в тот же прогон после перезапуска хаба | пересматривает R4-06 / R5-13 для `--resume`: каталог прогона дописывается, миграция папок SP4 |
